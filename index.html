ch01 · 手写 Qwen3 推理

解决什么问题：把"大模型推理到底在算什么"拆到最底层——不用任何推理框架，只用 Python 和 PyTorch 完成 Qwen3-0.6B 的 Tokenizer 与单请求自回归生成，为后续所有优化建立 baseline。

机制通俗版：baseline 是"裸生成"：读取模型配置和 Safetensors 权重，实现 Byte-level BPE 和 non-thinking Chat Template，逐层手写 Qwen3 前向，greedy decoding 逐 Token 生成。没有 variant——本期唯一变量是"能否自己跑通"，对照物是 Transformers：相同输入、greedy 条件下逐 Token 比较，三组 Prompt 的 Logits 最大误差均为 0。成本侧也裸露了问题：每次 Decode 都重新计算完整上下文（无 KV Cache），19 个输入 Token + 32 输出在 3080 Ti 上 Prefill 34.43 ms、平均 Decode 33.40 ms/token，峰值显存 1173.80 MiB。

架构上的位置：整个系列的起点。它确立了两条主线：一是 Prefill（一次处理整段 Prompt）与 Decode（逐 Token 生成）的延迟结构差异，二是"每步重算全部历史"这一明显浪费，正是 ch02 KV Cache 要解决的。边界：只支持固定 revision 的 0.6B dense 模型、batch size 1、greedy、关闭 thinking；聊天模板只覆盖 system/user 纯文本，不支持工具调用和多模态；单次测量不能外推。

业界对应：对应任何推理引擎的最小可运行内核；Transformers 在这里只作正确性对照，不进入推理路径。

讲给客户的一句话：在谈任何加速比之前，先建立一份可复现的 baseline——否则"优化"无从谈起。

深挖入口：帖子「手写Qwen3推理」（8/24）· 教材 p1

ch02 · KV Cache

解决什么问题：Decode 每生成一个 Token，都要对全部历史 Token 重跑模型层——历史越长浪费越大。KV Cache（把每层历史 K/V 存下来复用）是第一个推理优化。

机制通俗版：baseline 每次 Decode 用完整上下文重算；variant 保留每层历史 K/V，Decode 只算新 Token 的 Q/K/V 再追加进 Cache。Cache 是普通 Tensor，用 torch.cat 增长；Key 在 QK Norm 和 RoPE 之后写入，位置编号从 Cache 长度续算。实测揭示了关键边界：16 Token Prompt 下 KV Cache 反而负优化（端到端 1191 vs 1012 ms）——小模型短上下文中，Python 调度、Kernel Launch 和 torch.cat 重新分配的开销足以覆盖省下的计算；到 1024 Token 才有约 1.85× 加速（Decode 均值 60.43→32.64 ms）。Cache 数据量按公式 2 × layers × num_kv_heads × head_dim × seq_len × batch × dtype_bytes 线性增长，1024 Token Prompt 实测 115.39 MiB。

架构上的位置：依赖 ch01 的手写模型。两条关键边界：KV Cache 不减少 Prefill 计算，收益只在 Decode；Query 仍要读全部历史 K/V，所以 Decode 不是与上下文长度无关的常数复杂度。1.85× 只属于本软硬件组合，不能外推。

业界对应：vLLM 等引擎的 Cache 预分配与分页管理（ch05 起）远优于动态 torch.cat [业界通识]。

讲给客户的一句话：KV Cache 的收益随上下文变长才显现，短 Prompt 小模型上管理开销可能吃掉全部节省。

深挖入口：帖子「超轻量AI Infra入门教程02 kv cache」（8/25）· 教材 p45

ch03 · Static Batching

解决什么问题：单请求利用率太低——把多个请求合并成一个成员固定的 Batch，共享一次模型前向，提高 GPU 并行度。

机制通俗版：baseline 是多个带 KV Cache 的请求逐个串行执行；variant 把它们组成固定 Batch：不同长度 Prompt 左 Padding + Attention Mask，一次 Batched Prefill，之后按 Batch 槽位组织 KV Cache 同步 Decode。关键约束：Batch 开始后不进新请求，完成请求的槽位空转到最长请求结束。代价随即暴露：混合长度组的有效槽位利用率仅 46.88%，有效吞吐从 115.30 掉到 57.63 token/s——这是 Padding 浪费，不是"短 Prompt 拖慢 Batch"。收益侧：Batch Size 16 相对串行 makespan 约 13.98×；但 Batch Size 192 吞吐 2981.83 token/s 高于 196 的 2931.97——接近显存边界后延迟上升，最大 Batch ≠ 吞吐最优 Batch。float32 下无请求串扰；bfloat16 下因矩阵 Shape 改变可能分叉，不属于准确性问题。

架构上的位置：依赖 ch02 的 KV Cache（扩展为 Batched KV Cache）。它是 ch04 Continuous Batching 的 baseline：固定批次的"完成槽位无法服务等待请求"正是后者的优化点。离线结果不含排队和网络，不代表在线 SLO。

业界对应：离线批量任务仍用固定 Batch 思路；在线服务已被 Continuous Batching 取代 [业界通识]。

讲给客户的一句话：拼批能提吞吐，但请求长短不齐时 padding 空转可能浪费一半算力。

深挖入口：帖子「Static Batching」（8/26）· 教材 p72

ch04 · Continuous Batching

解决什么问题：固定 Batch 里已完成请求的槽位空转到整批结束。Continuous Batching 允许这些名额在下一次迭代被等待请求复用。

机制通俗版：baseline 是成员固定的批次；variant 在每次模型迭代前执行"回收完成槽位 → FCFS 填补 → 有新请求做 Batched Prefill，否则 Decode"。唯一变量是"完成名额能否复用"。异长输出场景 Makespan 加速 1.169×、吞吐 +16.8%、槽位有效率 62.50%→74.07%；等长输出负对照两条路径几乎无差（约 0.4%）——没有可提前复用的槽位就没有收益，机制成立的前提是负载不整齐。固定到达轨迹下加速 1.486×、TTFT p95 从 1511 降到 205 ms，但 ITL p95 从 36.50 升至 71.48 ms：新请求 Prefill 会阻塞已有请求的 Decode，这是留给 ch07 的伏笔。KV Cache 本期仍是 dense 槽位，扩容需搬移。

架构上的位置：依赖 ch03 的 Batched 执行与 KV Cache。关键边界：本期 Prefill 优先、FCFS 是为了可复现而非最优；dense Cache 的扩容搬移引出 ch05 Paged KV Cache。

业界对应：vLLM/SGLang 等在线引擎的标准调度方式 [业界通识]，源自 Orca 论文 [业界通识]。

讲给客户的一句话：Continuous Batching 让新请求"见缝插针"，但 Prefill 与 Decode 会互相干扰——延迟分位数要一起看。

深挖入口：帖子「连续批处理」（8/27）· 教材 p102

ch05 · Paged KV Cache

解决什么问题：dense KV Cache 按全局最长请求预留物理宽度：一个 4096 Token 请求会让所有槽位在 4096 级别上跑 masked Attention，长度不均时显存浪费严重。

机制通俗版：baseline 沿用 dense 槽位，长请求加入时所有层所有槽位一起左扩容搬移；variant 借鉴操作系统虚拟内存分页（把显存切成固定大小的物理 Block，用 Block Table 把逻辑 Token 位置映射到物理块）：请求只为实际长度申请 Block，尾块内的浪费被限制在最后一个 Block，完成后物理块直接归还复用，不动其他请求的 K/V。实测：长度越不均，KV 读取减少越多（3072 Token 长请求下 KV 读取减少 94.1%、Cache Pool 减少 82.6%），但同并发吞吐反而降 36–45%——PyTorch reference 的 Block gather、分组 Attention 和额外 Kernel Launch 吃掉了计算节省。真正的收益在容量：12GB 卡上 dense 最大成功并发 8（12 起 OOM），paged 跑到并发 16，吞吐 157.80 token/s 略高于 dense 最优、峰值显存低约 43%。

架构上的位置：依赖 ch04 的 Continuous Batching。两条边界：减少 K/V 访问 ≠ 端到端更快，Kernel 效率同样关键；Block Pool 容量按已知上界预分配，无动态准入。它是 ch08 前缀共享和 ch12 换出的物理基础。

业界对应：vLLM 的 PagedAttention [业界通识]，专用 CUDA/Triton Kernel 直接读 Block Table，无本期 reference 路径的开销。

讲给客户的一句话：分页的价值是把显存从"按最长请求预留"变成"按需分配"，同一张卡能多接一倍请求。

深挖入口：帖子「从零实现Paged KV Cache」（8/28）· 教材 p144

ch06 · 迭代级推理请求调度器

解决什么问题：ch05 的调度没有算力预算：Prefill burst 一次涌入时，调度器可能连续多轮做 Prefill，已有 Decode 请求被长时间饿停。

机制通俗版：baseline 是纯 FCFS——有空闲槽位就一次 Prefill 所有可加入请求；variant 是软 Token Budget：按 padded cost（batch_size × max(prompt_length)）扣预算，预算不足即停，且已有 Decode 时两个 Prefill iteration 之间至少插一次 Decode iteration。"软"的含义：单条 Prompt 超预算时不拆分，允许队头超预算执行避免永久阻塞。突发 12 条长短混合 Prompt 的实测：budget 2048 相对 baseline 吞吐 +13.1%、既有请求最大 ITL 降 58.5%、Padding 减少 53.0%，但 ITL p95 从 98.52 升到 207.37 ms——把一次长停顿拆成多次中等停顿，不是延迟全面改善。budget 256 过紧，反而因超预算请求吞吐 -6.8%。

架构上的位置：依赖 ch05 的 Paged KV Cache 与 Continuous Batching，是 ch07 的前半步。边界：不做显存准入、抢占、优先级和 P/D 分离；预算按 padded 而非有效 Token 计，Padding 本身也耗预算。

业界对应：vLLM/SGLang 迭代级调度与 Decode 保护 [业界通识]。

讲给客户的一句话：调度器的核心不是"多接请求"，而是控制单轮 Prefill 的预算，让已开始的对话不被卡住。

深挖入口：帖子「MiniInfra系列之推理请求调度器」（8/31）· 教材 p183

ch07 · Chunked Prefill

解决什么问题：软预算下长 Prompt 必须整条执行：一条 2048 Token 的 Prefill 会让同批 Decode 停数百毫秒。只有单条 Prompt 可拆，Token Budget 才能成为硬约束。

机制通俗版：baseline（full）沿用 ch06 软预算，长 Prompt 一次算完、可以超预算；variant（chunked）给请求新增 prefilling 状态和 prefill_cursor，把 Prompt 按 Token Budget 切成多轮，每轮只把本段 K/V 追加到 Block Table，中间 Chunk 不出 Token，最后一块完成才生成首 Token。2048 Token 长 Prompt 干扰实验：budget 256 把最大单轮 Prefill 从 316.28 缩到 65.39 ms（-79.3%）、既有请求最大 ITL 降 67.8%、峰值显存降 16.8%；代价是长请求 TTFT +141.6%、吞吐 -6.2%。两个负对照很说明问题：短 Prompt 场景 chunked 没有可拆工作，反而慢 6.4%；无并行 Decode 场景收益按定义为零。budget 1024 是本负载下吞吐与 TTFT 更平衡的档位。

架构上的位置：依赖 ch05 的 Paged Cache（支持跨块追加）和 ch06 的调度器，完成"无预算 → 软预算 → 硬预算 + Chunked Prefill"的调度三连。边界：这是引擎内部的序列增量计算，不是 RAG 切分或流式接收；chunk 越小停顿越短，但迭代与 Kernel Launch 开销越多。

业界对应：vLLM/SGLang 均默认启用 Chunked Prefill [业界通识]。

讲给客户的一句话：Chunked Prefill 把长 Prompt 拆成多次小步，用首 Token 稍晚换取其他请求不掉帧——本质是延迟在请求间的再分配。

深挖入口：帖子「从零实现Chunked Prefill」（9/3）· 教材 p225

ch08 · Prefix Cache

解决什么问题：多条请求共享同一长前缀（系统提示、few-shot、文档）时，前缀 KV 被反复重算。块级 Prefix Cache 让后续请求复用已算好的完整 Prompt KV Block。

机制通俗版：baseline 每条请求重算完整 Prompt；variant 匹配最长连续完整前缀，只算未命中后缀。两个安全设计是关键：一是缓存键不是对当前块单独哈希，而是 SHA256(model_namespace || parent_hash || block_token_ids)——相同 Token 块在不同历史上下文里 KV 不同，不能误命中；二是只共享已填满并发布为不可变的 Block，未填满的尾块和 Decode Block 私有，因此无需 Copy-on-Write；且 KV 不含首 Token Logits，最多复用 prompt_length - 1，至少重算最后一个 Prompt Token。实测 8 条请求共享 2048 Token 前缀：热请求 service TTFT p50 降 86.30%、Prefill Token 减少 84.85%，但 Makespan 只降 11.33%——Decode 不受益，且缓存池多占 280 MiB。生命周期用引用计数 + leaf-LRU：请求结束只减请求引用，缓存索引仍持有的块不回池。

架构上的位置：依赖 ch05 的物理块与 ch07 的 Chunked Prefill。边界：不做部分块共享/COW、并发冷请求去重、跨模型或跨进程共享（后者是 ch14）。

业界对应：vLLM Prefix Caching、SGLang RadixAttention [业界通识]；跨进程共享见 LMCache（ch14）。

讲给客户的一句话：命中率取决于业务前缀是否整齐；命中省的是 TTFT 和 Prefill 算力，Decode 一秒都省不了。

深挖入口：帖子「从零实现Prefix Cache-infra系列教程8」（9/4）· 教材 p256

ch09 · FlashAttention

解决什么问题：Eager Attention 显式物化 QK^T → softmax → PV 的完整 Score 和 Probability 矩阵，中间显存随序列长度平方增长——4096 Token 增量峰值 2576 MiB，8192 直接 OOM。

机制通俗版：baseline 是 Eager 路径；variant 用 Triton 手写 inference-only FlashAttention 前向：分块读取 K/V，每个 Query 行维护最大值 m、归一化和 l 与累加器 acc，用 Online Softmax 逐块修正（alpha = exp(m - m_new)），完整中间矩阵不落显存。数学结果相同，计算量仍是二次方，降的是显存读写。微基准（因果 Attention、head_dim 128）：1024 Token 加速 3.38×、4096 达 3.70× 且增量峰值仅 16 MiB；但接入完整引擎后端到端只有 1.08–1.10×——Chunked Prefill 把 Query 限制在 256，Projection、MLP、调度和 Cache 管理稀释了 Kernel 收益。这是"Kernel 加速比 ≠ 模型加速比"的典型教材。工程细节：Chunked Prefill 要用全局因果偏移 k <= P + q，不能按局部位置算。

架构上的位置：依赖 ch05–ch08 的引擎底座；不依赖第三方 flash-attn 包。边界：不支持 backward/任意 Mask/直接读 Block Table 的 Paged Attention。

业界对应：FlashAttention 官方库、vLLM/SGLang 内置融合 Attention [业界通识]。

讲给客户的一句话：FlashAttention 省的不是计算量而是显存搬运，序列越长收益越大，但整体加速要看它占总时间多少。

深挖入口：帖子「手写FlashAttention」（9/6）· 教材 p291

ch10 · CUDA Graph

解决什么问题：Decode 每步计算量很小，而 Eager 路径单步约 1903 次 cudaLaunchKernel——Host 提交开销占了主导。

机制通俗版：baseline（static_eager）每轮逐个提交 Kernel；variant 把同一组 Kernel 提前捕获成 CUDA Graph，之后更新输入缓冲、一次 cudaGraphLaunch 重放。代价是静态化：每个 (batch_capacity, context_bucket) 建 Runner，预分配全部 Buffer 和覆盖 Bucket 的 KV Block，地址形状不变，无效位置用 Mask 屏蔽。实测：capacity 1、128 Token 下 Decode TPOT 从 37.90 降到 5.22 ms（7.26×）；但上下文与 Batch 变大后 GPU 工作变重，加速比降到 2.25×——Graph 不减少计算，能消除的只有 Host 开销。Capture 耗时 95–140 ms，约 3–5 个 Decode 步即可摊销。端到端提示：Prefill 仍是 Eager，2048 Token 请求 TPOT 提升 4.03× 但端到端只有 2.53×。

架构上的位置：依赖 ch09 的 FlashAttention 和静态 KV Pool。边界：需要 Bucket/Padding 换取可捕获性，Bucket 尾部有无效读取；请求准入和 Block 分配仍在 Graph 外。逐 Token .item() 同步会掩盖收益。

业界对应：vLLM/SGLang 均对 Decode 使用 CUDA Graph，按 batch/context 分档缓存 Graph 实例 [业界通识]。

讲给客户的一句话：CUDA Graph 解决的是"CPU 指挥慢于 GPU 计算"的问题，Batch 和上下文越大、剩余收益越小。

ch11 · Greedy Speculative Decoding

解决什么问题：Decode 逐 Token 串行调用大模型。Speculative Decoding 用小 Draft Model 快速提候选，大模型一次并行验证多个，减少串行 Target 调用。

机制通俗版：Qwen3-0.6B 做 Draft 连续提出 γ 个候选，Qwen3-4B 做 Target 一次块验证：接受最长匹配前缀，拒绝处补 Correction Token，全对时补 Bonus Token；两套 KV Cache 按同一接受边界提交或回滚。数学上 Greedy 输出与 Target-only 完全等价（FP16 下实测逐 Token 一致）。但实测在 3080 Ti 上几乎全是负优化：中文解释负载 γ=8 接受率仅 0.173，TPOT 加速比 0.284×；只有接受率 1.0 的代码样例在 γ=8 得到 1.023×。根因在组件成本：Draft 单步 42.51 ms 只比 Target 的 48.16 ms 快约 12%——Eager 教学栈里两者都被小算子和 Host Launch 拖住，参数量 6.7 倍差距没有转化为速度差，而一轮推测还要多付 γ+1 次 Draft 前向。

架构上的位置：本期是独立实现（PyTorch SDPA、float16）。边界：只做 Greedy（不做随机 Speculative Sampling）、Batch 1、无 MTP/EAGLE/Medusa；KV 回滚必须与输出提交同一接受边界。

业界对应：vLLM/SGLang 内置 speculative decoding；MTP/EAGLE 是更轻的候选生成器 [业界通识]。

讲给客户的一句话：投机解码是"用便宜计算赌接受率"，Draft 不够快或接受率不够高时是纯亏——上线前必须按业务负载实测。

深挖入口：帖子「Greedy Speculative Decoding」（9/10）· 教材 p362

ch12 · KV Cache Offloading（抢占式换出）

解决什么问题：GPU Block 不足时新请求进不来。乐观准入 + 抢占：暂停受害请求，把它的 KV 挪走腾出显存，让系统级并发超过 GPU 池容量——容量不足从"失败"变成"延迟"。

机制通俗版：两个抢占路径对比。swap：整请求 KV 经 PCIe 换出到 Pinned CPU 池，恢复时换回断点续算；recompute：KV 直接丢弃，恢复时对 prompt + 已生成部分重新 Prefill。为什么是整请求：Decode 每步 Attention 要读全部历史 KV，"运行中部分换出"不存在。实测决策依据清晰：swap 双向传输约 49–63 ms（实测约 11.9 GB/s，仅对 PCIe Gen3 x16 平台有效），recompute 的重新 Prefill 暴露 673–764 ms——本环境下 swap 机制成本明显更低，但端到端均值受负载支配，不能只看一次均值。容量收益成立：同池下 swap 吞吐 37.0 vs 保守准入 35.7 token/s（池 230）、44.9 vs 40.7（池 320）；但都低于 664 块大池的 45.5——池充足时抢占收益为零。ITL max 约等于受害请求的秒级暂停，主要代价落在被抢占请求自身。

架构上的位置：依赖 ch05 的 Paged Cache 与 ch07 的调度器；单请求上下文上限仍由 GPU 池决定。换出副本只用于恢复，不做共享复用（那是 ch14）；同步拷贝停顿是 ch13 的优化对象。

业界对应：vLLM 的 swap 抢占与 CPU Offload [业界通识]。

讲给客户的一句话：换出把"显存不够就失败"变成"慢一点但能跑"，代价由被抢占请求的延迟承担。

深挖入口：帖子「KV Cache Offloading」（9/12）· 教材 p381

ch13 · KV Cache 异步传输

解决什么问题：ch12 的换出/换入在默认计算 Stream 上同步拷贝，拷贝期间 GPU 不推进其他工作——传输等待全部暴露。

机制通俗版：baseline（sync）在计算 Stream 逐块传输，完成后调度器才继续；variant（async）在独立 Copy Stream 上提交 D2H/H2D，用 CUDA Event 延迟转移 Block 所有权：D2H 完成前 GPU 源块不能释放，H2D 完成前目标块不能读；调度器只在无工作可做或下一步必须申请 Block 时才等 Event。请求新增 swapping_out / swapped / swapping_in 中间状态。受控微基准证明本机具备重叠能力（传输与 GEMM 并发 1.21–1.50×）；但主实验不是单向正优化：池 230 组 async 略慢（39.31 vs 39.61 token/s），池 320 组较快（47.62 vs 45.55）——D2H 在紧急水位触发、完成前源块不能释放，重叠窗口可能大部分暴露。机制结论要看分阶段 Event 指标：async 把暴露等待从 48.3 降到 20.0 ms（池 230）。

架构上的位置：依赖 ch12 的两级池与抢占语义。边界：能隐藏多少取决于有无独立计算和抢占触发时机；"异步提交"不等于"传输完成"，也不保证端到端更快。

业界对应：vLLM/SGLang offloading 与 NIXL 等传输层的异步流设计 [业界通识]。

讲给客户的一句话：异步传输的正确性靠 Event 管理块所有权，收益靠"传输时有没有别的计算可做"——不是开了就快。

ch14 · 外部 KV Cache 与 LMCache

解决什么问题：ch08 的 Prefix Cache 只在同一进程内共享物理块；多引擎实例、重启后的进程都无法复用彼此的 KV。外部 KV Cache 用进程无关的标识把 KV 变成可跨进程、跨请求命中的服务。

机制通俗版：baseline（recompute）新请求完整重算；variant（external）用链式 CacheKey SHA256(model namespace || parent digest || token ids) 标识 256 Token 的外部 Chunk，向独立 Cache Service 发 Lookup/Load/Store，命中的 CPU KV 重建到新申请的本地 GPU Block（重建 Block Table，因为外部对象不含本地 Block ID），只 Prefill 未命中后缀。与 ch08 的关键差异：只存 prompt_length - 1 范围的完整 Chunk，KV 不含首 Token Logits，所以至少要重算最后一个 Prompt Token 才能出首 Token。正确性完美：跨进程命中 512 Token、warm Prefill 只算 1 Token、输出与重算逐位一致。但性能全是负优化：2048 Token 前缀 warm TTFT 2131.68 ms vs 重算 480.62 ms（0.23×）——Lookup 只要约 1 ms，成本在 TCP 传输（Payload 约 235 MB）与逐 Chunk 重建。"已经命中"不等于"值得加载"。

架构上的位置：与 ch12/13 不同：CPU KV 由 Token Chunk 标识，可被任意请求/进程命中，不只恢复原请求。业界映射：ExternalCacheClient→Connector、Memory Object、CPU Backend + LRU 等 LMCache 职责。边界：同步 TCP + 用户态复制，非共享内存/RDMA；命中收益取决于传输路径与模型规模。

讲给客户的一句话：外部 KV Cache 的价值在"命中率 × 复用范围"，但必须保证加载比重算快——慢速传输会让缓存变负资产。

ch15 · Prefill/Decode 分离

解决什么问题：Prefill 是计算密集、Decode 是访存密集，混在一个 Worker 里互相干扰。P/D 分离让 Prefill Worker 算完 Prompt KV 和首 Token，把 KV 移交给 Decode Worker 继续生成。

机制通俗版：baseline（monolithic）同一进程完成 Prefill、首 Token 和 Decode；variant（disaggregated）跨进程 Handoff：Prefill Worker 导出逻辑 KV Payload，经同步 GPU→CPU→TCP→CPU→GPU 路径发布，Decode Worker 重建本地 Paged KV 后返回 ACK，确认所有权转移后才继续生成、首 Token 才可发给客户端（ACK-gated）；Payload 损坏或 Namespace 不匹配时 fallback，Decode 侧完整重算保证正确。正确性达标：三个 Worker PID 不同、首 Token Logits 摘要一致、输出与 monolithic 一致。但单卡串行路径下明确负优化：2048 Token 的 KV Payload 224 MiB，split TTFT 是 mono 的 5.49×（2378 vs 433 ms），其中 Publish 约 896 ms、Export 约 433 ms；换 1.7B 压力模型倍数仅缩小到 5.23×，"负优化是模型太小"不成立——单请求 split 永远比 mono 多一次 KV 交接。

架构上的位置：与 ch14 的区别：Handoff 是同一 Request ID + Attempt ID 的一次性所有权交接，不做前缀 Lookup、不留副本。系列至此指出真正收益所在：多 GPU P/D 并行吞吐与 KV-aware 调度（如 Mooncake [业界通识]）不在单卡实测范围。

业界对应：vLLM disaggregated prefill、DistServe、Mooncake 等多卡 P/D 分离方案 [业界通识]。

讲给客户的一句话：P/D 分离卖的是大规模下的资源配比和干扰隔离，不是单请求更快——单卡串行演示里它只会更慢。

ch18 · 固定Mini-batch（训练篇 03）

解决什么问题：ch17 前一条更新内是逐样本 Forward/Backward 累加梯度；把多个变长样本合成一个二维 Batch 一次算，能否保持训练目标又提高吞吐？

ch19 · 按长度分桶（训练篇 04）

ch20 · Sequence Packing（训练篇 05）

解决什么问题：分桶只能缩小长度差；只要一个样本独占一行，短样本仍以 Padding 填满自己那行。

ch23 · BF16混合精度（训练篇 08）

解决什么问题：FP32 的前向/反向由 GEMM 主导，没吃到 Tensor Core 低精度算力的红利。

机制通俗版：唯一变量是 Forward 与 Loss 放进 torch.autocast(bfloat16) 执行；主参数、梯度、AdamW 状态仍保持 FP32——这就是"混合"的含义。BF16 比 FP16 动态范围大，不需要 loss scale 的 GradScaler。效果预期：前向/反向显著缩短，激活显存减半但 FP32 主状态不动，峰值显存只部分下降；Loss 与梯度出现 BF16 舍入级分叉并随步数累积，用轨迹误差和 dtype 普查（forward hook 逐模块记录输出 dtype）量化。

架构上的位置：依赖 ch22 的稳定数据流水。边界：TF32 显式关闭并记录，避免混入第三个精度变量。

业界对应：autocast 混合精度；GradScaler 是 FP16 方案 [业界通识]。

讲给客户的一句话：混合精度省的是计算和激活，不省优化器状态；数值分叉是精度代价，要用轨迹误差盯住。

深挖入口：帖子「BF16混合精度」（10/5）

ch24 · 梯度累积（训练篇 09）

解决什么问题：单步能容纳的 Batch 受显存约束，想要大 Batch 的训练语义却没有大 Batch 的显存。

机制通俗版：一个 Optimizer Step 由 K 个 micro-batch（一次 Forward/Backward 的最小批）的梯度累加构成。正确性全在一个加权规则：微批 i 的损失按 token_sum_i / total_supervised 缩放，累积出的梯度才与一次大 Batch 的 token_mean 严格同口径——微批均值直接平均在监督 Token 数不均时会偏离联合目标，本章用反例显式验证这一点。代价是 K 次小 GEMM 的时间加总，收益是微批级显存上限带来的容量和更少 Padding。

架构上的位置：依赖 ch23。边界：FP32 下与大 Batch 只差求和顺序噪声；与 ch31 的 no_sync 是分布式版的天然搭档。

业界对应：gradient accumulation [业界通识]。

讲给客户的一句话：梯度累积用时间换显存容量，等价性的钥匙是每个微批按监督 Token 占比加权。

深挖入口：帖子「梯度累积」（10/10）

ch25 · Activation Checkpointing（训练篇 10）

解决什么问题：ch24 解决了大 Batch 准入，但 autograd 为 Backward 保留的中间激活仍是显存大头。

机制通俗版：不再保存全部激活，只保存每层（段）的输入，Backward 时先恢复该段的 RNG 状态（dropout 等随机算子依赖它），再 enable_grad 重算一次前向、然后正常反传。本章手写 RecomputeCheckpoint（autograd Function），与 torch.utils.checkpoint 的 use_reentrant=False 对照；dropout 正反例验证"不恢复 RNG 就逐位不一致"。粒度扫描（存 1/2/4/7/14/28 段）呈现权衡曲线：段越细越省显存、重算越多，代价约为 Backward 内多一次前向。

架构上的位置：依赖 ch24。边界：只存层输入的重算方案，不涉及按算子的选择性 checkpoint。

业界对应：gradient checkpointing，FSDP 内建 [业界通识]。

讲给客户的一句话：激活显存可以换成约一次额外前向的时间，段数粒度就是这之间的定价表。

深挖入口：帖子「Activation Checkpointing」（10/10）

ch26 · 训练版FlashAttention（训练篇 11）

解决什么问题：Eager Attention 会物化完整的 S² score/probability 矩阵，序列一长显存先爆。

机制通俗版：换成 scaled_dot_product_attention 的分块计算后端，不物化 S²。关键认知：FP32 下 flash 后端不可用（要求 BF16/FP16），可用的是 mem_efficient 后端；512 长度下端到端收益不大，机制价值在显存与序列边界。本章做后端普查（probe_backend_support）、数值差异对照和序列容量扫描，Attention 实现以注入点方式接入模型。

架构上的位置：依赖 ch25。边界：BF16 只出现在明确标注的跨精度对照臂，不与本机制混淆。

业界对应：FlashAttention 系列、PyTorch SDPA [业界通识]。

讲给客户的一句话：FlashAttention 的训练收益首先是"能不能装下长序列"，其次才是速度——而且后端可用性跟精度绑定。

深挖入口：帖子「训练版FlashAttention」（10/12）

ch27 · Fused AdamW（训练篇 12）

解决什么问题：AdamW 数学公式没变，但 0.6B 模型有约 310 个参数 Tensor，逐 Tensor 循环更新的 Kernel 发射次数成了 Optimizer 段的主要开销。

机制通俗版：三种 Kernel 组织对照：loop（逐 Tensor）、foreach（多 Tensor 打包发射）、fused（单 Kernel 完成整个更新）。用 profiler 统计一次 step 的 CUDA Kernel 数和设备时间，配合手写参照实现（含解耦权重衰减与偏置校正）验证三臂数值一致。核心方法论：算子不变，只改 Kernel 组织，开销差异就能被干净地归因。

架构上的位置：依赖 ch26 的稳定步体；clip_grad_norm_ 三臂同路径并单独计时作锚点。边界：不涉及优化器状态 dtype 与分片（那是 ZeRO-1 的事）。

业界对应：torch.optim.AdamW(fused=True)、apex fused optimizer [业界通识]。

讲给客户的一句话：小 Tensor 一多，优化器也能吃掉可观的步时间——省 Kernel 发射次数是零数学风险的提速。

深挖入口：帖子「Fused AdamW」（10/13）

ch28 · torch.compile（训练篇 13）

解决什么问题：Eager 执行下逐元素算子链有大量 Kernel 启动和内存读写开销，编译能融合，但代价要先算清。

机制通俗版：唯一变量是 Forward/Backward 交给 torch.compile（Inductor 默认配置），Loss、裁剪、优化器留在 Eager。三个必须分开记的账：稳态收益（Inductor 只能融合逐元素链，受 GEMM 份额限制）、首次编译成本（Break-even 摊销）、变长序列的重编译——每来一个新 shape 就触发一次编译，dynamic=True 用动态 shape 消化重编译但可能牺牲部分优化。用 dynamo 统计图数、重编译与 graph break。

架构上的位置：依赖 ch27。边界：变长训练的主要风险就是重编译风暴；编译优化器/裁剪、max-autotune 均不混入。

业界对应：torch.compile/Inductor [业界通识]。

讲给客户的一句话：编译的账是"首次编译成本 vs 稳态收益"，变长输入会不断触发重编译——生产里要先固定 shape 策略。

深挖入口：帖子「torch.compile」（10/13）

ch29 · DDP（训练篇 14）

解决什么问题：单卡机制已被压到边界，训练的第一个并行维度——数据并行——还没打开。

机制通俗版：DDP（Distributed Data Parallel，数据并行）让每张卡持一份完整模型、完整梯度和完整优化器状态，各处理全局批次的一个分片。等价性核心：本地损失按 supervised_local / supervised_global 缩放后，Backward 结束做一次 AllReduce SUM（把各卡梯度求和广播为一致）就与单卡大 Batch 的 token_mean 数学等价。AllReduce（全归约）的通信量公式为 2(W-1)/W·D。两卡走 PCIe 无 NVLink 时，每步约 2.4 GB 的 FP32 梯度 AllReduce 完全暴露在关键路径上。

架构上的位置：最低 2 卡。这是分布式篇章的起点，ch30–33 分别修它的通信时机与状态冗余。边界：Strong Scaling 效率显著低于 2 是预期内的。

业界对应：torch.nn.parallel.DistributedDataParallel、NCCL [业界通识]。

讲给客户的一句话：数据并行的语义等价性很好证明，但后置的全量梯度同步在慢互联上会全额暴露——通信时机是下一章的变量。

深挖入口：帖子「DDP」（10/14）

ch30 · DDP Gradient Bucket与通信计算重叠（训练篇 15）

解决什么问题：ch29 的 AllReduce 严格排在 Backward 结束后，整段通信时间都暴露；而反向传播是逐层完成的，早算完的层梯度本可以早发。

机制通俗版：把参数按反向就绪顺序（参数逆序）装成若干 Bucket（桶），用 hook 监听：某桶梯度一齐就绪就立刻 async_op=True 发起 AllReduce，与后续 Backward 计算重叠，尾部再 wait 把梯度以视图挂回参数。通信数据总量与 ch29 完全相同，变的只是启动时机。桶是双刃剑：桶太小则固定延迟占比上升反而变慢，桶太大退化为全暴露形态——用 1/16/128/1024 MiB 四档实测。

架构上的位置：最低 2 卡，依赖 ch29。边界：PCIe PHB 无 NVLink、通信计算共享带宽，收益可能有限。

业界对应：真实 DDP 的 bucket 机制、gradient_as_bucket_view [业界通识]。

讲给客户的一句话：把一次大同步拆成若干小桶提前发，通信就藏进了计算——桶大小决定藏得多少。

深挖入口：帖子未发，读仓库 README

ch31 · 梯度累积期间延迟同步（训练篇 16）

解决什么问题：ch30 重叠了单次 Backward 内的通信；当一步由 K 个微步累积时，每个微步都全量同步一次是纯浪费——中间结果反正不用于更新。

机制通俗版：前 K−1 个微步 no_sync（纯本地累积梯度），最后一个微步结束后统一 AllReduce SUM。损失按监督 Token 占比缩放的前提下，两种模式最终梯度数学等价，通信量降为 1/K。关键陷阱："每微步同步"的正确实现必须用独立累加器——对已归约的累积缓冲再次 AllReduce 会把先前微步的贡献放大 World Size 倍。

架构上的位置：最低 2 卡，依赖 ch24 的加权规则；本期刻意不用 Bucket（那是 ch30 的变量），AllReduce 仍是 Backward 后平铺 SUM。边界：K=2 时省一次全量 AllReduce。

业界对应：DDP 的 no_sync() 上下文 [业界通识]。

讲给客户的一句话：梯度累积和延迟同步是天然搭档——K 个微步只同步一次，通信量直接除以 K，数学一点不变。

深挖入口：帖子未发，读仓库 README

ch32 · ZeRO-1切分优化器状态（训练篇 17）

解决什么问题：DDP 每卡冗余持有完整模型、梯度、优化器状态；0.6B 在 12GB 上，AdamW 的 FP32 状态已是容量压力的大头。

机制通俗版：ZeRO-1（Zero Redundancy Optimizer 第一级，DeepSpeed 提出 [业界通识]）把 AdamW 动量（exp_avg/exp_avg_sq）在 Data Parallel Rank 间连续分片，参数和梯度仍是完整副本。AdamW 是逐元素更新，"本 Rank 的状态分片 × 本 Rank 的参数分片 × 本 Rank 的梯度分片"与全量 AdamW 逐位一致；更新只发生在参数分片所有者上，更新后用分块 AllGather（128MB 块缓冲）把新参数同步给其他 Rank。

架构上的位置：最低 2 卡，依赖 ch29 的梯度路径。省什么省多少：省的是优化器状态显存，W 卡时从每卡 14N 字节降到 14N/W，量级是"状态除以卡数"；代价是每步新增约 1× 参数字节的 AllGather，DDP 本来没有这笔通信。 边界：准入边界应比复制式 DDP 更晚 OOM。

业界对应：DeepSpeed ZeRO stage 1 [业界通识]。

讲给客户的一句话：先把最占显存的优化器状态按卡数切开，多付一笔参数同步的通信——这是显存换通信的第一步。

ch33 · ZeRO-2切分梯度（训练篇 18）

解决什么问题：ch32 切了状态，但每卡仍留完整梯度——Backward 结束那一刻它必须存在，之后只有本 Rank 的那一份会被用到。

机制通俗版：把通信算子从 AllReduce 换成 Reduce-Scatter（归约并分散：各卡得到求和结果的一个分片），完成后立即释放完整梯度，只留本 Rank 的分片。W=2 时 Reduce-Scatter 与 AllReduce 的每链接数据量同为 2(W-1)/W·D，通信时间应接近；梯度显存再降为 1/W。连带改造：梯度分片后 clip_grad_norm_ 不可用，全局范数须由"各 Rank 分片局部范数平方和 → 一次标量 AllReduce"合成再缩放本地分片。

架构上的位置：最低 2 卡，依赖 ch32（状态分片沿用 ZeRO-1，参数仍是完整副本，所以是 ZeRO-2 不是 ZeRO-3）。省什么省多少：在 ZeRO-1 基础上再省梯度显存，从每卡 2N 降到约 2N/W。 边界：本期逐参数发起 Reduce-Scatter，真实 ZeRO 用扁平桶，代价如实测量不掩盖。

业界对应：DeepSpeed ZeRO stage 2 [业界通识]。

讲给客户的一句话：AllReduce 换 Reduce-Scatter，通信几乎不涨、梯度显存再除以卡数——但梯度裁剪要自己重建全局范数。

深挖入口：帖子未发，读仓库 README

ch34 · ZeRO-3/FSDP（训练篇 19）

解决什么问题：状态和梯度都切了，参数仍整份常驻——它只在 Forward/Backward 里被读取，却在两个 Step 之间占着显存。

机制通俗版：ZeRO-3/FSDP（Fully Sharded Data Parallel，全分片数据并行）让参数也只以 Shard（分片）形式常驻，于是参数有了完整生命周期：分片常驻 → Forward 前 AllGather（聚合出全量）→ 计算 → Reshard（释放全量存储）→ Backward 前按需再 AllGather → 梯度 Reduce-Scatter → 分片 Optimizer Step。下一个 Forward 的 AllGather 本身就是参数刷新，ZeRO-1/2 那次 post-step AllGather 被取消。通信从"一步一次"搬进了 Forward/Backward 热路径。

架构上的位置：最低 2 卡，参考 4 卡与双节点 4+4。省什么省多少：每卡常驻模型状态从 ZeRO-2 的 2N+14N/W 降到 16N/W 字节（FP32 账本）——小 World Size 下参数冗余是最后一块大头。 代价：AllGather 进热路径，0.6B 上很可能 Step Time 变长，负优化如实保留。

业界对应：torch.distributed.fsdp FULL_SHARD、DeepSpeed ZeRO-3、Megatron-LM 均为此形态 [业界通识]。

讲给客户的一句话：参数也切开后显存账本最好看，但通信进了热路径——模型越大越划算，小模型是负优化。

深挖入口：帖子未发，读仓库 README

ch35 · MLP Tensor Parallel（训练篇 20）

解决什么问题：ZeRO/FSDP 切的是"层与层之间"的状态，单层内部的矩阵乘和权重还是每卡完整——模型宽到单层放不下时需要层内切分。

机制通俗版：Tensor Parallel 把 SwiGLU MLP 的权重切开：Gate/Up 沿输出维切（Column Parallel，输入复制输出分片），Down 沿输入维切（Row Parallel，输入分片、输出 AllReduce 求和）。梯度所有权分三类：分片权重梯度纯本地不通信；残差流输入梯度必须每层一次 backward AllReduce（Megatron 的 f 算子），漏掉会让"部分梯度"静默流进 Attention 路径；复制参数（Attention/LN/Embedding）梯度在 TP 组内天然一致，再 AllReduce 是放大 tp_size 倍的错误不是浪费。

架构上的位置：最低 2 卡，TP 组内数据复制，每 Rank 处理相同 Batch。边界：0.6B 单卡本可完整常驻，TP 是预期内的可能负优化——课程如实保留。

业界对应：Megatron-LM 的 Column/Row Parallel [业界通识]。

讲给客户的一句话：层内切分是"模型大到单层放不下"的工具，代价是每层两次强制同步的通信。

深挖入口：帖子未发，读仓库 README

ch36 · Attention Tensor Parallel（训练篇 21）

解决什么问题：MLP 切了，Attention 投影与 Head 仍每卡完整。

机制通俗版：把 Q/KV Head 按 TP Rank 整数切分。Qwen3-0.6B 是 GQA（分组查询注意力：32 个 Q Head 共享 8 个 KV Head，4:1），切分约束是每 Rank 拿到整数个完整 Head：TP=2 各得 16 Q/4 KV，TP=4 各得 8 Q/2 KV，局部 GQA 组数不变（4）；head_dim 永不切。RoPE 是 Head 内固定旋转，局部重放与全局逐位等价。陷阱：q_norm/k_norm 权重是复制的，但每个 Rank 只累积自己 Head 的梯度项——部分和各 Rank 不同，必须 hook 一次 backward AllReduce，否则副本从第一步起静默分叉。

架构上的位置：最低 2 卡，在 ch35 的 MLP TP 之上叠加。边界：0.6B 的 Attention 占比小，预期收益有限甚至为负。

业界对应：Megatron-LM 的 Attention TP、GQA 分组切分 [业界通识]。

讲给客户的一句话：按 Head 切 Attention 的前提是整除约束，GQA 下 Q 和 KV 头要成组切；归一化权重的部分梯度同步是最容易踩的坑。

ch37 · Vocab Parallel Embedding与分布式CE（训练篇 22）

解决什么问题：权重都切了，最后一个大头是词表：完整 Logits 是 TP 模型里最大的单项激活——batch 2 × seq 512 时约 622 MiB。

机制通俗版：Embedding/LM Head 沿词表维切（词表 151936，TP=2 每 Rank 75968 行，tie 共享同一分片 Parameter），配合不物化完整 Logits 的分布式 Cross Entropy：log-sum-exp 可按词表分块——全局 max 用 AllReduce MAX、全局 exp 和用 AllReduce SUM、目标 token 的 logit 按所属 Rank 用一次 SUM 取回；backward（softmax−onehot）只需要本 Rank 分片和三个全局标量，CE 本身 backward 零通信。注意 LM Head 输入梯度 dlogits_r @ W_r 是部分和，仍需一次 backward AllReduce（f 算子）。

讲给客户的一句话：词表切分省下的不是权重而是那 600 多 MiB 的 Logits 激活，方法是让 CE 只用分块归约的三个标量完成。

ch38 · Sequence Parallel（训练篇 23）

解决什么问题：TP 区域之间的激活仍各 Rank 重复保存：残差流与 LayerNorm 的激活是完整 [batch, seq, hidden]，与权重切不切无关。

机制通俗版：利用 RMSNorm 逐 Token 独立（均值只在 hidden 维）、残差逐元素的性质，把这些非 TP 区域的激活沿 Sequence 维切分：进入 TP 区域前 AllGather（g 算子）聚合出全序列，离开时 Reduce-Scatter（ḡ 算子）收回分片；Attention 是唯一序列耦合算子，仍在 TP 区域内跑全序列。代价是每层多一对 AllGather/Reduce-Scatter 边界通信；收益首先出现在长序列容量。连锁变化：LayerNorm 等复制参数的梯度从"天然一致"变成"部分和"，须 hook 同步。

架构上的位置：最低 2 卡，权重布局与 ch36 完全一致。边界：明确排除 Context Parallel/Ring Attention；Megatron 把 f/g 融合为一次 Reduce-Scatter 省一半反向字节，本章不做。

业界对应：Megatron-LM Sequence Parallel [业界通识]。

讲给客户的一句话：序列并行切的不是权重是激活——长序列下那才是显存大头，代价是每层一次往返的边界通信。

ch39 · GPipe Fill-Drain（训练篇 24）

解决什么问题：TP/SP 切的是"层内"；Pipeline Parallel 把 28 层按层跨卡切（PP=2 每 Stage 14 层）。但只切层不够——一个 micro-batch 从头走到尾时，任一时刻只有一张卡在算。

机制通俗版：GPipe 的 Fill-Drain 调度：先让所有 micro-batch（micro-batch 即流水线上流动的小批次）连续做完 Forward，再逆序做 Backward，流水填满后排空。Bubble（流水气泡，即 Stage 空转）上界为 (S-1)/(M+S-1)，micro 越多气泡越小；代价是每个 Stage 从 Fill 起要同时驻留 M 份激活图。Backward 靠 P2P 传"输出激活的输入梯度"驱动，与单卡语义一致。PP 特有的工程问题：tied Embedding/LM Head 分居首末 Stage，反向后要一对 P2P 交换两份部分梯度再更新。

架构上的位置：最低 2 卡，与 serial（逐个走完全流水）对照。边界：0.6B 太小、P2P 走 PCIe，端到端可能为负。

业界对应：GPipe 论文、Megatron-LM pipeline [业界通识]。

讲给客户的一句话：流水线用 micro-batch 排队填满各 Stage，气泡随批数下降，但显存要同时握住所有批的激活。

ch40 · 1F1B（训练篇 25）

解决什么问题：GPipe 的 Fill-Drain 要求每个 Stage 从头握到尾 M 份激活图，显存随 M 线性上涨。

机制通俗版：非交错 1F1B（一次 Forward 一次 Backward 交替）：Stage s 先做 min(S−1−s, M) 个 Warm-up Forward，进入 Steady State 后每轮先收后发地交替一次 Forward、一次 Backward，最后 Cool-down 排空 Backward。in-flight 激活（同时在手的激活图）从 M 份降到 min(S−s, M) 份——这是 1F1B 的主要价值，Bubble 上界仍服从同一填充-排空模型。细节：Steady 一轮必须"所有阻塞 recv 先于 send 挂出"，否则严格阻塞的传输（gloo）会互相等待成死锁；梯度按 micro 序累加，与 GPipe 逐位一致。

架构上的位置：最低 2 卡，参考 4 卡，与 ch39 共享 Stage 划分与 P2P 协议。边界：价值首先是峰值激活显存下降，不是吞吐大幅上升。

业界对应：PipeDream/Megatron-LM 的 1F1B schedule [业界通识]。

讲给客户的一句话：1F1B 不减少气泡，它把每个 Stage 手里攥的激活从 M 份压到与 Stage 位置相关的小数目——用调度换显存。

ch41 · Interleaved 1F1B（训练篇 26）

解决什么问题：1F1B 的流水级数 S 被物理卡数锁死，每卡只持一个连续 Stage，气泡压不下去。

机制通俗版：每张卡保存多个非连续的虚拟 Stage（模型块），total stage = P × vpp：虚拟 Stage s 放在物理 Rank s % P，28 层 / P=4 / vpp=2 时 8 个虚拟 Stage 依次 [4,4,4,4,3,3,3,3] 层，每卡合计仍是 7 层。调度上 micro 按 P 分组，组内按块扫 Forward、按块逆序扫 Backward；流水级数从 P 增到 2P，气泡缩短，但同一载荷要飞过 2P−1 条 Stage 边，P2P 次数约翻倍、Warm-up 数与 in-flight 显存上升。依赖在块边界闭合成环，阻塞 send 会死锁，必须异步 isend 投递 + 固定 FIFO 顺序。

架构上的位置：最低 2 卡，参考 4 卡；与每 Rank 一个连续 Stage 的 1F1B 对照，两臂每 Rank 层数相同。边界：micro 必须能被 P 整除；0.6B + PCIe 下端到端可能为负。

业界对应：Megatron-LM 的 interleaved schedule（virtual pipeline）[业界通识]。

讲给客户的一句话：虚拟 Stage 用"每卡多拿几段模型"把气泡压小，付的是通信次数翻倍和更长的等待链。

ch42 · 混合并行与双节点4+4（训练篇 27）

解决什么问题：DP、TP、PP 已各自验证，真实的训练集群需要三者同时启用——组合会不会破坏语义？跨节点该让哪个维度跨出去？

机制通俗版：不发明新原语，按 rank 分解公式建三维拓扑（TP 组节点内、PP 组节点内、DP 组跨节点），每节点一份完整 TP2×PP2 模型副本，训练主路径只有 DP 同步跨节点。数据只按 DP 切，TP 切权重不切数据，PP 按 micro 流过。三组单变量差分（只加 PP / 只加 DP）加一个综合配置保证受控性；任意两维布局之间的横向差异不写成单变量因果结论。易错点集中：dist.new_group 是全局集合操作必须全 Rank 同序创建；TP 组内再 AllReduce 复制参数梯度会放大 tp_size 倍；精确全局范数要防 (dp,pp) 单元被重复计数。

架构上的位置：最低 4 卡，完整参考为双节点 4+4。边界：跨节点通信口径以 NCCL Transport 记录解释，不做分段数字；边界激活在 TP 组内冗余传输 tp_size 倍是本布局的真实代价。

业界对应：Megatron-LM/DeepSpeed 的 3D 并行 [业界通识]。

讲给客户的一句话：三维并行的工程本质是一张 rank 分配表加三类组内通信——把 TP/PP 留在节点内、DP 跨节点，是对互联带宽的尊重。

ch43 · 分布式Checkpoint与恢复（训练篇 28）

解决什么问题：三维并行跑通了，但训练状态只存在于各 Rank 内存——崩溃即从头再来。checkpoint（检查点）要做的不只是存参数：进度、Sampler、调度器、每 Rank 的 RNG 都得进清单。

机制通俗版：唯一变量是保存方式：centralized（rank 0 聚合写单文件，其他 Rank 在 barrier 等待）对照 sharded（每 Rank 并行写自足分片 + rank 0 写 manifest 清单），torch.distributed.checkpoint 作官方对照。DDP 下各 Rank 状态逐位相同，所以"分片"是可互换的完整副本，4 卡保存 → 2 卡加载的重分片退化为"副本选择 + 校验"。恢复陷阱三连：LR Scheduler 的 state dict 不回写 optimizer 的 param_groups，必须用 _last_lr 手动回填；RNG 是每 Rank 状态，各取自己槽位；全部写盘走 *.tmp + os.replace 原子替换，被 Kill 的进程不会留下会被信任的半写文件。

架构上的位置：最低 2 卡，训练配置固定为 ch29 的 DDP 4 卡。边界：DDP 分片不省字节（sharded 体积约等于 centralized，收益只在并行 I/O 时间）；ZeRO/FSDP 的真字节级重分片属 ch34 形态。

业界对应：torch.distributed.checkpoint、各训练框架的 reshardable checkpoint [业界通识]。

讲给客户的一句话：checkpoint 的价值在"恢复后逐位接上"——学习率、随机数、进度任何一项漏存，续训就在静默漂移。

公式一：训练显存（什么时候 12GB 放不下）

FP32 混合精度训练的常驻状态 ≈ 每参数 16 字节：

组件 每参数字节 说明
参数（FP32） 4
梯度（FP32） 4
AdamW 动量 m（FP32） 4
AdamW 二阶矩 v（FP32） 4

0.6B 模型 ≈ 0.6e9 × 16B ≈ 9.6GB——所以原课程反复强调"0.6B 在 12GB 上已经足以形成容量压力"（ch32）。激活再加一截（batch × seq × hidden × 层数）。推论：7B 模型纯常驻状态 ≈ 112GB，单卡必不可能；这就是 ZeRO/切分存在的理由，不是炫技。

公式二：KV Cache 显存（什么时候上下文贵）

每章 README 给出（ch02）：

2 × layers × num_kv_heads × head_dim × sequence_length × batch × dtype_bytes

以 Qwen3-0.6B（28 层、8 KV head、head_dim 128、bf16 2B）为例，每 1024 Token 上下文约 115 MiB（ch02 实测口径：batch 1）。要点：

  • 随并发×上下文线性涨——batch 和 context 任一翻倍，KV 翻倍。长上下文服务的成本大头在 KV，不在权重。
  • GQA 的价值（ch36）：Q 32 头 / KV 8 头（4:1），KV 存储直接少 4 倍。
  • 这条公式是"KV Cache 命中与未命中的成本极限分析"那类帖子的底层（延伸阅读见原作者主页）。

公式三：Token 成本（自建 vs 调 API）

自建一枚 token 的成本 ≈（卡租费 + 电 + 运维）÷（卡的 token 吞吐 × 利用率）。售前现场要做的是量级判断，不是精确报价：利用率没打满时，自建的单价可以比 API 贵几倍；利用率打满的长稳负载，自建才可能占优。原作者《自建服务器卖token的详细计算过程》《10亿Token到底需要多少钱》等帖即按此思路展开（延伸阅读）。

Agent 场景的新变量：原作者 8/10 帖的结论性观察是 agent 场景产生数百倍于聊天场景的存储/内存消耗（多轮、工具结果、长上下文驻留）。给客户做容量规划时，先问清楚"请求是一次性还是 agent 循环式"，两者差几个数量级。

遇到瓶颈的开刀顺序（推理侧）

  1. 先削无效计算：KV Cache（ch02）→ 连续批处理（ch04）→ 长度分桶思想同样适用于推理的组批。
  2. 再管显存结构：Paged（ch05）+ Prefix 共享（ch08）——结构问题不解决，加卡只是延迟爆炸。
  3. 然后才外移：swap/重算（ch12）→ 异步分层（ch13）→ 外部 Cache（ch14）→ PD 分离（ch15）。
  4. 算子最后：FlashAttention（ch09）、CUDA Graph（ch10）——它们决定"每步多快"，前面的决定"每步算多少"。

常见售前误判：客户一抱怨慢就想"换大卡/加卡"，实际多数场景先死在调度与显存结构上。

Q1 · 客户：模型 7B，一张 80GB 卡跑训练够吗？ 机制版：常驻状态 ≈ 16 字节/参数（FP32 参数+梯度+AdamW 两状态）≈ 112GB，没算激活——单卡不可能。要么 ZeRO 切分到多卡（ch32–34），要么换 bf16 纯推理思路。追问点：客户说的"训练"是全参数 SFT 还是 LoRA/推理？三者差一个数量级。

Q2 · 客户：为什么上下文越长，每次回答越慢越贵？ 机制版：KV Cache 随上下文线性涨（公式二），Decode 每步都要读全量 KV；Prefill 一次算完整个 prompt（ch02 已知边界：Decode 并非与上下文长度无关的常数复杂度）。长上下文贵在 KV 存储+带宽，不在"思考更久"。

Q3 · 客户：都说 PagedAttention 省显存，到底省在哪？ 机制版：固定批/连续批时代 KV 按"全局最长请求"预留 dense 空间，短请求的空槽全是浪费；Paged 把逻辑序列映射到固定大小物理块，按需分配释放（ch05）。省的是"预留但不填"的部分。注意边界：教学实现无 fused kernel，生产引擎另有 kernel 优化 [业界通识]。

Q4 · 客户：多轮对话/固定 system prompt，重复算不浪费？ 机制版：前缀相同 → 前缀 KV 可共享（ch08）。只共享"填满且不可变"的块，所以不用 CoW；至少重算最后一个 prompt token（KV 不存首 token 的 logits）。

Q5 · 客户：GPU 都满了，新请求进来怎么办？ 机制版：准入控制（预算/排队，ch06）→ 不够时抢占：swap 保留断点 vs 重算放弃缓存（ch12，取舍是 PCIe 时间 vs 重算算力）→ 更大规模上外部分层缓存与 PD 分离（ch13–15）。

Q6 · 领导：为什么大厂要做 PD 分离？我们用得上吗？ 机制版：Prefill 是"一次吃长序列"，Decode 是"每步走一小步"，资源形状完全不同；同一 Worker 里互相干扰（ch15）。规模大、两类负载比例失衡才值得分离；小规模上了就是纯复杂度。

Q7 · 客户：agent 应用怎么容量规划？ 机制版：先问请求形态。agent 循环式（多轮工具调用、长驻上下文）的 KV/存储消耗是聊天式的百倍量级（原作者 8/10 帖结论性观察：数百倍内存消耗）——按"并发数×上下文长度×驻留时长"算，不按"日活"算。

Q8 · 客户：国产卡/ASIC 能不能替换 NVIDIA？ 机制版：看生态三件套——CUDA 生态的 kernel 覆盖（如 FlashAttention 类算子）、通信库（NCCL 对应物）、推理引擎适配。训练侧要求更高（并行通信栈）。延伸：原作者《廉价算力的希望——ASIC芯片》《国产算力，终于要上桌吃饭了》《求寒武纪显卡推理性能》等帖（延伸阅读）。

Q9 · 领导：训练中断了怎么办，之前白跑了？ 机制版：取决于 checkpoint 覆盖度。完整训练状态=参数+优化器状态+调度器状态（warm-up 进度等，ch43）；分片保存+manifest 恢复语义最完整。没保存调度器状态的"能续"大多是假续。

Q10 · 客户：为什么你们的方案不用更大的单卡就行？ 机制版：因为三座大山（参数/梯度/优化器状态）+ KV 都吃显存，大卡只是把爆炸点推迟；ZeRO/TP/PP 是结构性解法，不是权宜（表 B）。反过来也要会讲：能单卡/少卡解决的，不上分布式——通信是真实的税。

Q11 · 面试/答辩：KV Cache 为什么有时候开了更慢？ 机制版：小模型+短上下文时，省下的计算量小于 Cache 管理开销（拼接/调度/kernel 发起）（ch02 实测：16-token 负优化，1024-token 才 1.85×）。能答出"优化有适用边界"比背加速比高一个档次。

Q12 · 面试/答辩：梯度累积和加大 batch 是一回事吗？ 机制版：等价的前提是 loss 缩放口径正确（微批 i 按 token_sum_i/total_supervised 加权，ch24）。梯度数学等价、优化器视角一样；但 BatchNorm 类统计、性能特征不同。Qwen3 用 RMSNorm，无此坑，但回答要显式提边界。

Q13 · 面试/答辩：ZeRO-1/2/3 一句话区分？ 机制版：切优化器状态 → 再切梯度 → 连参数也切（ch32–34）。代价依次是参数 AllGather、Reduce-Scatter、双向 AllGather；通信越多，换来的是常驻显存 16N/W 量级递减。

Q14 · 面试/答辩：TP 和 PP 通信量谁大？ 机制版：TP 每层都要通信（前反向高频、要求高速互联）；PP 只在 stage 边界传激活（量小但引入 bubble）。所以 TP 卡要同机高带宽，PP 可以跨机（ch35–41 的架构含义）。
