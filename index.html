1. 模型眼里的文字：Token 与词表

你打"今天天气真好"，模型看不见汉字。它先查一本出厂自带的词表（vocab）：Qwen3 的词表有 151,936 条，每条是一个编号。"今天天气真好"会被 BPE 分词器切成若干 Token，每个 Token 变成一个编号，比如 [10432, 10021, ...]。BPE（Byte-level Byte Pair Encoding）的分词哲学一句话：高频组合合成一个 Token，生僻词切成小块——所以同一个词在不同上下文里切法一致，英文长词常被切成几块。

为什么模型不用汉字直接算？ 因为编号只是目录，真正参与计算的是每个编号对应的一行数字——Embedding。151,936 个编号 × 每行 1,024 个浮点数，就是一张 1.56 亿参数的查表（Qwen3-0.6B 词表部分 ≈151,936×1,024，hidden size 1,024 这个数来自 ch37 的 Logits 算术反推：151,936×1,024 个位置×4 字节 ≈622MiB，README 原话）。模型的"思考"，从头到尾都是向量运算。

2. Transformer 的一层：一次"看别人 + 想自己"

Qwen3-0.6B 有 28 层（ch39），每层是同一套结构的重复：

  • 注意力（Attention）：让每个 Token 回头"看"它前面的 Token，决定该把谁的信息拿进来多少。Qwen3-0.6B 每层有 32 个 Q 头、8 个 KV 头、每个头 128 维（ch36）。"头"可以理解为 32 个不同视角的观察员；KV 头只有 8 个——4 个观察员共用一份"被看的记录"，这个 4:1 就是 GQA，ch36 会算它的显存账。
  • FFN（前馈网络）：看完之后"想一想"，一个大矩阵变换，参数大头在这里。
  • 残差 + Norm：每小步都把输入原样加回来再归一化，防止网络越叠越深学不动。

3. 生成循环：模型怎么把一句话写完

现在把生成过程串起来（上图）：

  1. Prefill（读完）：你输入的 19 个 Token 一次性并行过完 28 层，得到每个位置的中间状态，并产出第一个新 Token。一次算完，所以快。
  2. Decode（逐字写）：之后每写一个字：把当前句子 → 28 层 → 得到 151,936 个 Logits（每个词表条目一个得分）→ 采样选出一个 → 接回句子末尾 → 再来一轮。
  3. 采样家族：greedy = 每轮直接取最高分（argmax，本课程全程用它，保证结果可复现）；温度 = 给分数"加热"后按概率抽，越热越随机；top-p = 只在累积概率前 p 的候选里抽。温度/top-p 属于采样策略，不改变模型本身 [业界通识]。
  4. 自回归 = 步骤 2 的循环：自己吃自己的产出，一个字接一个字，直到写出结束符。

把 Prefill 和 Decode 的时间线掰开看（这是后面 43 章最重要的底图）：

步骤 计算了几个位置 读了多少历史 特点
Prefill 19 个（并行） 无 算得多、只做一次、顺手建 KV Cache
Decode 第 1 步 1 个 读 19 份 K/V 算得少、读得多
Decode 第 2 步 1 个 读 20 份 K/V 历史越来越长，读的越来越多

"算得少、读得多"是 Decode 的本质：每写一个字，计算量是 1 个位置过 28 层，但要把它前面所有位置的 K/V 从显存搬进计算单元——瓶颈逐渐从算力（FLOPS）转移到显存带宽（GB/s）。判断一个推理方案好坏，本质上是看它怎么处理这个"读"字：少读（ch08 前缀复用）、快读（ch09 好的 Kernel）、边算边读（ch13 异步）、读了存着别丢（ch05 分页、ch12 换出）、换个地方读（ch14 外部缓存、ch15 分离）。

4. 显存四座山与精度阶梯

推理时一张卡的显存里住着四样东西：

山 是什么 大小怎么定
权重 6 亿个参数的数值本体 参数量 × 每参数字节数
KV Cache 每层每头的历史 K/V，给 Decode 复用 ch02 公式：2×层数×KV头数×头维×序列长×并发×每字节数
激活 计算过程中的临时矩阵（如 Logits） 随 batch×上下文暴涨，ch37 有 622MiB 实例
框架开销 CUDA 上下文、allocator 碎片等 数百 MiB 量级 [业界通识]

精度阶梯（每参数占多少字节）：

精度 字节/参数 白话
FP32 4 全精度，训练的"账本"精度
BF16 2 尾数短但指数位和 FP32 一样大——不拍大数，训练界标配
FP8 1 推理新贵，显存减半再减半 [业界通识]
INT8/INT4 1 / 0.5 量化路线（AWQ/GPTQ 等），显存最省、精度有损 [业界通识]

一句话记住：权重显存 = 参数量 × 每参数字节数。0.6B 用 BF16 就是 1.2GB；这个乘法会贯穿后面所有选型算例。

5. 为什么要学"手写"那一章

后面 43 章的每个优化名词（KV Cache、批处理、分页、调度、FlashAttention、DDP、ZeRO、TP/PP……）都是给上文某个环节"动手术"：KV Cache 治 Decode 重算（ch02），批处理治 GPU 吃不饱（ch03–04），分页治 KV 显存碎片（ch05），调度治谁先谁后（ch06–07），精度治权重显存（ch23），并行治"一张卡根本放不下"（ch29–43）。不认识手术对象，方案就是空话——这就是 ch01 手写的意义。

掌握目标能答出 Token/Embedding/Logits/采样四件事的关系；能算出任意模型 BF16 权重显存（参数量×2 字节）；能区分 Prefill 和 Decode 的计算形状。

ch01 · 手写 Qwen3 推理

先回答最基本的问题：语言模型到底在做什么？

你在对话框打"你好"，模型一个字一个字往外蹦。它不是想好了再说话——它在玩一个高级接龙：每次只猜"下一个 Token 是什么"，猜完接到句子末尾，再猜下一个。"猜下一个"这个动作，就是大模型推理的全部。本章把这个接龙循环徒手拆开：不用 vLLM，不用 Transformers，只用 Python 和 PyTorch，从权重文件一路写到第一个字蹦出来，为全系列 43 章建立 baseline。

ch02 · KV Cache

先看一个日常场景：你和模型聊到第十轮，它每蹦出一个字，都要把你前面说过的一百个字从头读一遍再写一个字。这就是 ch01 手写推理的现状——历史 Token 的中间结果用完即扔，每一步 Decode 都对完整上下文重跑所有 28 层。KV Cache 是对这个浪费最直接的回应：算过一次的东西，存下来别扔。要理解它存的是什么，得先把"一个字怎么被处理"拆到注意力计算的每一步。

名词卡
名词 白话解释
Q（Query） 当前 Token 发出的"检索词"：我在找什么样的信息
K（Key） 每个 Token 的"标签"：我能被什么样的检索词匹配到
V（Value） 每个 Token 的"内容"：一旦匹配上，取走的就是它
注意力三步 出题（算 Q）→ 配对打分（Q 和所有 K 点积+softmax）→ 取内容（按权重加权 V）
KV Cache 历史每层的 K/V 存下来复用，"配对打分"和"取内容"照常做，K/V 不再重算
Prefill 一次性读完整个 Prompt 的一次前向计算，产出首 Token 并建 Cache
Decode 之后逐 Token 生成：每步只算 1 个新位置，但要读全部历史 K/V
RoPE 位置编码，给 Token 标"位置编号"；位置从 Cache 长度续算，不从头数
GQA 多个查询头共用一组 KV 头（Qwen3 是 4:1），KV 存储按 KV 头数算

先讲清注意力在算什么（后面十几章全靠这个底子）。一层注意力对当前 Token 做三步：第一步出题——用当前 Token 的向量算出一个 Query（"我在找什么"的向量）；第二步配对打分——Query 和历史里每个 Token 的 Key 做点积，得到"该多看谁"的分数，softmax 归一成权重；第三步取内容——按权重把历史各 Token 的 Value 加权求和，得到当前 Token 在这一层的输出。所以 K 和 V 不是玄学：K 是"我被怎么找到"的标签，V 是"找到我之后取走的内容"——像图书馆检索：书脊标签是 K，书里的内容是 V，你脑中的检索词是 Q。

为什么没有 Cache 时每一步都贵：没有 Cache 的写法里，写第 21 个 Token 时，前 20 个 Token 的 Q/K/V 和全部中间结果都被重新计算（28 层 × 20 个位置）。但注意力的数学里藏着一个被浪费掉的免费午餐：历史 Token 的 K/V 只依赖"过去"，不随"现在在写谁"变化——写第 20 个字时算出的第 3 个字的 K/V，和写第 21 个字时算出的第 3 个字的 K/V，一模一样。RoPE 位置编号也是固定的。重复计算它们 = 纯浪费。

variant 的做法：Prefill（第一次读 19 个 Token）时顺手把每层每头的历史 K/V 存进 Cache；此后每步 Decode 只算新 Token 自己的 Q/K/V（一个位置），K/V 追加进 Cache，Q 拿去和 Cache 里全部 K 打分、按权重取 V 加权。历史不再重算，只有新 Token 走 28 层。Cache 的形状是每层一对普通 Tensor：[batch, num_kv_heads, seq_len, head_dim]，教学实现用 torch.cat 逐步增长；Key 在 QK Norm 与 RoPE 之后写入。float32 对照下两条路径逐 Token 一致——Cache 没改错东西。

两阶段时间线（看上图下半）：第 1 步 Prefill，19 个位置并行过 28 层，建 Cache、出首 Token——算得多但一次做完；第 2 步起是 Decode，每步只算 1 个新位置，但要读前面所有位置的 K/V——"算得少、读得多"。这解释了 ch01 那个怪现象的另一半：读 19 个字只要 34.43ms（并行），写一个字也要 33.40ms（串行读全部历史）。也埋下后面所有章节的伏笔：Decode 的瓶颈从"算力"变成了"把 KV 从显存搬进计算单元的带宽"。

算一算Cache 数据量 = 2 × layers × num_kv_heads × head_dim × seq_len × batch × dtype_bytes。Qwen3-0.6B：28 层 × 8 个 KV 头 × 128 头维 × 2 字节（bf16）× 2（K 和 V）≈ 0.11 MB/Token——1024 Token Prompt 生成到 1055 长度时实测 Cache 恰好 115.39 MiB，与公式吻合。

数字（3080 Ti、bf16、batch size 1、32 输出 Token、README 实测）：16 Token 短 Prompt 上 KV Cache 反而负优化——端到端 1191.07 vs 1011.79 ms，因为 Qwen3-0.6B 单步算量极小，Python 调度、Kernel Launch 和 torch.cat 再分配把省下的计算吃掉了；到 1024 Token 才有约 1.85× 加速，Decode 均值 60.43→32.64 ms，端到端 1930.00→1067.75 ms。收益随上下文变长才从负转正，这条曲线本身就是本章最重要的实测结论。

重点KV Cache 只优化 Decode、不优化 Prefill；收益随上下文变长才显现——短上下文上管理开销可能反超节省的计算。
边界与常见误区KV Cache 不减少 Prefill 对完整 Prompt 的计算；Decode 时 Query 仍要读全部历史 K/V，所以 Decode 并非与上下文长度无关的常数复杂度；torch.cat 动态增长的教学实现也谈不上高效。[易错] "开了 KV Cache 一定更快"——16 Token 组实测更慢，结论必须按负载给出。
产品对应KV Cache 是所有推理引擎的核心组件；vLLM 等引擎的 Cache 预分配与分页管理（ch05 起）远优于本期的动态 torch.cat [业界通识]。
方案视角先问客户的判据是业务 Prompt 的典型长度：上下文越长，KV Cache 及其显存管理越关键，长文档/RAG 场景几乎必谈；全是几十 Token 的短对话时，重点反而落在调度与其他开销上。看哪个指标——Prompt 长度分布，而不是模型大小。
讲给客户的一句话KV Cache 让"每写一个字重读全部历史"变成"只算新字"，收益随上下文变长才显现，短 Prompt 小模型上管理开销可能吃掉全部节省。

ch03 · Static Batching

ch02 修好了"单请求"的浪费，但服务台不可能只服务一个人。单请求跑模型时 GPU 利用率很低——每次 Decode 只算 1 个位置的小矩阵，算力大部分在空转。最朴素的"凑大批"是把多个请求拼进同一个 Batch、共享一次模型前向：GPU 一次算 16 个人的活。但请求长短不齐时，省下来的算力会从两条缝里漏回去：补位的无效 Token 也占计算，先完成的槽位只能干等。这两条缝，正是本章要把机制拆开看的地方。

名词卡
名词 白话解释
Batch 一组请求拼在一起，共享一次模型前向执行
Padding 把短序列补到统一长度，凑成矩形 Tensor
左 Padding 把补位放左边，让每个请求的有效 Token 右对齐
Attention Mask 标出哪些位置是真 Token、哪些是补位，补位不进注意力
槽位 Batch 中的一个固定名额，配一块独立 KV Cache
makespan 一批任务从开始到最后一个完成的全部耗时
Position IDs 每个 Token 的位置编号，按各自有效长度增长

这一章怎么工作（拆到计算步骤级）：baseline 是多个带 KV Cache 的请求逐个执行——每个请求各自 Prefill、各自 Decode，GPU 每次只吃一个小矩阵。variant 把 N 个异长 Prompt 装进一个成员固定的 Batch，分三步走。第一步：左 Padding——长度 [16,32,64,128] 的 Prompt 全部补到 128，凑成 [batch, 128] 矩形 input_ids，同时配两张辅助表：attention_mask（标记哪些列是真 Token）和 position_ids（每个请求的有效 Token 仍从逻辑位置 0 起 RoPE 编号，不用物理列号）。第二步：一次 Batched Prefill——矩形全体并行过 28 层，注意力的"配对打分"里补位列被 Mask 挡住不进打分，但矩阵形状仍按 128 列执行，无效列的计算一个不少；每层的 K/V 按槽位写入 [batch, num_kv_heads, cache_length, head_dim]。第三步：按槽位同步 Batched Decode——每轮 1 次前向同时给 4 个槽位各算 1 个新位置、各读各的历史 K/V；输出预算 [8,16,32,64] 的槽位分别在第 8、16、32、64 轮写完，之后它们的列被 Mask 成"哑槽"，矩形 Tensor 照跑——但 Batch 一旦开始不进新请求，空槽不复用。float32 对照下换同伴、换排列的 Logits 误差为 0，无请求串扰。

回到两阶段时间线：Batched Prefill 还是"算得多、只做一次"（N 个人的 Prompt 并行读完），Batched Decode 还是"算得少、读得多"（每槽 1 个新位置读各自历史）——批处理改变的是同时算几个人，没有改变每个人"算多少、读多少"的形状。这就是为什么 Padding 的账只出现在 Prefill（矩形按最长 Prompt），空转的账只出现在 Decode（矩形按最长输出轮数）。

算一算输出预算 [8,16,32,64] 的四人批次必须跑到第 64 轮：有效槽位利用率 = (8+16+32+64)/(4×64) = 46.88%——一半以上的执行轮次在做无效计算。同款账也适用于 Padding：长度 [16,32,64,128] 补到 128，有效率同为 (16+32+64+128)/(4×128) = 46.88%。

数字（3080 Ti、bf16、README 实测）：收益侧，Batch Size 16 相对串行 makespan 约 13.98× 加速，Batched Cache 随 Batch Size 线性增长。浪费侧，混合长度组 [16,32,64,128] 的 Prefill 有效吞吐 6880.90 token/s，几乎只有整齐组 14641.75 token/s 的一半，而 Prefill 延迟和峰值显存几乎不变——浪费来自无效 Token 也占满计算，不是"短 Prompt 拖慢 Batch"。容量侧还有个反直觉数字：Batch 192 吞吐 2981.83 token/s 高于 196 的 2931.97，且 197 起在 Prefill LM Head 处 OOM（该处需单次分配约 7.14 GiB 的 Logits Tensor）——最大可跑 Batch 不是吞吐最优 Batch。

重点固定 Batch 的吞吐收益来自并行度，而 Padding 浪费与空转槽位会把它抵消——拼批的关键是请求长度整齐，不是越大越好。
边界与常见误区bfloat16 下 Batch Shape 改变矩阵 Kernel 的归约顺序，候选 Logits 接近时可能分叉（Batch Size 2 时第 4 步分叉、Top-1 一致率 37.5%）——这是数值现象，不是"Batch 降低准确率"；离线结果不含排队与网络，不代表在线 SLO。[易错] 把 46.88% 的浪费读成"短 Prompt 拖慢别人"——真实原因是矩形 Tensor 按最长长度执行。
产品对应离线批量任务（评测打分、数据标注）仍用固定 Batch 思路 [业界通识]；在线服务已被 Continuous Batching（ch04）取代。
方案视角面向离线批量客户时先问"请求长度分布是否整齐？"——看哪个指标：请求长度分布的离散程度。整齐的可用静态拼批吃满并行度，不齐的收益先打个对折；在线交互业务不看这章，直接看下一章的调度。
讲给客户的一句话拼批能提吞吐，但请求长短不齐时 Padding 和空槽可能浪费一半算力——批不是越大越好。
掌握目标能算出给定长度分布下 Batch 的 Padding 有效率；能区分"批越大越好"与"吞吐最优 Batch"两个命题。

ch04 · Continuous Batching

固定 Batch 留下的最大裂缝是"先完成的不能退场"：在线场景里请求随时到达、输出长度随机，ch03 的批次却要等最长的那个结束才换人——槽位常年空着，排队的人干瞪眼。Continuous Batching 把换人粒度从"整批"细化到"每一次模型迭代"：谁写完最后一个字，谁的名额立刻让给等待队列里的人。

名词卡
名词 白话解释
迭代 模型前向的一次执行，Decode 每步就是一次迭代
Continuous Batching 每次迭代前回收完成槽位、补入新请求的动态拼批
状态机 每个请求的流转记录：waiting→running→finished
FCFS 先到先服务：按到达顺序填空槽，最简单的调度规则
TTFT 首 Token 延迟：从请求到达到第一个字吐出
ITL Token 间隔：Decode 阶段相邻两个字的间隔时间
dense Cache 按最大并发和物理长度预留的整块矩形 KV Cache

这一章怎么工作（拆到计算步骤级）：为每个请求维护 waiting → running → finished 状态机，然后每次模型迭代前执行固定三拍。第一拍，回收：扫描 running 集合，把写完最后一个 Token 的请求标记 finished，清空其槽位的有效 Mask，腾出空位。第二拍，填补：按 FCFS 从 waiting 队列按到达顺序把新请求填进空槽，空位与已到达请求同时存在时本期固定 Prefill 优先。第三拍，执行：本迭代有新请求就对它们做一次 Batched Prefill（读各自整个 Prompt、建 Cache、产首 Token）；没有新请求就对剩余槽位做一轮 Batched Decode（每槽算 1 个新位置、读各自全部历史 K/V）。baseline 与 variant 用相同的 FCFS 顺序、相同的最大运行请求数，唯一变量是完成名额能否在迭代边界被复用。正确性靠对照验证：float32 下两条 Batch 路径与单请求独立执行逐 Token 一致，换槽轨迹 [0,1] → [2] → [3] 没有串扰。KV Cache 本期仍是 dense 固定容量 [max_running_requests, num_kv_heads, physical_length, head_dim]，新请求更长时全批左扩容搬移——这个浪费留给 ch05。

回到两阶段时间线：批处理形状没变——Prefill 仍是"算得多、只做一次"（一次读完新请求的全部 Prompt），Decode 仍是"算得少、读得多"（每槽 1 个新位置读全部历史）。变的是时间线上 Prefill 出现的时机：ch03 里 Prefill 只在整批开头出现一次；ch04 里每当空槽遇到新请求，一轮完整 Prefill 就插进 Decode 流。这正是延迟恶化的根源——512 Token 的 Prefill 是"19 个位置的算术放大 27 倍"的一次大算，会把它撞上的那几轮 Decode 全部堵住。

算一算固定到达轨迹（每 150 ms 一请求、Prompt 128、输出 32）里，第 5 个请求的 TTFT 差距可以直接推出来。固定批次：前 4 人占满 4 个槽位，须整批跑完（约 1 次 Prefill + 32 轮 Decode ≈ 34 + 32×34 ≈ 1500 ms 量级）才有空槽——实测 TTFT p95 1511.07 ms 与这个推算吻合。Continuous：有人第 8 轮写完就腾槽，新请求在第 9 轮左右做完 Prefill 出首 Token——实测 TTFT p95 205.39 ms，差出约 7 倍的就是"迭代边界换人"这一件事。

数字（3080 Ti、bf16、逻辑时间线、README 实测）：异长输出场景 makespan 加速 1.169×、吞吐 +16.8%、执行槽位有效率 62.50%→74.07%；等长输出负对照里没有可提前复用的槽位，两条路径只差约 0.4%——机制成立的前提是负载不整齐。固定到达轨迹下收益更明显：makespan 加速 1.486×、TTFT p95 1511→205 ms，但 ITL p95 36.50→71.48 ms：新请求的完整 Prefill 会阻塞已有请求的 Decode，干扰实验里 512 Token Prompt 中途到达使 ITL 最大值 35.07→72.71 ms，而 p95 只有 34.89 ms 会掩盖这个局部尖峰。

重点Continuous Batching 在迭代级复用完成槽位，但新请求的完整 Prefill 会卡住已有请求的 Decode——这个矛盾要等 Chunked Prefill 才能解决。
边界与常见误区本期的"Prefill 优先 + FCFS"是为了得到唯一、可复现的执行路径而固定的策略，不代表生产调度器的最优选择；CPU 调度与 Cache 管理仍有约 2.3% 开销；dense Cache 扩容须搬移。[易错] 把 ITL p95 从 36.50 恶化到 71.48 ms 读成机制失效——这是 Prefill 阻塞其他请求的确认代价，不是槽位复用本身的错误。
产品对应vLLM/SGLang 等在线引擎的标准调度方式，思路源自 Orca 论文的 iteration-level scheduling [业界通识]。
方案视角评估在线引擎时这是必选能力，没有它在线并发吞吐无从谈起；现场先问"TTFT p95 和 ITL p95 是否同时可接受"——只看一项会被 Prefill 干扰欺骗，p95 也会掩盖局部尖峰，要连最大值一起看。
讲给客户的一句话Continuous Batching 让新请求见缝插针补进批次，新请求更少等，但 Prefill 与 Decode 会互相干扰，延迟分位要一起看。
掌握目标能画出请求在 waiting→running→finished 状态机中的槽位复用流程，并说出每次迭代前的固定三拍；能判断什么负载下 Continuous Batching 无收益。

ch05 · Paged KV Cache

ch04 的 KV Cache 还是 dense 整块预留：物理宽度等于这批请求里出现过的最长 Cache。于是一个 4096 Token 的长请求会让所有槽位——哪怕只装 128 Token——都在 4096 级别上跑 masked Attention；长请求走后，宽度也不缩回来。长度不均时显存浪费严重、并发上不去，而"上万人同时用"恰恰意味着长度分布最杂乱。Paged KV Cache 借用操作系统的老办法：分页。

名词卡
名词 白话解释
Paged KV Cache 把 KV 显存切成固定小块，按需分配给各请求
Block 固定大小的物理 KV 块，一次装 block_size 个 Token
Block Pool 预分配好的物理块大池子，所有请求共用
Block Table 每请求的逻辑页表：逻辑块号→物理块号
尾块 请求最后一个未装满的块，碎片只出现在这里
gather 按页表把散落的物理块收起来读的操作

这一章怎么工作（拆到计算步骤级）：baseline 沿用 dense 槽位——物理长度等于运行集合的历史最大 Cache 长度，长请求加入时所有层所有槽位一起左扩容搬移，完成后只清 Mask、宽度不缩。variant 借鉴操作系统的虚拟内存分页：显存切成固定大小的物理 Block，一个 Block 携带全部层 K/V（[num_layers, 2, kv_heads, block_size, head_dim]），所有层共用同一张映射表；每个请求只存一张 Block Table 和逻辑长度——逻辑连续不要求物理连续。执行流程固定四步。第一步，申请：Prefill 时按 ceil(prompt_len / block_size) 从 Block Pool 取空闲块，例如 258 Token 的 Prompt 在 block_size 16 下取 17 块；Prompt 的 K/V 逐层写入对应块。第二步，写尾块：每步 Decode 的新 Token K/V 追加进该请求最后一个未满的块（尾块）。第三步，满了再取：尾块装满时才从池里再取一个空闲块挂到 Block Table 末尾，平时零开销。第四步，gather 读：做注意力的"配对打分 + 取内容"时，按逻辑长度分组，经 Block Table 把散落的物理块收起来按序读——尾块超出逻辑长度的槽位被 Mask。请求完成后物理块归还空闲堆，给后续请求复用，全程不动其他请求已写入的 K/V。float32 对照下 dense 与 paged 逐请求 Token 完全一致，换槽与 Block 复用轨迹也没有串扰。

回到两阶段时间线：每槽"算多少、读多少"的形状没变——Prefill 一次读完整 Prompt，Decode 每步算 1 个新位置、读全部历史。分页改变的是"读到哪里去"：dense 读的是一整条连续预留的槽（短请求也在按最长宽度跑 masked Attention），paged 只读 Block Table 指到的有效块——同样读 20 份 K/V，不再附带 4000 份无效槽位的搬运。这是把 basics 里"读了存着别丢"的那条伏笔落了地。

算一算dense 槽位显存 = 最长请求 × 槽位数 × 0.11 MB/Token（ch02 公式）。10 个槽位、最长 4096：4096×10×0.11 ≈ 4.5 MB/层×全部层的预留，哪怕 9 个请求只有 128 Token。paged：每个请求按 ceil(实际长度/16) 申请，128 Token 只占 8 块，碎片被限制在每个请求自己的尾块里（不足 16 Token）——10 个 128 Token 请求按需只付约 128×10 的量，加上尾块零头。

数字（3080 Ti、bf16、README 实测）：硅上的双面结果——长度不均（3072 Token 长请求）时 KV 读取减少 94.1%、Cache Pool 减少 82.6%，但同并发吞吐反而降 36–45%：PyTorch reference 的 Block gather、分组 Attention 和额外 Kernel Launch 吃掉了计算节省。真正的收益在容量：12GB 卡上固定负载下 dense 最大成功并发 8（12 起 OOM），paged 跑到并发 16、吞吐 157.80 token/s 还略高于 dense 最优约 0.9%，峰值显存低约 43.0%。

重点分页把显存占用从"按最长请求预留"变成"按需分配"——收益主要在并发容量；同并发下的单步速度要靠专用 Kernel 而非分页本身。
边界与常见误区减少 K/V 访问不等于端到端更快——Block gather 的 Kernel 效率同样决定成败；Block Pool 按已知上界一次预分配，没有动态准入。[易错] "上了分页吞吐就涨"——本期同并发吞吐是负的，价值是容量换吞吐：同一张卡多接一倍并发。
产品对应vLLM 的 PagedAttention 是此机制的代表实现；vLLM/SGLang 的专用 CUDA/Triton Kernel 直接读 Block Table，没有本期 PyTorch reference 的 gather 开销 [业界通识]。
方案视角先问客户两个问题："Prompt 长度分布有多离散？显存余量有多紧？"——看哪个指标：长度分布的离散程度加显存余量。长度越离散、显存越紧张，分页收益越明显；然后算容量账——同一张卡能多接多少并发，能不能少买一张卡。
讲给客户的一句话分页把 KV 显存从"按最长请求预留"变成"按需分配"，同一张卡能多接一倍请求，代价是单步吞吐依赖引擎 Kernel 的成熟度。
掌握目标能画出逻辑 Token 位置经 Block Table 到物理 Block 的映射，并按序说出"申请→写尾块→满了再取→gather 读"四步；能判断"减少 KV 读取"与"端到端变快"何时不是一回事。

ch06 · 迭代级推理请求调度器

想想你正在和一个模型长对话，聊到一半页面上突然一个字都不蹦了，几秒后才恢复——不是模型算不动，而是调度器把 GPU 交给了刚涌进来的新请求：它连续做了好几轮 Prefill，把已在生成中的会话晾在一边。ch05 解决了显存怎么分，但"每一轮迭代该干什么"仍无约束：调度器默认 Prefill 优先，新请求的突发可以无限挤压老请求。本章给调度器装上"算力预算"。

名词卡
名词 白话解释
迭代级调度 每次模型前向就是一个调度机会：每轮都重新决定这轮做 Prefill 还是 Decode
FCFS 先来先服务：按到达顺序排队处理，不插队
Token Budget 每轮 Prefill 允许消耗的 Token 上限，像每轮的"饭量额度"
padded cost 预算按批补齐后的矩形宽度扣账，补的空白 Token 也算钱
软预算 单条 Prompt 超预算不拆分，允许它整条执行、排队不清空
ITL Token 间隔时间：正在生成的用户两次看到新字之间的等待
TTFT 首 Token 时间：请求从提交到看到第一个字的延迟
Decode 保护 强制规则：有请求在生成时，两次 Prefill 轮之间至少插一次 Decode 轮

为什么需要：baseline 是纯 FCFS + Prefill 优先，有空闲槽位就一次 Prefill 所有可加入的请求。突发 12 条长短混合 Prompt 时，调度器可以连续多轮做 Prefill，已有 Decode 停摆数百毫秒到秒级。调度优化的价值不是"多收请求"，而是限制每轮 Prefill 强度、强制插入 Decode 轮保护已开始的会话——界面上的"系统卡了"多半缺的就是这个。

怎么工作（拆到计算步骤级）：引擎维护 waiting / running / finished 三个队列，每轮模型前向前调度器先走三拍：第一拍，算预算——variant（budgeted）按 prefill_cost = batch_size × max(prompt_length_in_batch) 扣 Token Budget（Prefill 用左 Padding，预算按补齐后的矩形算，Decode 轮的成本就是 running_request_count）；第二拍，FCFS 准入——按到达顺序把 waiting 队头逐个装进本轮 Prefill，预算不够装下一个时立即停止，且不跳过队头去找更短的 Prompt（跳过会饿死队头）；第三拍，Decode 保护——已有请求在 Decode 时，两个 Prefill 轮之间至少执行一次 Decode 轮。每轮调度只产出一个 SchedulerOutput（阶段、请求、Token 数、是否超预算），执行器照它跑一次 Batched Prefill 或一次 Decode。注意"软"字的含义：本期没有 Chunked Prefill，队头单条 Prompt 超预算时不拆分、整条放行——否则 FCFS 队头被永久跳过。自检里最能说明机制成立：baseline 最大连续 Prefill 轮数为 2–3，budgeted 恒为 1（README「代码使用方法·CPU 快速自检」）。

两阶段时间线：用"算几个位置 × 读多少历史"的语言看每一轮——Prefill 轮：批内每条请求并行算它的全部 Prompt 位置（矩形补齐后最长那条决定成本）、顺手建 KV Cache；Decode 轮：每条运行中请求只算 1 个新位置，但要读各自全部历史的 K/V——"算得少、读得多"。两种轮混在同一张时间线上互相挤占，就是调度器要管的核心矛盾。

数字（3080 Ti、Qwen3-0.6B、突发 12 条长短混合，README「Prefill burst 与 Token Budget 实验」实测）：budget 2048 相对 baseline 吞吐 63.01→71.26 token/s（+13.1%），既有请求最大 ITL 906.84→376.79 ms（降 58.5%），突发请求 TTFT p95 降 15.8%，Prefill padded token 减少 53.0%。但 ITL p95 从 98.52 升到 207.37 ms——baseline 把 Prefill 集中成少数次长停顿，budgeted 拆成多次中等停顿：最大值改善、p95 反而恶化，这不能写成"延迟全面改善"。另一头，budget 256 过紧，出现 6 次单请求超预算加更多轮次开销，吞吐反而 -6.8%。

算一算同样 3000 ms 的 Prefill 总量：baseline 集中 3 次各 1000 ms 的停顿（最大 1000），budgeted 拆成 10 次各 300 ms（最大 300）——"最坏一次"改善，"经常等多久"变差。max 看最坏一次，p95 看频繁的中停顿，两个指标可以反向变化。
重点调度器的核心不是多收请求，而是用 Token Budget 限制每轮 Prefill 强度并强制插入 Decode 轮。
边界与常见误区预算按 padded 而非有效 Token 计，补齐的空白也耗预算；且无显存准入、抢占、优先级与 Prefill/Decode 分离，budget 2048 只是本次扫描的最佳档位，不是通用最优。[易错] "预算调小总是更公平"——过紧的预算引发超预算执行和额外轮次开销，吞吐反向下降（256 档实测 -6.8%）。
产品对应vLLM/SGLang 的迭代级调度都内置 Decode 保护这类机制；调度器里的 max_num_batched_tokens 参数就是 Token Budget 的产品形态。
方案视角有已开始会话被新请求打断的在线交互业务都需要它；纯批量离线任务无所谓。评估时先问两件事："单轮 Prefill 最长多久？""已有会话的最长卡顿（ITL max）是多少？"并看 Token Budget 默认值是否按你们的负载扫过档。
讲给客户的一句话调度器的核心指标是"已开始的对话不被新请求卡住"——要看最大停顿，而不是平均。

掌握目标能画出 FCFS + Token Budget 的每轮选择逻辑（含超预算队头处理）；能答出 ITL max 与 ITL p95 何时反向变化及原因。

ch07 · Chunked Prefill

一个人上传了 2048 Token 的长文档，点下发送的瞬间，整个服务里所有正在打字的人同时卡住——因为调度器要一口气把 2048 个 Token 的 Prefill 做完，这期间其他人一次 Decode 都轮不上。ch06 的 Token Budget 本该拦住这种事，但"软"字露了馅：预算不够时只能放行整条 Prompt，预算形同虚设。本章把这件事补齐：单条 Prompt 也可以拆成小块，分多轮做完。

名词卡
名词 白话解释
Chunked Prefill 把一条 Prompt 按预算切块，跨多轮迭代逐步做完 Prefill
Chunk 一轮里被处理的那段 Prompt 切片，含若干 Token
prefilling 状态 请求新状态：Prefill 做了一部分、还没做完
prefill_cursor 游标：记录这条 Prompt 已经算到第几个 Token
硬预算 预算不足时切断 Prompt 而非放行，预算真正有约束力
全局因果偏移 Chunk 内位置仍按整条 Prompt 的全局位置算注意力范围
因果性 每个 Token 只能看见它之前的 Token，不能偷看未来

它是什么：不是文本切分（不受 RAG chunking），而是引擎内部对同一条 Token 序列的增量计算。

怎么工作（拆到计算步骤级）：请求状态机从 waiting → running 扩成 waiting → prefilling → running → finished，机制拆成三步：第一步切块——请求进入 prefilling，prefill_cursor 从 0 开始，每轮调度器按硬 Token Budget 给它切一段连续区间 [start, end)，末尾几个 Token 挪进 running 后可与其余请求拼批（共享前缀长度的多请求 Chunk 分在同一轮计划）；第二步中间块只写 KV——每轮只把本段 K/V 按 Prompt 的全局逻辑位置追加进 Block Table，中间 Chunk 不产出任何 Token；第三步末块才出首 Token——最后一块完成时整条 Prompt 的 KV 齐了，生成首 Token、转入 running。时序从"[整条 Prefill] → Decode"变成"[chunk 0] → Decode → [chunk 1] → … → [末块] → 首 Token"。一个必须做对的计算细节：Chunk 内 Attention 用全局因果偏移——历史长度为 P 时，局部位置 q 只能看见 k ≤ P + q 的 Key，不能按局部位置写 k ≤ q，否则会偷看或漏看历史。

两阶段时间线：回到"算几个位置 × 读多少历史"的底图。baseline（full）的那次长 Prefill 是"一轮并行算 2048 个位置"——算得多、一次做完，但把所有 Decode 轮堵在后面；chunked 把它切成 8 段，每段只算 256 个位置、读已有的 0–1792 份历史 K/V，每段之间正常插入 Decode 轮（每请求算 1 个新位置、读全部历史）。单次停顿从"容纳 2048"降到"容纳 256"，别人等的时间从一整份变成 1/8 份。

数字（3080 Ti、Qwen3-0.6B、budget 256、2048 Token 长 Prompt 干扰实验，README「3080 Ti 实测结果」）：最大单轮 Prefill 316.28→65.39 ms（-79.3%），既有请求最大 ITL 374.78→120.60 ms（降 67.8%），峰值显存降 16.8%。代价同样是再分配：长请求 TTFT 增加 141.6%（它自己排队更久了）、输出吞吐降 6.2%、ITL p95 反而升 88.8%。两个负对照很干净：短 Prompt（128 Token）没有可拆的工作，chunked 反而慢 6.4%——收益来自"拆超预算长 Prompt"本身，不是新增状态机；无并行 Decode 场景中没有要保护的 ITL，隔离收益按定义为零。

算一算2048 Token 的 Prompt 在 budget 256 下拆成几块？2048 ÷ 256 = 8 轮 Prefill，中间穿插 Decode——这也解释了 TTFT 为何变差：同一份工作切成 8 段排队慢慢推进，但每段只有 1/8 长，别人只能等 1/8。
重点Chunked Prefill 让单请求 Prefill 可拆分，Token Budget 才从软建议变成硬约束；本质是延迟在请求之间的再分配。
边界与常见误区Chunk 切得越小停顿越短，但迭代、Kernel Launch、历史 K/V 读取与 Python 状态管理开销越多——budget 512 实测最大 ITL 降 60.4% 而吞吐只降 0.6%，说明档位要按负载扫；最大 ITL 改善不保证 ITL p95 与吞吐同时改善。[易错] 把它当无条件加速器——两个负对照说明收益的前提是"有要保护的 Decode + 有要拆的长 Prompt"；另外它和 RAG chunking、流式接收 Prompt 完全是两码事。
产品对应vLLM/SGLang 均默认启用 Chunked Prefill；max_num_batched_tokens 等参数实际控制的就是每轮 Prefill 的 Chunk 粒度。
方案视角负载里有长文档/Prompt 输入且输出流式交互（多人同时在打字）的业务必须开启；纯批量生成、没有并发交互的离线任务，收益有限还多付轮次开销。现场先问："你们的输入 Prompt 长度分布什么样？输出是不是流式多人并发？"落点指标：既有请求的 ITL max 与长请求的 TTFT p95。
讲给客户的一句话Chunked Prefill 用"首 Token 稍慢一点"，换"其他用户不掉帧"——本质是延迟在用户之间的再分配。

掌握目标能画出 prefilling 状态下 Cursor 的推进与 Chunk 间穿插 Decode 的时序（含全局因果偏移 k ≤ P + q）；能判断某个负载该不该开 Chunked Prefill。

ch08 · Prefix Cache

你要问客服模型 8 个问题，每个问题前面都带着同一段 2048 Token 的公司制度说明。第一条请求把 2048 Token 的前缀算下来没有任何问题，第二条、第三条……每一条都要把这段一模一样的前缀重新 Prefill 一遍——算力花在计算"已知答案"上。系统提示、few-shot 示例、合同/代码模板：很多业务所有请求共用同一段长前缀。本章让后面这些请求直接复用第一条算好的 KV Block，不重算。

名词卡
名词 白话解释
前缀命中 新请求与已缓存的某条序列开头完全一致，可复用其 KV
链式哈希 块哈希绑定父块摘要，同内容不同位置哈希不同
不可变 Block 已填满并宣布只读的物理块，可安全多人共享
私有尾块 未填满的末块与 Decode 块不共享，故无需写时复制
引用计数 多少请求正在用某块；归零才允许回收
leaf-LRU 从链的叶子端开始淘汰最久未用的缓存块
热请求 命中缓存的那次服务调用，TTFT 显著变短

怎么工作（拆到计算步骤级）：baseline（disabled）每条请求重算完整 Prompt；variant（enabled）把 Prefill 拆成三步：第一步，哈希匹配最长完整前缀——把 Prompt 按 Block 切开，沿链式哈希 SHA256(model_namespace || parent_hash || block_token_ids) 逐块查找，取最长连续命中段；为什么必须带 parent：相同的 Token 块在不同历史上下文里算出的 K/V 不同，单独哈希每块会误判命中——自检专门验证了"相同第二个 Token 块位于不同历史上下文时不能误命中"，且哈希命中后还会确定性比较父摘要与 Token IDs。第二步，命中块引用——命中的块都是已填满并发布为不可变的物理块，新请求把它们的引用加进自己的 Block Table 即可（引用计数 +1），一个字节都不重算；未填满的尾块与 Decode 块始终私有，因此无需 Copy-on-Write。第三步，只算未命中后缀——Prefill 只做未命中的 Prompt 后缀；还有一条隐蔽边界：KV 不保存首 Token Logits，所以最多复用 prompt_length − 1 个 Token，至少要重算最后一个 Prompt Token 才能拿到完整 Logits。释放侧两本账分开管：请求结束只减请求引用；缓存索引仍持有的块不回空闲池，池满时按固定 LRU 顺序从叶子缓存块开始淘汰，只有缓存所有权已移除且引用计数为零的块才安全复用。

两阶段时间线：复用全部发生在 Prefill 阶段——热请求的 Prefill 从"并行算 2048 个位置"缩成"只算未命中的几十个位置"，这正是"算得少"的直接兑现；Decode 完全不变，每步照旧算 1 个新位置、读全部历史。

数字（3080 Ti、Qwen3-0.6B、8 请求共享 2048 Token 前缀，README「3080 Ti 实测结果」）：热请求 service TTFT p50 从 384.11 降到 52.64 ms（-86.30%），实际 Prefill Token 16896→2560（-84.85%，命中 14336 Token，即除首条外每条命中全部 2048）。但 Makespan 只降 11.33%——Decode 是大头且分毫不受益；enabled 还为缓存池多保留物理块，峰值显存增加 280 MiB。

算一算为什么 Prefill Token 减 84.85%、TTFT 降 86.3%，Makespan 只降 11.33%？总执行时间 ≈ Prefill + Decode。设 Prefill 占 20%、Decode 占 80%：Prefill 省掉约 85% 只能省总量的 0.85 × 0.20 ≈ 17%——再被缓存管理开销摊薄，剩下约 11% 与实测吻合。收益上限由 Decode 占比决定，不是命中率。
重点Prefix Cache 省的是 TTFT 和 Prefill 算力，不省 Decode 一秒；链式哈希保证"相同 Token 在不同上下文"不会被误共享。
边界与常见误区本期不做部分块共享/COW、并发冷请求去重（in-flight dedup）、跨模型或跨进程共享（跨实例见 ch14）；缓存池多占的 280 MiB 受池容量与 PyTorch 分配方式影响，不能当作所有实现的固定开销。[易错] "命不命中决定一切"——命中率高但 Makespan 只小降，收益上限由 Decode 占比与显存代价共同决定。
产品对应vLLM 的 Prefix Caching（按哈希组织缓存块）；SGLang 的 RadixAttention（Radix Tree 组织前缀）；跨进程/跨实例的分层缓存见 LMCache（ch14）。
方案视角判断按两点：业务前缀是否整齐、有多长。统一系统提示/固定模板/RAG 长 context 的业务值得开；用户自由闲聊、前缀散乱的业务命中率低还白占显存。现场先问"system prompt 是否每轮重复、前缀是否整齐"，再用指标验证：实际执行 Prefill Token 相对总请求数的比值。
讲给客户的一句话前缀缓存的价值取决于业务前缀是否整齐——命中省的是首 Token 延迟和 Prefill 算力，Decode 一秒都省不了。

ch09 · FlashAttention

想把上下文窗口从 2048 放大到 8192，改完配置直接 OOM——不是 KV Cache 装不下，而是 Attention 这一步先把显存吃穿了。ch02 说过，Decode 的瓶颈在"读"：算得少、读得多，好的 Kernel 就是"快读"。但本章的账先落在 Prefill 上：朴素写法要把 QK^T 的整个 Score 矩阵连同 softmax 结果完整写进显存，中间矩阵随序列长度平方增长——4096 Token 增量峰值 2576 MiB，8192 直接 OOM。长上下文能不能上，先卡在 Attention 这个算子的写法上。本章用 Triton 亲手写一个：中间矩阵根本不落显存。

名词卡
名词 白话解释
Score 矩阵 Q 与 K 转置相乘的注意力打分矩阵，尺寸随序列平方
物化 把中间计算结果完整写进显存存放
分块计算 一次只装一小段 K/V 进算，算完丢弃搬下一块
Online Softmax 不等全量打分就边收边修正的流式 softmax
m / l / acc 每行维护的运行最大值、归一化总和、加权累加器
alpha 修正系数 出现更大 max 时用 exp(m − m_new) 把旧结果换算到新基准
微基准 单独测这个算子的受控实验，区别于完整模型
Triton 写 GPU Kernel 的高级语言，比手写 CUDA 简单

怎么工作（拆到计算步骤级）：baseline（eager）显式走 ch02 的注意力三步——出题、配对打分、取内容——但三步之间的 Score 和 Probability 张量按 [seq, seq] 尺寸真正写显存再读回来。variant（inference-only Triton 前向）把这套三步改成流式：第一步装载——Q 常驻，K/V 按 BLOCK_M × BLOCK_N 的 tile 分块从显存搬进片上，算完丢弃；第二步 tile 打分——对当前块算局部 Score，做因果 Mask，取行最大值更新 m_new = max(m, rowmax(scores_tile))，再用 alpha = exp(m − m_new) 把之前所有累加结果换算到新基准；第三步取内容并累加——p = exp(scores_tile − m_new)，acc = alpha × acc + p @ value_tile，l = alpha × l + rowsum(p)；收尾归一——全部块扫完后 output = acc / l。完整 Score 和 Probability 从头到尾不写 GPU 全局显存。两个必须记住的性质：数学结果与 eager 相同（Kernel 数值验证最大绝对误差 0.003906，真实模型 4 Token greedy 输出完全一致）；FLOPs 仍是二次方——省的是中间显存和显存搬运量，不是计算量。接入引擎时的细节：Chunked Prefill 必须用全局因果偏移——历史长度为 P 时，局部位置 q 只能读 k ≤ P + q 的 Key，不能按局部位置写 k ≤ q。

数字（3080 Ti、因果 Attention、head_dim 128、batch 1、heads 16 微基准，README 实测）：1024 Token 单步延迟 1.070→0.316 ms（3.38×），4096 Token 15.937→4.309 ms（3.70×）；增量峰值显存 2576.1 MiB 对 16.0 MiB；8192 Token 上 eager OOM、flash 15.79 ms 正常完成。但接入完整引擎后收益被稀释到极限：2048 Prompt + 16 输出 Token 端到端只有 1.08–1.10×（Makespan 1166.86→1075.65 ms）。原因有三：Chunked Prefill 把每轮 Query 限制在 256 个、Attention 只占整体时间一小部分、Projection/MLP/Paged KV 读取与调度继续占大头。Kernel 加速比 ≠ 模型加速比，这是全系列最重要的反面教材之一。

算一算为什么增量显存从 2576 MiB 掉到 16 MiB？eager 要物化 [seq, seq] 的 Score 矩阵：4096 Token 一个副本就是 4096 × 4096 × 2B ≈ 32 MiB，再乘多头、多层与中间副本；flash 只需要几百 KB 的 tile 加每行 3 个状态量——平方级变常数级。8192 时平方项再翻四倍，eager 于是 OOM。注意这账治的是 Prefill 的中间矩阵：Decode 的 Query 只有 1 个位置，Score 只有 1 行，本来就不大。
重点FlashAttention 省的是显存搬运而非计算量；它决定长序列能不能算，端到端收益幅度则由 Attention 占全模型时间的比例决定。
边界与常见误区本期是 inference-only 教学实现：不支持 backward、任意 Mask，也不感知 Paged KV 的分块存储（K/V 仍先 gather 成稠密再进 Kernel），不能代表 PyTorch SDPA 或官方 flash-attn 库的性能。[易错] "接入 FlashAttention 引擎能快几倍"——微基准 3.70× 到端到端只剩 1.08×，瓶颈在别处；把 Kernel 基准宣传成产品加速能力，正是这一章要你反省的场景。
产品对应FlashAttention 官方库（flash-attn Kernel）；vLLM/SGLang 内置融合的 FlashAttention/FlashInfer 后端。
方案视角长上下文业务的前置条件——8K+ 上下文没有它基本不可行；但选型时不要信 Kernel 公认数字，要问"Attention 占你们端到端时间的多少"，并用集成后的端到端 TTFT/吞吐验证。短上下文、Decode 重负载的服务，FlashAttention 层面的升级感知很小。
讲给客户的一句话FlashAttention 省的是显存搬运：序列越长收益越大、长上下文能不能开全靠它，但整体加速要看它占总时间的多少。

ch10 · CUDA Graph

想象你在指挥一条流水线，每拧一颗螺丝都要喊一声"开始"——工人手速再快，也全耗在等你喊话上。小模型 Decode 就是这条流水线：回到 basics 的两阶段时间线，每步 Decode 只算 1 个新位置、读全部历史 K/V——计算很轻，但 CPU 要逐个提交上千个 Kernel（README 实测单步 1903 次 cudaLaunchKernel），GPU 大部分时间在等指令。ch02 说 Decode 瓶颈是带宽，本章暴露的是另一头：Host 提交开销把带宽瓶颈完全盖住了。CUDA Graph 的思路是"把整段指令提前录成一张施工图，之后每次只喊一声：照图重放"。

名词卡
名词 白话解释
Kernel 提交 CPU 把一个计算任务发给 GPU 执行的动作，每次都有固定开销
Host Launch 开销 CPU 端发起提交所花的时间，与 GPU 实际计算无关
CUDA Graph 把一整段 Kernel 序列提前录下，之后一次调用整体重放
Capture 录制阶段：跑一遍程序，把 Kernel 序列存成 Graph
Replay 重放阶段：一次 cudaGraphLaunch 执行整张图
静态 Buffer 地址和形状固定的预分配显存，Graph 只认固定地址
Context Bucket 预留的上下文长度档位，按档建 Graph
Block Table 逻辑块→物理块映射表，Replay 前可更新内容

怎么工作（拆到计算步骤级）：baseline（static_eager）与 variant（cuda_graph）执行完全相同的 Decode Tensor 程序——相同模型、权重、KV Pool、greedy 设置——唯一变量是提交方式。variant 的流程固定四拍：第一步静态化——为每组 (batch_capacity, context_bucket) 预建独立 Runner，把 input_ids、sequence_lengths、固定宽度 Block Table、覆盖整个 Bucket 的物理 KV Block 全部预分配成固定地址的 Tensor；第二步 Capture——在所有 Slot inactive 的安全状态下完整跑一遍程序，把 Kernel 序列录成 Graph（真实 Prompt 之后才加载，避免 Capture 消耗正式请求状态）；第三步更新——每步 Replay 前改写输入 Token、Block Table 里的物理块 ID 和有效长度：内容可换，地址和形状不许变，无效位置靠 active_mask 屏蔽；第四步重放——一次 cudaGraphLaunch 执行整张图，argmax 和下一 Token 回填也搬进 Graph 内，避免每步 .item() 同步把 CPU 拽回来。

数字（3080 Ti、Qwen3-0.6B、bf16、1 次 warm-up + 3 次重复均值，README 实测）：Profiler 显示 Eager 单步 1903 次 cudaLaunchKernel，Graph 提交侧只有 1 次 cudaGraphLaunch。capacity 1、128 Token 下 Decode TPOT 37.90→5.22 ms（7.26×）；上下文和 Batch 变大后 GPU 计算变重，capacity 4、2048 Token 下只剩 2.25×——Graph 不减少矩阵计算和 K/V 读取，能消除的 Host 开销占比自然下降。端到端实验里 TPOT 提升 4.03×、完整请求只提升 2.53×：Prefill 保持 Eager、不受机制影响，把 Decode 收益稀释了。Capture 一次约 95–140 ms。

算一算capacity 1、128 Token 时每步节省 37.90−5.22=32.68 ms，Capture 花 115.82 ms，115.82÷32.68≈3.5 步回本——前提是这组 Graph 能被后续请求复用（生产系统还要算 Graph Cache miss 与驱逐成本，README 明确此估算不含）。
重点CUDA Graph 消除的是 Host 提交开销，不是计算量；GPU 越忙（Batch 大、上下文长），剩余收益越小。
边界与常见误区可捕获性要用静态换——Bucket 尾部存在无效 K/V 读取和 Mask 计算，请求准入、Block 分配、取消仍在 Graph 外处理。[易错] "静态化导致显存暴涨"——实测 Graph 稳态峰值反而略低于 Eager（复用 Capture 期内存）；真正的显存代价是 KV Pool 必须按 Bucket 整段预留，随 Capacity 和 Bucket 线性增大（本实验 19.2→917.0 MiB）。加速比也不能外推到更大模型或动态流量。
产品对应vLLM、SGLang 均对 Decode 路径启用 CUDA Graph，按 batch size 与上下文档位缓存多套 Graph 实例，命中档位才 Replay [业界通识]。
方案视角小模型、低并发的服务 Decode 粒度细、Host 开销占比高，Graph 收益最大；大模型高并发下 GPU 本就吃饱，Graph 是标配但增益有限。现场先问：你们的加速比是 Decode TPOT 还是端到端？让客户把 TPOT 提升倍数和端到端提升倍数并排看——差距就是 Prefill 等不受机制影响部分的稀释。
讲给客户的一句话CUDA Graph 解决的是"CPU 指挥慢于 GPU 计算"的问题；Batch 和上下文越大、GPU 越忙，剩余收益越小。

ch11 · Greedy Speculative Decoding

你请教授写作文，但他每写一个字都亲自提笔——其实很多字是套路，可以让助教先猜几个候选，教授只做圈阅。Speculative Decoding 就是这个思路：小模型（Draft）连猜候选 Token，大模型（Target）一次批验证。听上去稳赚，本章实测却几乎全是负优化——这个反转比机制本身更值得记住。

名词卡
名词 白话解释
Draft Model 提候选的小模型，便宜但不保证和大模型答案一致
Target Model 做最终裁定的大模型，验证一批候选只跑一次前向
Draft Length γ 每轮让小模型连猜的候选个数
接受率 候选里与小模型外答案相符的比例，收益的决定因素
最长匹配前缀 一批候选里从头连续被接受的那段
Correction Token 首个被拒绝处由 Target 给出的纠正 Token
Bonus Token 候选全对时 Target 顺带多出的下一个 Token
KV 回滚 候选被拒时把两套 KV Cache 截断回接受边界
块验证 Target 对 γ 个候选一次并行前向打分

为什么需要它（用两阶段时间线看 Decode 的串行问题）：basics 的时间线说，Prefill 一次算多个位置所以快，Decode 每步只算 1 个位置——第 t 个字不算出来，第 t+1 个没资格开始，这是自回归的硬依赖，baseline 里大模型被串行调用 N 次。但还有一个被浪费的并行性：模型一次前向本来就能算多个位置的 Logits（Prefill 正是这么干的，"算得多"）。推测解码就是把这个并行性借回 Decode：Draft 先猜一段，Target 一次前向验证一整段——验证 γ 个候选是一次批量前向，像一次"小 Prefill：算 γ+1 个位置、读全部历史"，成本远低于 γ 次串行生成。只要接受率够高、Draft 足够便宜，每轮就能白拿多个 Token。本章实现 Greedy 版本：小模型猜的与大模型 greedy 一致才接受，数学上输出与只跑大模型完全相同。

怎么工作（拆到计算步骤级）：baseline（Target-only）逐 Token 串行生成。variant 每轮四拍：第一步提候选——Qwen3-0.6B 串行连猜 γ 个候选（一轮共 γ+1 次 Draft 前向，每个候选都要接回末尾才能猜下一个）；第二步块验证——Qwen3-4B 对 γ+1 个位置一次并行前向打分；第三步裁定——接受最长匹配前缀，拒绝处补 Correction Token，全对再加 Bonus Token，一轮最多产出 γ+1 个 Token；第四步对账——两套 KV Cache 按同一个接受边界提交或截断回滚，否则 Target 和 Draft 的 Cache 会漂移。正确性实验（FP16）显示输出与 Target-only 逐 Token 一致；但 BF16 下块验证与单 Token 前向选了不同 argmax——数学等价不等于任意 dtype 下的逐位保证，主实验因此固定 FP16。

数字（3080 Ti、FP16、Batch 1、生成 32 Token、EOS disabled、3 次重复均值，README 实测）：中文解释负载接受率最低，γ=8 时仅 0.173，TPOT 加速比 0.284×——越猜越错还越贵；只有接受率 1.000 的代码补全负载在 γ=8 拿到 1.023×，勉强回本。根因在组件成本：Draft 单步 42.51 ms 只比 Target 的 48.16 ms 快约 12%——参数量差 6.7 倍，但 Eager 教学栈里两者都执行大量小算子、都被 Host Launch 拖住（这正是 ch10 要治的病）；一轮还要多付 γ+1 次 Draft 前向，块验证省下的 Target 调用覆盖不了。

算一算一轮 γ=8 的期望成本 = 8×42.51（Draft）+ 约 57（块验证），约 397 ms；期望产出 = 8×0.173+1≈2.4 个 Token，即约 165 ms/Token——比 Target 直接生成的 48.16 ms/Token 贵 3 倍多，接受率低时必亏。
重点投机解码是"用便宜计算赌接受率"；Draft 不够快或接受率不够高时是纯亏，且每轮都要多付 γ+1 次 Draft 前向。
边界与常见误区只实现 Greedy 路径（不含随机 Speculative Sampling）、Batch 1、无 MTP/EAGLE/Medusa；结果不能外推到 32B/70B 或融合执行栈。[易错] "候选越多收益越高"——γ 越大错得越远、Draft 成本线性涨；接受率 0.357–0.833 的组别在所有 γ 下加速比都低于 1。先看组件成本比，再谈接受率。
产品对应vLLM/SGLang 内置 speculative decoding，支持 n-gram、draft model、MTP、EAGLE 等候选来源 [业界通识]；MTP 等更轻量 Speculator 是本机制成立的前提，但不是本章自变量。
方案视角适合输出重复性强（代码、模板）、接受率高，且候选生成器明显比 Target 快一个量级（原生 MTP、融合 Kernel）的负载。现场先问：业务 Prompt 的输出重复性如何？候选生成器单步比 Target 快多少？——接受率和最佳 γ 都要按业务负载实测，不能凭"理论上快"上会。
讲给客户的一句话投机解码是"用便宜计算赌接受率"，Draft 不够快或接受率低时是纯亏——上线前必须按业务负载实测。

ch12 · KV Cache Offloading

餐厅满座时来了新客人：要么门口挂"客满"牌子（拒绝请求），要么请一位吃得最慢的客人暂时去休息区，让出座位。推理引擎显存装不下所有并发请求的 KV 时也面临同样选择——被请出去的客人，随身行李是寄存（swap 到 CPU）还是扔了、回来重吃一遍（recompute）？这就是本章对比的两条抢占恢复路径。

名词卡
名词 白话解释
抢占 显存不足时暂停一个运行中请求，腾出它的 KV Block
受害请求 被选中暂停的请求，默认是最后接纳的那个
swap 整请求 KV 经 PCIe 换出到 Pinned CPU 池，恢复时换回
recompute 直接丢弃 KV，恢复时对全部已有内容重新 Prefill
Pinned Memory 锁页内存，CPU 不换页，可跑满 PCIe 带宽
乐观准入 先放请求进池，不够了再抢占，把池始终打满
保守准入 预留 prompt+最大输出，绝不抢占，池用不满
Makespan 一批请求从到达到全部完成的总时长
ITL 相邻两个输出 Token 的时间间隔

它是什么、为什么需要：显存装不下所有并发 KV 时，悲观预留把池"用不满"，拒绝请求又损失体验。乐观准入 + 抢占给出第三条路：池满了就让晚来的请求挤掉最后接纳的 running 请求，把"显存不足=失败"变成"慢一点但能跑"。换出单位是整请求：回到 basics 时间线——Decode 每步只算 1 个新位置，却要读全部历史 K/V，历史 K/V 一刻不能缺，"部分换出"不存在。

怎么工作（拆到步骤级）。两条路径共用相同的池容量、准入水位、受害者选择（最后接纳的 running 请求）和恢复顺序（swapped 队列 FCFS 优先于 waiting），只在"恢复"一步分岔：

  • swap 三拍：①换出——把受害者整请求 KV 按块主序拼成 contiguous 数据，经 PCIe 拷进预分配的 Pinned CPU 池（连续布局保证一个物理块一次拷完）；②断点存档——CPU 侧记下该请求的 block 表，这就是"断点"；③恢复搬回——轮到它时按 block 表把 KV 拷回 GPU 新块、重建映射，从暂停处的下一个 Decode 步续算。
  • recompute 两拍：①丢——受害请求的 KV Block 直接释放回池；②重 Prefill——恢复时把全部已有内容当成新 Prompt，并行重算所有位置、重建 Cache，再续接 Decode。

一个前置细节：Pinned Pool 必须预分配——现场申请 448 MiB pinned 要约 102 ms，比一次换出还贵，所以池在启动时建好。

数字（3080 Ti、PCIe Gen3 x16、Qwen3-0.6B、bf16、8 请求固定负载，README chapter_12 实测）：swap 的换出+换入合计约 49–63 ms（约 11.9 GB/s）；recompute 的额外 Prefill 暴露约 673–764 ms，重算明显贵于搬运。容量收益成立：swap 吞吐 37.0 vs 保守准入 35.7 token/s（池 230）、44.9 vs 40.7（池 320），逻辑并发从 2–3 升到 4–5；但都低于 664 块大池的 45.5——池充足时抢占收益为零。

算一算Qwen3-0.6B 单 Token KV = 28 层 × 8 KV 头 × head_dim 128 × K/V 两份 × 2 字节 ≈ 112 KiB，Block Size 16 时每块 1.75 MiB；一个 2048 Token 的请求占 128 块 ≈ 224 MiB，按 11.9 GB/s 换出约需 19.7 ms——与 README 实测 2048 Token 换出 19.67 ms 吻合。
重点抢占把显存不足从失败语义变成延迟语义；代价由被抢占请求的秒级暂停承担，恢复方式的选择取决于带宽成本与重算成本的相对值。
边界与常见误区换出副本只用于恢复原请求，不做命中或复用（复用是 ch14）；换出不提升单请求上下文上限；拷贝在默认 Stream 上同步进行，期间 GPU 不推进其他工作（异步化是 ch13）。[易错] "swap 一定优于 recompute"——端到端受负载支配：池 230 中 recompute 吞吐 37.6 略胜 swap 37.0；也别把秒级 ITL max（约等于受害者暂停时长）归因于几十毫秒的 PCIe 拷贝。
产品对应vLLM 的抢占式调度与 CPU Offload（swap-based preemption）[业界通识]；LMCache 等做 KV Cache 分层存储，其"复用"超出本章只换不复用的边界 [业界通识]。
方案视角适合"不能拒绝请求、可容忍偶发秒级慢回复"的客户。现场先问：恢复延迟和重算算力哪个贵？判据落在两条曲线——KV 传输时间（≈上下文字节 ÷ PCIe 带宽）对重新 Prefill 时间（随上下文近线性、随模型变贵）：长上下文、大模型、PCIe 宽的平台偏 swap；短上下文、带宽差时 recompute 未必输。再问 SLA 对秒级尖刺的容忍度——本实验暂停 p95 达 4–10 s。
讲给客户的一句话换出把"显存不够就失败"变成"慢一点但能跑"，代价由被抢占的请求承担，走搬运还是重算要按上下文长度和算力价格算。

ch13 · KV Cache 异步传输

上章的换出有个尾巴：拷贝发生时，GPU 亲自去搬 KV——搬那几十毫秒里自己在"停工"。可你想想快递站：收银员不必亲手把包裹扔上卡车，收完客人的钱继续服务下一位，扔包裹是装卸工的事。GPU 上也有这样一条"装卸通道"。本章只改一个变量：KV 在 GPU 和 Pinned CPU 池之间的搬运，从"计算流上同步搬"换成"独立通道上异步搬"，看显存压力下的调度器能不能趁机干点别的。

名词卡
名词 白话解释
Copy Stream 独立的拷贝通道，与计算流各走各的队列
CUDA Event 流上的"完成回执"，可查询传输做完没有
Block 所有权 某块 KV 此刻归谁管的规则，未转移前不许动
query() 轮询 只查 EVENT 状态、不原地干等的非阻塞问询
暴露等待 调度器被迫停下等传输的时间，优化的真正目标
容量压力 池不够导致抢占，传输与计算竞争资源的场景

它是什么、为什么需要：回到 basics 时间线——Decode 每步算 1 个新位置、读全部历史 K/V，而 ch12 的同步换出恰好卡在"读"上：拷贝排在计算流队列里，前后的 Decode 都排队等它。异步传输不减少搬运字节，只把"搬"从计算队列里摘出去，让"算"和"搬"并行。

怎么工作（拆到步骤级）。variant（async）每次换出/换入走三步：

  1. 提交：D2H/H2D 逐块提交到独立 Copy Stream，计算流立即返回——调度器马上安排下一个 Prefill 或 Decode。
  2. Event 同步：在 Copy Stream 上记一个 CUDA Event 当"完成回执"，传输推进到它即算完成。
  3. 所有权转移：正确性全靠 Event 管块所有权——D2H 完成前 GPU 源块不能释放/改写；H2D 完成前目标块不能读、CPU 源块不能丢。状态机因此多了三个中间态：running → swapping_out → swapped → swapping_in → running。

调度层诀窍在"不白等"：Event.query() 只轮询回执状态、不原地干等；只有确实没有可执行工作、或下次 Decode 必须申请 Block 时，才去等对应 Event——有别的 Prefill/Decode 可推进就先推进。对照 baseline（sync）在默认计算流上逐块拷贝，拷完调度器才继续，期间 GPU 无任何推进。

数字（3080 Ti、PCIe Gen3 x16、Qwen3-0.6B、bf16、Block Size 16，README chapter_13 实测）：受控微基准证明本机确有重叠能力——传输与 BF16 GEMM 并发后，16 Block 一次 D2H 从串行 6.69 ms 压到 4.64 ms（1.44×），各方向加速 1.21–1.50×。但主实验不是单向正优化：池 230 组 async 略慢（39.31 vs sync 39.61 token/s），池 320 组较快（47.62 vs 45.55）。机制指标更干净：async 把暴露等待从 48.3→20.0 ms（池 230）、62.2→19.2 ms（池 320）——等待确实被藏掉了，端到端却还有别的东西在波动。

算一算池 230 组 async 的设备传输 44.8 ms、暴露等待 20.0 ms，即约 55% 的传输时间已被独立计算覆盖；但 Makespan 差值看不出来（38.79 vs 39.07 s）——几十毫秒的传输窗口决定不了几十秒批次里真正的瓶颈。
重点异步传输的正确性靠 Event 管块所有权，不靠提交顺序；能赚多少取决于拷贝时有没有独立计算可做——判断优化用"暴露等待"，不是设备总传输时间。
边界与常见误区D2H 在紧急 Block 水位触发，完成前源块不能释放，重叠窗口可能大部分暴露；H2D 完成前占着 GPU Block 和运行名额，有别的请求时才可能被藏住；不实现 SSD、RDMA、传输优先级或预测性换出。[易错] "开了异步端到端就更快"——池 230 组反而略慢；Makespan 差异远大于传输窗口且波动明显，别把端到端差值全归因于隐藏 PCIe 传输；"异步提交"也不等于"传输已完成"。
产品对应vLLM/SGLang 的 offloading 流水线、NIXL 等 KV 传输层设计中的异步 Stream 使用 [业界通识]。
方案视角需要它的是"抢占频繁、且同一时刻总有别的请求可推进"的满载服务；不需要的是池充足、抢占为零的服务——大池无抢占负对照下收益本来就是零。现场先问"池还紧不紧、恢复时卡上有没有别的活在跑"，判据落到"暴露等待时间"，而不是"异步加速 1.4×"。
讲给客户的一句话异步传输用独立通道和 Event 管住块所有权，卖出的是"搬运期间计算不停"；但要看它是不是真的帮你——请拿暴露等待时间验收，不是拿"开了异步"验收。

掌握目标能画出 Copy Stream 与 Event 化的块所有权转移时序（swapping_out→swapped→swapping_in 并标出"谁在什么时候允许动块"）；能区分"暴露等待"与"总传输时间"两个指标并答出为何前者才是优化目标。

ch14 · 外部 KV Cache 与 LMCache

你重启了推理服务，客户那些三千字系统提示词的 KV 全部蒸发——接下来每个请求又从零 Prefill 一遍；隔壁实例也在重算同一份提示。问题是：KV 只活在单进程显存里，没身份证、出不去。给它一个跨进程都认的"身份证"，换台机器也能 Lookup 一下、加载过来、只算个尾巴——这就是本章。LMCache 之所以存在，就是为了这件事。

名词卡
名词 白话解释
Token Chunk 以 256 个连续 Token 为单位存放的外部 KV 块
CacheKey 链式哈希：模型 + 父块摘要 + 本块 Token，当身份证
Namespace 打包模型/revision/dtype/拓扑等参数的隔离标记
Cache Service 独立进程，只管存不可变 KV 字节与索引淘汰
Lookup/Load/Store 查索引、取 Payload、写回，三步远端访问
leaf-LRU 只淘汰没有后继的叶子块，避免留孤儿前缀
warm 命中 新进程查到旧 KV 并成功加载的状态

它是什么、为什么需要：KV 的价值全在"复用"，前提是"活着且找得到"。ch12 的换出副本只伺候原请求、用完即弃；这里要把 KV 变成跨进程资产：谁需要同一份前缀，谁来取——包括重启后的新进程。

怎么工作（拆到步骤级）。variant（external）把一次 warm 启动拆成三步：

  1. 查最长连续外部块：新 Prompt 切成 256 Token 的 Chunk，逐块用链式 CacheKey SHA256(model namespace || parent chunk digest || chunk token ids) 向独立 Cache Service 发 Lookup；从第 0 块数到第一个未命中的 Chunk 为止，命中前缀必须"最长连续"——中间断一块，后面全不算，缺任何一段 K/V，后面位置的注意力都配不上对。
  2. 搬入本地块：对命中部分发 Load，把远端 CPU KV 重建到新引擎申请的本地 GPU Block，重建本地 Block Table（外部对象不含本地 Block ID，映射必须重造）。
  3. 补算末 Token：外部 Chunk 只存到最后一个 Prompt Token 之前——KV 里没有首 Token 的 Logits，所以即便 512 个全命中，也要对最后 1 个 Prompt Token 做一次 Prefill（时间线上"算 1 个位置"那步）才能吐出回应；未命中的后缀再正常 Prefill。

协议细节两处：服务端按实际字节数限容，Store 校验通过、父 Chunk 在场才发布子 Chunk（子块 CacheKey 链着父块摘要，父丢子全作废，故淘汰用 leaf-LRU 只删叶子）；Lookup/Load 失败或校验不过，引擎记错误并安全回退完整重算——缓存坏了不能影响正确性。

数字（3080 Ti、Qwen3-0.6B、bf16、GPU/External Chunk 16/256 Token，README chapter_14 实测）：正确性端到端过关——两个独立进程，Producer 存完退出，Consumer 仍命中 512 Token、warm 侧只 Prefill 1 Token，输出与重算逐位一致。性能端却是全负优化：2048 Token 前缀 warm TTFT 2131.68 ms vs 重算 480.62 ms（0.23×）；Lookup 始终约 1 ms，瓶颈在 TCP Payload 传输 1831.88 ms 与逐 Chunk 重建，2048 Token 的 KV Payload 达 234,881,024 Bytes（约 235 MB）。

算一算235 MB ÷ 1.83 s ≈ 128 MB/s 有效带宽，而重算 480 ms 里那次 Prefill 只动权重、带宽压力小得多——当"搬进来的字节多到超过链路能力"时，命中的贵过重算的，缓存就成了负资产。
重点给 KV 发跨进程身份证（Token Chunk + CacheKey）是架构上的关键一步；但缓存是否有价值取决于传输路径总成本是否低于重算——"已经命中"不等于"值得加载"。
边界与常见误区本期固定同步 TCP 加 SHA-256 校验的搬运，路径存在用户态复制，不是共享内存、CUDA IPC、GPUDirect 或 RDMA；Cache Service 无认证/多租户且退出即丢数据，不做多个冷请求的并行去重。[易错] "命中了就赚"——当传输成本超过重算成本，命中率越高亏得越多；负优化不是机制错误，是传输路径不达标，别把本教学节点的瓶颈外推到 LMCache 的高性能 Connector 或更大模型。
产品对应LMCache 逐块对应本期（ExternalCacheClient↔Connector、Token Chunker↔Token Index、不可变 KV Payload↔Memory Object、CacheStore↔CPU Backend+LRU）；vLLM 通过 KV Connector 接 LMCache 作为外挂存储 [业界通识]。
方案视角需要它的是多实例部署、频繁重启/滚动升级、请求间共享长系统提示或文档前缀的业务；不需要的是单实例、短上下文、前缀差异大的闲聊型业务。现场先问三个问题落到三个数字上："同一前缀会被打多少次（命中率）？Cache 放在哪层、加载走什么链路？搬一份前缀多少字节、加载 vs 重算的临界点在哪？"
讲给客户的一句话KV 拿到跨进程身份证后，"重启不丢、实例之间能带飞"才有戏；但请务必算过"加载 vs 重算"这笔账再上——慢链路会把缓存做成越用越亏的负资产。

掌握目标能画出 Lookup→Load→重建 Block Table→重算末 Token 的完整流程（含失败回退路径）；能按 Payload 字节数与链路带宽算出"加载 vs 重算"的成本临界点。

ch15 · Prefill/Decode 分离

你让餐厅里唯一的服务员既负责带新客从头念完十页菜单（Prefill，计算密集），又要随时给老客续杯（Decode，访存密集）——两种节奏不一样的活挤在一个人身上，互相拖累，想多雇人也说不清该按哪种活配大厨还是配传菜工。把两种角色拆开，就要有人把"旧客已经念到哪"交接下去：这份交接物就是请求的 KV，交接协议就是本章的 Handoff。

名词卡
名词 白话解释
5 种角色 Prefill Worker、Decode Worker、Handoff Service 三进程
KV Handoff 一份请求的 Prompt KV 从生产者交到消费者的过程
逻辑导出 按连续布局导出 KV，不传进程内物理 Block ID
ACK 接收方"校验通过、装进显存了"的确认回执
ACK-gated 首 Token 等 ACK 之后才允许发给客户端
fallback 载荷损坏/不匹配时退回完整重算的保底路径

它是什么、为什么需要：basics 时间线里，Prefill 是"一次算完几十上百个位置"的并行大活，Decode 是"每步算 1 个新位置、读全部历史 K/V"的串行细活——一个吃算力，一个吃带宽。挤在同一张卡上，长 Prompt 的 Prefill 会瞬间占满算力，同卡 Decode 的 ITL 出现尖刺；想扩容也不知该按哪种负载买卡。拆开各自扩容，代价是每个请求都要经历一次"搬家"。

怎么工作（拆到步骤级）。variant（disaggregated）按 Request ID + Attempt ID 做一次性交接，分三段：

  1. Prefill worker 全程：接单 Worker 只做 Prefill——并行算完整个 Prompt 的所有位置（时间线上"算得多"那步）、建好 KV、顺手产出首 Token，随后它对这个请求的任务结束。
  2. KV+首 Token 过同步通道：把逻辑导出的 KV Payload 走 GPU→CPU→TCP→CPU→GPU 同步发给 Handoff Service 再到 Decode Worker；Payload 用"逻辑布局"（连续、按层），不暴露进程内物理 Block ID——物理块映射是各进程私有的，传过去也对不上。
  3. Decode worker 接管：Decode 校验、分配本地 Block、H2D 导入后回 ACK；Producer 收到 ACK 才释放本地 KV——在那之前谁都不能动这份 KV。首 Token 也在 ACK 之后才允许外发（ACK-gated）：客户端收到首字时，接手方已确实装好 KV，后续 Decode 不断档。

故障路径：Payload 损坏或 Namespace 不匹配时，Decode 发 fallback ACK，双方再用原始 Prompt 完整重算——先保正确，再谈速度。注意它和 ch14 的差别：Handoff 不做前缀 Lookup、不保留副本、只有一次交接，Payload 用完即释放。

数字（3080 Ti、Qwen3-0.6B、bf16、ACK-gated split TTFT、2048 Token Prompt，README chapter_15 实测）：正确性三 Worker PID 互异、Logits 摘要与输出逐 Token 一致；但单卡串行路径是明确负优化——KV Payload 224 MiB，mono TTFT 433.39 ms vs split 2378.55 ms，5.49×。阶段中位数里，Export 约 433 ms、Publish 约 896 ms、Receive 约 358 ms、Import 约 253 ms——交接本身的搬运比 Prefill 本身还贵。端到端也别指望回本：mono 685.59 vs split 2648.27 ms。换成 1.7B 压力模型（同 28 层、8 KV Head，KV 字节不变），split/mono 仍 5.23×，负优化的根不在"模型太小"。

算一算224 MiB 走两次 socket 传递，Publish + Receive ≈ 1254 ms，纯搬 KV 就吃掉约 1.25 秒——monolithic 里这份 KV 根本不用离开进程；这就是"角色分离要付出数据搬家税"的具体单价。
重点P/D 分离卖的是"角色拆开后各自扩容、互不干扰"，不是单请求更快；单请求路径上，它是比 monolithic 多一次昂贵 KV 交接的负优化。
边界与常见误区两个 Worker 共一张卡，没有真正的 GPU 隔离；Handoff Service 无认证/多租户/超时转移，Payload 走同步 CPU Bytes 和 TCP。[易错] "上 P/D 分离就加速"——本期所有长度全负优化；多 GPU 的并行吞吐收益不在范围，别拿本章数字论证产品效果。
产品对应vLLM disaggregated prefill、DistServe、Mooncake 等多卡/多机 P/D 分离方案 [业界通识]；KV-aware 调度是其配套能力，超出本章范围 [业界通识]。
方案视角需要它的是并发大到 Prefill 与 Decode 互相挤压、要按两种瓶颈独立配 GPU 数量的服务；不要的是单实例、低并发的单请求场景——拆开只会多一次搬家税。现场先问"规模是否大到有收益（并发量级、上下文长度、当前卡上两阶段是否互相拖）"，判据落到"两种角色的高峰并发量与资源占比"，而不是"新架构一定快"。
讲给客户的一句话P/D 分离是给"大了"之后做角色分工与独立扩容用的，不会让单个请求变快——你先有多大的并发，再谈拆不拆。

ch16 · 手写Qwen3-0.6B全参数SFT（训练篇 01）

先回答最基本的问题：一次全参数 SFT 的一步，到底由哪些状态和计算构成？

SFT 的全称是 Supervised Fine-Tuning（监督微调）：拿一批"输入对话 → 期望回答"的数据，在预训练权重上继续训练，让基座学会按对话格式回答。训练框架把 Forward、Backward、优化器、断点恢复都封装成黑盒，出了数值问题无从下手。本章不用 Transformers、Trainer 或任何训练框架，只用 Python 和 PyTorch 手写从数据编码到可恢复 Checkpoint 的完整链路，为全系列建立 baseline。

名词卡
名词 白话解释
全参数 SFT 模型里所有权重都参与训练，区别于只训一部分的"参数高效微调"
labels 每个位置"该预测出的正确 Token"编号表；Loss 就是拿模型输出跟它对答案
Causal LM Loss 接龙打分：位置 t 的输出跟 labels[t+1] 对答案，只许看过去
Shifted Cross Entropy 上面那条"错一位对答案"的具体损失实现
梯度裁剪 梯度向量太长时按比例缩短，防止一步走得太猛（本章阈值 1）
AdamW 最常用的参数更新算法：按梯度的一阶/二阶动量走步，附带权重衰减
Scheduler 学习率随训练进度变化的日程表
Checkpoint 训练状态的完整存档（权重+优化器状态等），恢复后能接着跑下一个 Step
Eager Attention 注意力的朴素实现：把完整分数矩阵算出来存住，后续章节会替换它

为什么需要它：训练框架把"一步"藏成一个函数调用。你要研究"训练系统每一笔开销花在哪"，就得先有一条每行代码都能打开看、数学上可验证的链路——否则后面任何优化的对照都无从谈起。

这一章怎么工作：组件全部手写——直接解析 tokenizer.json 的 Byte-level BPE、RMSNorm/RoPE/GQA/SwiGLU 模型、Safetensors 权重加载，固定基座 Qwen3-0.6B-Base@da87bfb6。一步训练拆开是九个可跟随的动作：① 渲染模板——把一条对话文本套进 Qwen3 chat template，变成带 <|im_start|> 边界的完整字符串；② 编码——BPE 把字符串切成 Token 编号，固定长度截断/补齐；③ 构造 labels——把 input_ids 左移一位当答案表，Padding 位置置 -100；④ 前向——Token 过 28 层，每个位置吐出一个"对全词表的打分"（logits）；⑤ Shifted CE——位置 t 的 logits 跟 labels[t+1] 对答案，错一位算交叉熵，得到一个标量 Loss；⑥ Backward——autograd 沿计算图反向，给每个参数算出"这一步往哪调"的梯度；⑦ 全局梯度裁剪——把所有参数的梯度拼成一个向量，范数超过阈值 1 就整体等比缩短；⑧ AdamW——用一阶/二阶动量按 Scheduler 给的学习率更新参数；⑨ Checkpoint——把权重、动量、Scheduler 进度全量存档，恢复后能复现下一个 Step。训练设置刻意保守：单卡、FP32、Micro-batch 1（一次只喂一条样本）、固定序列长度、Eager Attention，除 Padding 外完整对话 Token 都参与 Loss。训练数据是从 MiniMind sft_t2t_mini.jsonl 校验大小与 SHA256 后按固定行号选出的 32 条确定性样本。对照 basics.md 的显存账本：这一步的显存里同时住着权重、梯度、优化器状态三座山，加上激活——"一次参数更新算多少东西"，本章就是那个账本的训练版。

数字（chapter_16 README）：数据文件校验 1,739,201,170 字节后选 32 条样本；正确性靠三条证据链支撑——手算 Shifted Cross Entropy、小模型有限差分梯度对照、Checkpoint 恢复后复现同一个下一 Step。

ch17 · Assistant-only Loss（训练篇 02）

同一个问题换一面：模型到底该跟谁学？

第 16 期的 Loss 让除 Padding 外完整对话的 Token 都成了预测目标——System 提示词、User 的问题、Assistant 的回答，模型都在花梯度学"怎么提问"。SFT 真正想教的是"怎么回答"，所以要把监督信号精确切到回答上。本期保持对话文本、input_ids、模型、优化器一切不变，只改 labels 中哪些位置置为 ignore_index=-100。

名词卡
名词 白话解释
ignore_index=-100 PyTorch Loss 约定的"此题不计分"标记：labels 里值为 -100 的位置不产生 Loss 与梯度
Loss Mask 决定哪些位置参与训练的掩码，就是把不要的位置写成 -100
Assistant-only Loss 只监督 Assistant 回答内容的掩码方案，本章 variant

ch18 · 固定Mini-batch（训练篇 03）

样本怎么进模型，才能既快又不偷偷改变训练目标？

一条更新内逐个样本 Forward/Backward 太慢——GPU 眼里的矩阵太小。把多个样本拼成一个二维 Batch 一次算，批量矩阵计算就能吃满并行度。但变长样本长度不一，拼 Batch 必须 Padding（把短样本用无意义 Token 补齐到最长），而且一不留神会在合并时暗中改变训练目标。

名词卡
名词 白话解释
Mini-batch 一次参数更新用的一小批样本
Padding 给短样本补无意义 Token，把所有样本凑成等长矩形
右 Padding 补在序列末尾的 Padding 方式，便于用 Mask 屏蔽
Loss reduction 把所有 Token 的 Loss 归并成一个数的规则——按 Token 平均还是按样本平均
token_mean 全部有效监督 Token 等权平均：L = Σℓ / Σnᵢ
sample_mean 每个样本先求平均，再让每个样本等权：(1/B)Σ(1/nᵢ)Σℓ
物理槽位 实际送进模型的 Token 总格数，含 Padding
有效监督 Token labels 不为 -100 的真实训练目标

为什么需要它：变长样本下 token_mean 和 sample_mean 不是同一个训练目标。如果逐样本路径和批量路径用了不同的加权，合 Batch 前后训练目标就悄悄变了——这在报表上看不出来，只会表现为"效果莫名变差"。

这一章怎么工作：baseline 是一组 [1, Tᵢ] 调用逐样本累加梯度；variant 右 Padding 到组内最大长度后一次 [B, max(Tᵢ)] 调用。梯度等价要走三步验证：第一步对齐输入——右 Padding 后，Padding 位置的 labels 置 -100，使它们既不产生 Loss 也不产生梯度，两条路径看到的"题目"完全相同；第二步对齐归约——逐样本路径要复现 token_mean，第 i 个样本的 mean Loss 必须乘权重 nᵢ / Σnᵢ 后再 Backward（nᵢ 是它的有效监督 Token 数）；用 sample_mean 时则每个样本乘 1/B——两种权重绝不能混用，混用的瞬间批量路径和逐样本路径就在优化两个不同的目标；第三步对齐更新——两条路径各自累积完梯度后，走同一次全局裁剪和同一次 AdamW Step，FP32 下梯度只差求和顺序噪声。代价侧：物理槽位从 ΣTᵢ 变成 B×max(Tᵢ)，Padding 槽位和激活显存都增加。

算一算一组三个样本长度 T=[900, 200, 300]：物理槽位 3×900=2700，有效 Token 只有 1400，Padding 浪费约 48%。这就是"吞吐要用有效监督 Token/s 衡量"的原因。

数字（chapter_18 README）：Benchmark 扫 Batch Size 1/2/4/8；physical_tokens、non_padding_tokens、supervised_tokens 三本账分开记；输入未用 Pinned Memory，数据在测量前已编码进 Host 内存，故磁盘读取不列为热路径指标。

边界与常见误区批量计算更快但有 Padding 浪费，这正是 ch19 分桶的引子。[易错] "样本平均后再平均"看起来最自然，却把长短样本强行等权，与按 Token 等权是两个训练目标——长短样本监督 Token 数悬殊时偏差可复现。
产品对应DataLoader 的 collate 函数与 padding 策略 [业界通识]；训练配置里的 group_by_length 选项是它的后续。
方案视角看供应商吞吐指标时，追问分母是物理 Token、非 Padding Token 还是监督 Token——三者可差数倍，判据是拿同一批数据的 supervised Token/s 对齐。
讲给客户的一句话合 Batch 不是免费提速，是用 Padding 槽位换批量矩阵计算，账要算监督 Token 的吞吐。
掌握目标能算出给定长度组 T=[900, 200, 300] 的物理槽位数与浪费比例；能区分 token_mean 与 sample_mean 并写出等价加权。

ch19 · 按长度分桶（训练篇 04）

Padding 浪费是 Batch 内长度差造成的——能不能让"队友"长度接近，又不牺牲随机性？

合 Batch 之后，长短样本混在一组时，短样本要陪长样本填满整行槽位。想让 Batch 内长度接近，办法是按长度排序组批；但完全按长度排序会得到一个几乎固定的训练顺序，数据随机性就没了。折中方案：在有限的 Shuffle 窗口内排序。

名词卡
名词 白话解释
Batch Sampler 决定"哪些样本组成一个 Batch"的组件
Shuffle Window 只在窗口内排序的"局部随机"范围，本章旋钮
分桶 窗口内按长度排序后切块组批，让同批长度接近
batch_length_spread_mean Batch 内最长与最短长度之差的均值——直接决定 Padding 量
companion_repeat_ratio 跨 Epoch 同批共现样本对的重复率，衡量随机性损失
plan 一次 Epoch 的批次划分方案，是种子等输入的纯函数，可重放
Epoch 全部训练数据过一遍

为什么需要它：一个具体场景：Batch Size 4，长度 [510, 505, 60, 55] 四条样本同批，物理槽位 2040 里近七成是 Padding——GPU 在替无意义的 Token 算前向。分桶让这四条各自找到长度相近的队友。

这一章怎么工作：baseline 用固定种子全局 Shuffle 后顺序切块。variant 的组批管线拆成五步可跟随的动作：① 全局 Shuffle——用 random.Random(f"{seed}|{epoch}|shuffle") 把 512 条样本的下标完全打乱，这一步保证整体随机性；② 切窗口——把打乱后的排列按顺序切成大小为 window 的窗口，窗口必须不小于且整除 Batch Size；③ 窗口内按长度稳定排序——只重排窗口内成员（等长样本保持随机顺序），让即将同批的样本长度彼此接近；④ 切批——窗口内顺序按 Batch Size 4 切块；⑤ 打乱批序——用同一随机流打乱 Batch 的先后，训练顺序不暴露长度结构。窗口越大，Batch 内长度越接近、Padding 越少；代价是 Batch 成员越来越由长度决定（companion_repeat_ratio 趋近 1），全排序还可能带来可测的训练顺序损失。注意 ②③④ 都不跨窗口动成员——window == batch_size 时每个窗口就是一个随机块，排序不改变成员，分桶与 baseline 完全一致——这个退化性质本身就是正确性对照。plan 是 (lengths, seed, epoch, batch_size, window) 的纯函数，结果 JSON 保存完整 plan，任何一次运行都能重放。

数字（chapter_19 README）：固定 512 条样本、Batch Size 4，窗口扫描 {4(随机), 8, 16, 32, 64, 128, 256, 512}；学习率 2e-5 无调度器、种子 20260912；脚本断言每 Epoch 监督 Token 总量等于编码语料总量、物理 Token 总量等于长度投影值。

算一算512 条样本、batch 4，全 Epoch 有 128 个 Batch。窗口从 4 开到 512，意味着"排序范围"从 1 个 Batch 扩大到整个 Epoch——batch_length_spread_mean 单调下降，companion_repeat_ratio 单调上升，窗口就是这个交换的连续旋钮。
边界与常见误区窗口受"整除 Batch Size"约束，不能任意取值；收益上限由语料自然长度分布决定。[易错] "分桶破坏了随机性"只说对一半——全局排列仍是随机的，被牺牲的是跨窗口的成员共现多样性，且这个损失可用 companion_repeat_ratio 实测。
产品对应HF Trainer 的 group_by_length、各框架的 length-grouped batching [业界通识]。
方案视角长文本混合语料且按 Token 计费时，分桶几乎总是划算；问供应商窗口取多大、有没有报告 Padding 比例随窗口的变化曲线。
讲给客户的一句话分桶用一点样本共现的随机性，换回被 Padding 吃掉的算力，窗口大小可调。
掌握目标能画出 window=8、batch=4 时 16 条样本的分组过程；能判断一个窗口取值是否合法并解释退化性质。

ch20 · Sequence Packing（训练篇 05）

分桶缩小了长度差，但短样本仍独占一行——能不能让它们拼满一行，还互相看不见？

分桶的极限是：只要一个样本独占一行，它自己内部的长度差没人管。Sequence Packing 把多个不切分的样本装进同一个固定容量的物理序列，把 Padding 槽位换成有效 Token。代价是必须严防"串门"：样本 A 的 Token 绝不能被样本 B 的 Attention 看见。

名词卡
名词 白话解释
Pack 多个样本共居的一个物理序列，容量固定
装包（First-Fit） 贪心地把样本依次塞进还能装下的 Pack，样本不切分
Position ID 每个 Token 的位置编号，RoPE 靠它编码相对距离
Block-diagonal Mask 块对角注意力掩码：同一样本内部因果可见，跨样本全屏蔽
加性 Mask 用 finfo(dtype).min 加到分数上的屏蔽方式，Softmax 权重精确为 0
边界 Label 截断 每个样本首个 Label 置 -100，防止上一样本末 Token"预测"下一样本首 Token
负对照 故意用错误机制（如 EOS 直拼不 Mask）验证隔离确实必要

为什么需要它：一个具体场景：Batch Size 4、长度 [510, 505, 60, 55] 四条样本同批，物理槽位 2040 里近七成是 Padding；就算分过桶，独占一行的短样本内部的长度差还是没人管。Packing 的想法很自然：把短样本拼进同一行。但代价是三个正确性约束缺一不可，否则训练语义悄悄出错（下面拆步细讲）。

这一章怎么工作：baseline 沿用 Padding Batch（Batch Size 4，右 Padding）；variant 的装包与隔离分两段讲。装包：固定种子 Shuffle 后 First-Fit 贪心——依次拿起每条样本，塞进第一个还有剩余容量的 Pack，塞不下就开新 Pack；样本不切分，plan 是 (lengths, capacity, seed, epoch) 的纯函数。三条正确性约束，每条防一种悄悄出错的方式：① 位置重置——每个样本在 Pack 内的 Position ID 从 0 重新编号。RoPE 是相对位置编码，不平移则后续样本全部位置相对独立执行发生平移；② 块对角加性 Mask——跨样本与 Padding 位置以 finfo(dtype).min 加到注意力分数上，Softmax 后权重精确为 0，这是隔离能逐位验证的原因；③ 边界 Label 截断——Causal Shift 让位置 t 预测 labels[t+1]，每个样本的首个 Label 必须置 -100，否则前一样本的末 Token 会把下一样本的首 Token 当预测目标。build_pack 执行拼接+重置+截断，build_block_diagonal_mask 造掩码；模型 forward 新增可选 position_ids 与 attention_mask_4d 注入点，缺省时与之前逐位一致。简单的 EOS 拼接加跨样本 Attention 只作负对照——故意不 Mask 跑一遍，证明隔离真的必要。

数字（chapter_20 README）：语料中 26% 样本短于 512 Token，天然能形成多样本 Pack；baseline 每 Epoch 128 Step，Packing 的 Step 数由装包结果决定——Step 数不同是 Packing 的固有属性，不是实现偏差。

算一算容量 512 的一个 Pack 装下长度 [300, 180] 两条样本：Padding Batch 里它们占两行共 2×300（按 300 与 180 各自成行即 600）槽位，Pack 只占 512 槽位且几乎无 Padding——省下的正是行与行之间的补齐。
边界与常见误区收益由长度分布决定——长度整齐的语料没什么可装；每步固定成本（Optimizer、Kernel 启动）随 Pack 数线性放大，单 Pack 每步可能仍慢于 4 行 Padding Batch。[易错] 只拼 Token 不做 Mask 是"看似省了槽位、实则训练语义已错"的最典型事故。
产品对应packing + block-diagonal attention [业界通识]；数据引擎的 sequence packing 选项与多种 Mask 实现。
方案视角语料长度方差大时 Packing 收益最大；问供应商"packing 的 mask 方案是什么、有没有逐位隔离验证"，而不是只看吞吐提升。
讲给客户的一句话Packing 把 Padding 槽位变成有效 Token，正确性靠位置重置、块对角 Mask、边界 Label 三条锁住，缺一条训练语义就悄悄错了。
掌握目标能画出两个样本共居一个 Pack 的 Block-diagonal Mask 结构；能答出三条约束分别防止哪种错误。

ch21 · 离线Token Shard（训练篇 06）

同一个数据集每个 Epoch 都被重复渲染和编码——这种确定性计算为什么占着训练热路径？

Chat Template 渲染和 BPE 编码（把文本切成 Token 编号）是纯确定性计算：同样的输入永远得到同样的输出。它们却发生在训练的每一步数据路径上。把编码搬到训练前一次性做完，训练只做读取——但必须保证读回来的和在线编码逐 Token 一致，坏了能被发现。

名词卡
名词 白话解释
Tokenize 文本 ↔ Token 编号的转换，BPE 是具体算法
在线编码 训练进程里现读现渲染现编码的 baseline 方式
Shard 离线写好的二进制 Token 数据文件，训练按索引随机读
revision 模型/数据的确切版本号，绑进文件头防止版本错配
FNV-1a 64 一种快速非加密哈希，这里只用来检测意外损坏
校验和 给每条记录算的"指纹"，读回时重算比对
O(1) 随机读 按记录号直接跳到位置读取，不用顺序扫描
materialize(index) 两条路径暴露的同一接口：给下标返回编码结果

为什么需要它：一个具体场景：同样的 512 条样本，第 3 个 Epoch 又被完整渲染、编码了一遍——GPU 在等 CPU 做它第 1 个 Epoch 就做过的同一件事。而且"数据到底是哪个版本"如果没有落在字节上，复现实验就全靠口头承诺。

这一章怎么工作：baseline 在线读 JSONL、逐条渲染编码；variant 的离线化拆成四步：① 读 JSONL——按 source line 取出对话文本；② 渲染——套 Qwen3 chat template（与在线路径同一份渲染逻辑）；③ 编码——BPE 切 Token，同时构造 Assistant-only labels（含 -100）；④ 写 Shard——头部固定 100 字节：magic MISFTSKD、格式版本、40 字节模型 revision、40 字节数据 revision、最大长度、记录数；每条记录以 source_line 和长度开头，接 input_ids（u32）与 labels（i32，含 -100），以 FNV-1a 64 校验和结尾；文件尾部是"索引区起始位置"自描述指针加记录偏移表，支持 O(1) 随机读。训练时按索引随机读，每次读取都强制校验：magic/版本/revision 不符、校验和不匹配、索引错位、文件截断，一律抛错而非静默回退。OnlineCorpus 与 ShardCorpus 暴露同一 materialize(index) 接口——同一接口是逐 Token 一致性可全量比对的前提，512 条逐一比对通过，离线化才算"换了个执行阶段"而不是"换了一份数据"。

数字（chapter_21 README）：头部 100 字节；512 条样本逐 Token 全量一致性比对；每条记录校验和为 FNV-1a 64 位。

边界与常见误区收益大小取决于在线编码成本占训练 Step 的比例，需要实测而非默认可观。[易错] 把 FNV-1a 当成完整性保证的全部——它不是密码学哈希，不防恶意篡改；revision 绑定和文件大小/SHA256 校验是另一层。
产品对应预 tokenize 数据格式，如 tokenized datasets / 预编码数据缓存 [业界通识]。
方案视角多 Epoch 长训练或数据集跨机分发时，离线 Shard 几乎稳赚；一次性小实验则要权衡构建成本，判据是"在线编码时间 ÷ Step 时间"。
讲给客户的一句话数据文件自带版本与校验，训练只做读取和验证——复现实验从数据格式这一层就有据可查。
掌握目标能画出 Shard 的头部/记录/索引三段布局；能区分"校验和防什么"与"revision 绑定防什么"。

ch22 · DataLoader预取与异步H2D（训练篇 07）

GPU 算完一步就闲着等下一批数据——这份"等待"能不能藏进"计算"的时间窗里？

Shard 读取、校验、组批和 Host-to-Device 拷贝仍发生在每步关键路径上。同步路径里，GPU 计算和数据准备严格串行；而"读取第 k+1 批"和"计算第 k 批"本来毫无依赖，完全可以同时进行。

名词卡
名词 白话解释
H2D Host-to-Device：把数据从内存拷到显存
预取 趁 GPU 算当前批，提前准备下一批
Worker 线程 后台专门负责物化未来 Batch 的线程
Pinned Memory 锁页内存：操作系统不许换出的内存，DMA 可直接异步拷贝；普通内存的"异步拷贝"会退化为同步
队列深度 最多缓存几个待用 Batch，本章为 2，限制宿主内存占用
CUDA Stream GPU 上的任务队列，不同 Stream 的任务可并行
双缓冲 两份缓冲轮流用：一份在算，另一份在拷
事件（Event） Stream 里的"完成标记"，另一条流可等它

为什么需要它：收益的上限在动手前就能想清楚：可隐藏量不可能超过同步路径的数据侧耗时。当数据成本远小于训练 Step 时，端到端收益自然有限——所以这一章的功夫一半在实现，一半在"量出数据侧到底占多少"。

这一章怎么工作：baseline 同步串行——主线程读 Shard、校验、组批、阻塞式 H2D 到默认流，GPU 全程等数据。variant 把两条时间线交错起来，按第 k 步拆开看：Worker 线（CPU）——后台线程提前把第 k+1 批从 Shard 读出、校验、组批，物化进 Pinned Memory，放入有界队列（深度 2）；主线程（第 k 步开始）——先在拷贝流上对第 k+1 步的 Batch 发起 non_blocking=True 的 H2D（源缓冲为 Pinned Memory，DMA 可以真异步），发起后在拷贝流上记录一个事件；计算流（GPU）——wait_event 等第 k 步自己的拷贝事件完成，然后放心算第 k 步的 Forward/Backward——此时第 k+1 步的 H2D 正在另一条流上与计算并行。两条铁律保证不出错：计算流使用某 Batch 前必须等到它的拷贝事件完成；Pinned 源缓冲在该事件完成前不会被复用（否则拷贝会读到被覆盖的数据）。Worker 异常通过哨兵与 check_error 在主线程显式抛出，不静默吞掉。

数字（chapter_22 README）：Worker 数固定 1、队列深度 2；两条路径消费同一个第 21 期 Shard、同一 Batch 计划与同一训练步体；可隐藏上限 = 同步路径的数据侧耗时。

边界与常见误区队列深度 2 是宿主内存占用与预取距离的折中；Worker 只开 1 个。[易错] 以为加了 non_blocking=True 就异步了——没有 Pinned 源内存和事件管理，拷贝仍会阻塞在默认流上，"伪异步"是这类流水线最常见的坑。
产品对应DataLoader 的 prefetch_factor + pin_memory=True + non_blocking 传输 [业界通识]。
方案视角数据侧耗时占比可以用分段计时量出来；占比小于一成时，预取不是优先级，先看计算段，判据是 CUDA Event 分段时间线。
讲给客户的一句话数据预取是把"等数据"藏进"算梯度"的时间窗里，能藏多少取决于数据侧原本占多少。
掌握目标能画出双缓冲的时序图（计算 k 与拷贝 k+1 重叠）；能判断一个数据流水线瓶颈在数据侧还是计算侧。

ch23 · BF16混合精度（训练篇 08）

FP32 稳但慢——能不能让"算"用低精度、"存"仍是高精度，两头都占？

FP32 的前向/反向由 GEMM（矩阵乘）主导，没吃到 Tensor Core 低精度算力的红利；但直接把参数全降精度又会动优化器的数值稳定性。混合精度的答案：算的部分降，存的主状态不降。

名词卡
名词 白话解释
FP32 32 位浮点数，精度高、显存和带宽翻倍
BF16 16 位脑浮点：指数位与 FP32 同多，动态范围一样大、尾数更少
autocast PyTorch 上下文管理器：进入区间后算子自动选低精度执行
Tensor Core GPU 上专做低精度矩阵乘的硬件单元，BF16 吞吐远高于 FP32
混合精度 算子用低精度、主参数/梯度/优化器状态保持 FP32 的折中方案
GradScaler FP16 专用的损失放大器，防小梯度下溢；BF16 不需要
TF32 另一种自动降精度的 GEMM 模式，本章显式关闭以免混淆变量
dtype 普查 逐模块/逐参数记录实际 dtype 的盘点手段

为什么需要它：不换精度，时间花在"每乘一个数都搬 4 字节"上；全换低精度，优化器的小步更新会被舍入吃掉。混合精度把两者分开：吃算力的部分（GEMM、激活）用 BF16，吃数值稳定性的部分（主权重、梯度、AdamW 动量）保持 FP32。

这一章怎么工作：baseline 全 FP32；variant 的拆法是"autocast 上下文里逐样清点 dtype"。进入 torch.autocast(bfloat16) 后：变了的——GEMM（QKV、O 投影、FFN）的输入被自动转成 BF16，走 Tensor Core；激活、注意力输出在区间内也是 BF16，所以激活显存约减半；没变的——主权重本身仍是 FP32（autocast 只是给算子造一份 BF16 副本，不原地改参数）、梯度 FP32、AdamW 两份动量 FP32、Softmax 等敏感算子仍按高精度走——这就是"混合"二字的全部含义。BF16 的指数位与 FP32 相同、动态范围一样大，因此不需要 FP16 那套 GradScaler。怎么确认上面每一条没说错？靠 dtype 普查：mixed_precision.py 用 forward hook 逐模块记录输出 dtype，并对参数/梯度/优化器状态做 dtype 直方图——"哪些变了、哪些没变"是测出来的，不是推断的。效果预期：GEMM 走 Tensor Core 后前向/反向显著缩短；FP32 主状态不动，峰值显存只部分下降。代价：Loss 与梯度出现 BF16 舍入级分叉并随步数放大，用整 Epoch 轨迹误差量化；TF32 显式关闭并记录，避免混入第三个精度变量。

数字（chapter_23 README）：512 条样本、批次计划与 ch19–22 相同；激活显存约减半、FP32 主状态不变；NaN/Inf 扫描与轨迹误差汇总是正确性的两只仪表。

算一算0.6B 模型：激活显存约减半意味着前向激活部分省一半；但主权重 2.4 GB + 梯度 2.4 GB + AdamW 两份动量 4.8 GB 仍是 FP32 共约 9.6 GB——混合精度省的是"算"，不是"存"。
边界与常见误区TF32 被固定关闭，防止它悄悄替你"开"了低精度 GEMM 污染归因。[易错] 把 FP16 的经验（必须 GradScaler、可能 NaN）直接套到 BF16 上——BF16 的动态范围与 FP32 相同，不需要 loss scale。
产品对应torch.autocast 混合精度；GradScaler 是 FP16 方案 [业界通识]；训练配置里的 bf16=True 选项。
方案视角显卡有 BF16 Tensor Core 时混合精度基本是标配；问供应商"精度策略是什么、优化器状态什么 dtype、有没有轨迹误差监控"，判据是 dtype 普查而不是口头承诺。
讲给客户的一句话混合精度省的是计算和激活，不省优化器状态；数值分叉需要用轨迹误差监控来定价。
延伸阅读NVIDIA: Mastering LLM Techniques（含精度策略的总览背景）
掌握目标能画出一行参数在混合精度下的各段 dtype（前向激活 BF16 / 主参数与优化器 FP32）；能算出激活显存大约减半而状态显存不变的账。

ch24 · 梯度累积（训练篇 09）

想要大 Batch 的稳定梯度，单卡显存却装不下——能不能把一步拆成 K 次小计算，效果还一样？

单步能容纳的 Batch 受单卡显存约束。梯度累积的思路：一个 Optimizer Step 不由一次大 Forward/Backward 构成，而是由 K 个 Micro-batch（微批，小份样本组）的梯度累加而成。关键不是"累加"本身，而是累加时的加权规则——加错了，训练目标就和大 Batch 不是同一个。

名词卡
名词 白话解释
Micro-batch 一次装得下的样本小组；若干微批凑成一个"有效大批"
梯度累积 连续多个微批的 Backward 不更新参数，只把梯度加起来
Optimizer Step 用累积好的梯度更新一次参数的动作
有效 Batch 累积后的等效批量：微批尺寸 × K
token_sum_i 第 i 个微批的监督 Token 数
total_supervised 整个有效 Batch 的监督 Token 总数
OOM 显存不足报错（Out Of Memory）
反例验证 故意用错误加权跑一遍，证明偏差真实存在

为什么需要它：想要大 Batch 的训练语义（更稳的梯度估计、更平滑的 Loss 曲面），单步显存却装不下。拆成 K 次，每次显存只按微批算——容量问题就变成了时间问题。

这一章怎么工作：baseline 一次大 Batch 完成 Forward/Backward/Step。variant 的一步拆成三段：① 切片——make_step_plan 用同一 shuffle 把有效 Batch 按 16 分组、再按微批尺寸切片，保证各臂吃到完全相同的样本序列；② 逐微批累积——第 i 个微批 Forward 算出 Loss，按 token_sum_i / total_supervised 缩放后 Backward；PyTorch 的梯度默认是累加的，所以每个微批的 Backward 只往 .grad 上加、不更新参数；③ 一步优化器——K 个微批全部算完后，执行一次全局裁剪 + 一次 AdamW Step。正确性全在这条加权规则：微批 i 的损失按 token_sum_i / total_supervised 缩放，累积出的梯度才与一次大 Batch 的 token_mean 严格同口径（这正是 ch18 等价条件在"跨次调用"上的重演）。如果每个微批的 Loss 取均值再简单平均，在监督 Token 数不均时会偏离联合目标——本章用反例显式验证这一点，而不是口头声明。FP32 下累积梯度与大 Batch 只差求和顺序噪声。代价是 K 次小 GEMM 的时间加总；收益是微批级显存上限带来的容量（大批 OOM 的配置可以跑）与更细的 Padding 控制。

数字（chapter_24 README）：Benchmark 四臂 big4 / acc_2x2 / acc_4x1 / acc_4x4（大批 4 / 微批 2×2 步 / 微批 1×4 步 / 微批 4×4 步）；大批递增做 OOM 扫描定位容量边界；make_step_plan 用同一 shuffle 按 16 分组再切片，保证四臂吃到完全相同的样本序列。

算一算两个微批分别有 100 和 300 个监督 Token，总监督 400：第一个微批的 Loss 要乘 100/400 = 0.25，第二个乘 300/400 = 0.75——监督多的微批权重大，这才与"全部 400 个 Token 等权平均"同口径。

ch25 · Activation Checkpointing（训练篇 10）

显存里最贵的一批"租客"是中间激活——能不能只留房卡，退房时再重造？

ch24 解决了大 Batch 的显存准入，但 autograd（PyTorch 的自动求导机制）为 Backward 保留的中间激活仍是显存大头：28 层 Transformer 每层的注意力分数、FFN 中间值都被扣着等反向用。Activation Checkpointing 的方案：激活不保存，只保存每层（段）的输入，Backward 时重算前向。

名词卡
名词 白话解释
激活 前向算出的中间结果，Backward 求导时要复用
autograd PyTorch 自动求导：记录前向计算图，反向沿图算梯度
Checkpointing 只存段边界输入、反向时重算段内前向的策略
段（Segment） 连续若干层打包成的一个"重算单位"
RNG 状态 随机数生成器的进度存档；dropout 每次丢哪些数由它决定
重算 Backward 时把该段前向再算一遍，临时重建激活
粒度 段划得多细：越细越省显存、重算越多
非重入式 use_reentrant=False 的官方 checkpoint 实现方式

为什么需要它：一个具体场景：28 层模型 batch 4、长度 512，28 层的激活全部扣着等反向——这是显存峰值的主要来源。若只存每段输入，段内激活用完即弃，峰值显存大幅下降；代价是 Backward 里多出约一次前向的重算。

这一章怎么工作：baseline 保存全部激活到 Backward；variant 的一次前向-反向拆成三段：① 前向（省着存）——把 28 层按 layers_per_segment 分成若干段，只把每段的输入（段边界激活）和该时刻的 RNG 状态存下来，段内中间激活用完即弃；② 反向入口（重造激活）——Backward 走到第 s 段时，先恢复该段前向时的 RNG 状态（dropout 每次丢哪些数由它决定），再在 enable_grad 下把这段的前向重算一遍——段内激活临时重建出来；③ 反传（即用即弃）——对着刚重造的激活正常算梯度，返回输入梯度，重建的激活随即释放，接着处理第 s-1 段。本章手写 RecomputeCheckpoint——一个 autograd Function 实现 forward 存输入与 RNG、backward 恢复 RNG → 重算 → 传播并返回输入梯度——并与 torch.utils.checkpoint 的 use_reentrant=False 对照。dropout 正反例验证："不恢复 RNG 就逐位不一致"——RNG 状态是正确性的一部分，不只是工程细节。粒度扫描 {1, 2, 4, 7, 14, 28} 段呈现权衡曲线：段越细越省显存、重算越多。

数字（chapter_25 README）：模型共 28 层，粒度扫描 6 档 {1,2,4,7,14,28}；双 Epoch 轨迹与不 checkpoint 版本要求逐位一致；容量扫描观察最大 batch/序列边界右移。

算一算28 层、段数为 4 时：每段 7 层，保存的从"28 层全部激活"降到"4 个段边界输入"；代价是每个段在 Backward 里多算一次 7 层前向——全模型合计恰好多约 28 层的一次前向，即"多付一次前向"。
边界与常见误区只存层输入的重算方案，不涉及按算子的选择性 checkpoint。[易错] "checkpoint 就是无损免费"——时间代价恒在；以及忘存 RNG 导致含 dropout 的重算逐位漂移。
产品对应gradient checkpointing，HF Trainer 的 gradient_checkpointing=True、FSDP 内建 [业界通识]。
方案视角显存不够、又不想减 Batch 时第一顺位开关；判据是客户能接受的步时间增幅（约 +1 次前向）与段数设置的匹配。
讲给客户的一句话激活显存可以换成约一次额外前向的时间，段数粒度就是这之间的定价表。
延伸阅读NVIDIA: Mastering LLM Techniques（显存优化技术的总览背景）
掌握目标能画出"存边界→重算→反传"的时序；能算出 28 层模型在段数为 4 时保存与重算的相对量。

ch26 · 训练版FlashAttention（训练篇 11）

注意力显存随序列长度平方增长——能不能算注意力但不把 S×S 矩阵摆出来？

Eager Attention 会物化完整的 S² score/probability 矩阵（S 是序列长度）：长度翻倍，这个矩阵占的显存翻四倍，序列一长显存先爆。FlashAttention 用分块计算解决它——但它在训练里能不能用，还跟精度绑定。

名词卡
名词 白话解释
Attention 矩阵 每对"查的 Token × 被看的 Token"一个分数，共 S×S 格
物化 把整个矩阵实实在在算出来放进显存
SDPA PyTorch 的 scaled_dot_product_attention：一个接口后接多种后端实现
后端 SDPA 背后选用的具体 Kernel（eager/math/mem_efficient/flash）
Flash 后端 真正的 FlashAttention Kernel，要求 BF16/FP16 输入
mem_efficient 显存高效后端：分块计算、FP32 也可用
注入点 模型里预留的替换口：attention_impl 为 None 时走原路径
容量边界 固定显存下能跑的最大序列长度

为什么需要它：一个具体场景：S=4096 时 S² 矩阵是 1600 万格，batch 一大几 GB 就没了——而且这还只是"存分数"，不算算它们的时间。分块计算把"先算完再归一化"改成"一小块一小块地算、边算边累计"，S² 矩阵从头到尾不落地。

这一章怎么工作：baseline 的 Eager Attention 物化 S² 矩阵——出题、配对打分、取内容三步全按朴素写法，打分产生的整个 S×S 分数矩阵和 softmax 后的概率矩阵都实实在在写进显存。variant 换成 SDPA：同一个 scaled_dot_product_attention 接口后面接多种后端，选哪个分四步：① 后端普查——probe_backend_support 实测可用性矩阵：FP32 下 flash 后端不可用（要求 BF16/FP16 输入），可用的是 mem_efficient 后端；② 数值对照——sdpa_math（把公式照朴素写法在 SDPA 框架里算一遍）作为数值参照，不同后端之间只有舍入级数值差异；③ 注入——Attention 实现以注入点方式接入模型（Qwen3Attention.attention_impl），None 时走与之前逐位相同的内联路径，切换后端不碰模型其余部分；④ 训练路径验证——Forward 和 Backward 都走分块 Kernel，整 Epoch 轨迹对照。分块计算的本质：把"先算完整个 S² 再归一化"改成"一小块一小块地算、边算边累计归一化统计量"，S² 矩阵从头到尾不落地。

数字（chapter_26 README）：512 长度下端到端收益不大——机制价值在显存与序列容量边界，序列容量扫描显示能装下的最大长度右移；FP32 下三个可测臂（eager / sdpa_math / mem_efficient）做整 Epoch 对照。

算一算S² 矩阵 FP32 存储约为 S² × 4 字节再乘 batch 与头数：S=512 时一"头"约 1 MB（512²×4B），S=4096 时约 67 MB——64 倍于前者，这就是"容量右移"的价值所在。
边界与常见误区BF16 只出现在明确标注的跨精度对照臂，不与本机制混淆。[易错] 在 FP32 训练里期待 flash 后端——它要求半精度输入，FP32 下只有 mem_efficient 可用。
产品对应FlashAttention 系列、PyTorch SDPA（torch.nn.functional.scaled_dot_product_attention）[业界通识]。
方案视角客户序列长度超过 2–4K 时注意力显存成为瓶颈，分块后端是刚需；判据是目标序列长度下 S² 矩阵的显存账，而不是短序列 benchmark。
讲给客户的一句话FlashAttention 训练版的入门门槛是"能不能装下长序列"，而且后端可用性跟精度绑定，要按 dtype 查支持矩阵。
延伸阅读FlashAttention 论文 (arXiv 2205.14135)（分块计算与在线 softmax 的原始出处）
掌握目标能画出 Eager 物化 S² 与分块计算两路径的显存对比；能答出 FP32 与 BF16 下各自可用的 SDPA 后端。

ch27 · Fused AdamW（训练篇 12）

优化器的数学一个字没改，只是"叫法"变了——为什么还能省出可观时间？

0.6B 模型约有 310 个参数 Tensor。朴素 AdamW（loop 模式）要对每个 Tensor 逐个发射一串小 Kernel——GPU 上"启动一个 Kernel"有固定开销，几百个小 Tensor 乘几遍，Optimizer 段的时间就不好看了。本期数学完全不变，只改 Kernel 的组织方式。

名词卡
名词 白话解释
Kernel GPU 上的一次最小执行单元，启动它有固定开销
Kernel 发射 CPU 命令 GPU 启动 Kernel 的动作，次数多了就是开销
loop 优化器 逐 Tensor 循环更新，每个 Tensor 发射一串 Kernel
foreach 多个 Tensor 打包成批一次性发射，减少启动次数
fused 整个 AdamW 融成单 Kernel：读梯度、更新、写回一趟完成
参数 Tensor 权重按结构切成的存储单元；0.6B 约有 310 个
解耦权重衰减 AdamW 的特征：权重衰减独立于梯度动量执行
偏置校正 Adam 对早期步估计偏小的修正项

为什么需要它：一个具体场景：模型小、步时间短，而优化器一步要对 310 个 Tensor 各发一遍"读-算-写"小 Kernel——Kernel 启动的固定开销积少成多，Optimizer 段在分段时间线里占比显眼。这时"少发射"就是零数学风险的提速。

这一章怎么工作：把一个 AdamW Step 拆到"对 310 个 Tensor 各做什么"。AdamW 对每个 Tensor 的更新数学：梯度先经偏置校正（对早期步估计偏小的修正），权重按解耦权重衰减 wd 0.1 独立缩放（不经过梯度动量），再用一阶/二阶动量走步。三种 Kernel 组织只改"谁一次做多少"：loop——逐 Tensor 循环，每个 Tensor 独立发射一串读-算-写小 Kernel，~310 串；foreach——把 310 个 Tensor 打包成批，每个子操作一次发射作用于全体 Tensor，发射次数除以打包规模；fused——整个 AdamW（读梯度、动量更新、衰减、写回）融成单 Kernel，每个 Tensor 一趟完成。三臂对照的正确性来自 reference_adamw_step——手写单 Tensor 参照实现，验证三臂数值一致（32 步轨迹要求一致且确定性）；"省在哪"来自 count_step_kernels——profiler 统计一次 step 的 CUDA Kernel 数与设备时间。clip_grad_norm_ 三臂走同一路径并单独计时，作为 step 分段计时的锚点——梯度裁剪不进对照变量。

数字（chapter_27 README）：0.6B 模型约 310 个参数 Tensor；三臂对照步 32 步轨迹要求一致且确定性；Kernel 数与设备时间由 profiler 普查量化。

算一算310 个 Tensor、loop 模式下每个 Tensor 若发约 5 个小 Kernel，一步就是 ~1550 次发射；fused 把它压到一次——发射次数差三个数量级，这是纯组织层面的收益。
边界与常见误区不涉及优化器状态 dtype 与分片——那是 ZeRO-1（后续章节）的事，两者维度正交。[易错] 把 fused optimizer 和"更快的收敛"混为一谈——它不改任何数学，只改执行方式；模型大、步时间长时 Optimizer 份额本就小，收益有限。
产品对应torch.optim.AdamW(fused=True)、apex fused optimizer [业界通识]；框架里 optim="adamw_torch_fused" 一类开关。
方案视角参数 Tensor 多、模型小、步时间短的场景里 Optimizer 份额才显眼；判据是 profiler 分段里 optimizer 段占比，而不是无差别上 fused。
讲给客户的一句话小 Tensor 一多，优化器也能吃掉可观的步时间——省 Kernel 发射次数是零数学风险的提速。
掌握目标能区分 loop/foreach/fused 三种 Kernel 组织并画出它们的发射模式；能判断一个优化器加速 claim 是否涉及数学变化。

ch28 · torch.compile（训练篇 13）

Eager 模式下每行 Python 都现算现发 Kernel——能不能让编译器先看完整张图再统筹？

Eager（即时执行）下逐元素算子链（Norm、激活、残差相加这类"逐位置运算"）有大量 Kernel 启动和内存读写开销。torch.compile 让编译器看到整张计算图后做融合优化；但编译不是免费的，账要分三笔记。

名词卡
名词 白话解释
Eager 逐行即时执行的模式，灵活但统筹少
计算图 一次前向涉及的算子依赖关系图
Dynamo torch.compile 的前端：把 Python 代码翻译成计算图
Inductor torch.compile 的后端编译器：生成优化后的 Kernel
算子融合 把相邻多个小算子合并成一个 Kernel，省启动和中间读写
Graph break Dynamo 看不懂某段代码，被迫切断图、退回 Eager
重编译 输入 shape 变化触发再次编译；变长训练的主要风险
dynamic=True 允许动态 shape 的编译模式，用灵活性换部分优化
Break-even 稳态每步节省累计到抵扣首次编译成本所需的步数

为什么需要它：一个具体场景：训练上千步，而第 1 步花了几十秒"编译"。这账划不划算，取决于"首次编译成本 ÷ 稳态每步节省 = 多少步回本"；更隐蔽的风险是变长序列——每来一个新 shape（张量形状）就可能触发一次重编译，训练被编译风暴拖垮。

这一章怎么工作：baseline 是 Eager 执行；variant 的 Forward/Backward 交给 torch.compile（Dynamo 前端把 Python 翻成计算图，Inductor 后端融合逐元素链生成 Kernel），Loss、梯度裁剪、优化器留在 Eager。机制拆到"编译器看见什么"：Eager 下每行 Python 现算现发——Norm、激活、残差相加这些逐元素链，每个小算子各自一次 Kernel 启动 + 一次中间结果显存读写；Inductor 看到整张图后把相邻逐元素算子融成一个 Kernel，中间量留在寄存器/合并的读写里。三笔记账分头记：账一·稳态收益——编译完成后每步省多少；注意 Inductor 只能融合逐元素链，GEMM 本身已高效，收益受 GEMM 份额限制；账二·首次编译成本——timed_first_step 把首步（含编译）与稳态分离单独计量，Break-even = 编译成本 ÷ 每步节省；账三·重编译——dynamo_stats/RecompileTracker 记录图数、重编译与 graph break 计数，dynamic=False 对照 dynamic=True 演示新 shape 触发的重编译风暴。变长序列经 pad_batch_to 固定到 512 形状（不触碰真实 Token 与 Labels），正是规避账三的工程手段。

数字（chapter_28 README）：三臂对照 eager_natural / eager_fixed / compiled_fixed；CPU 编译对照要求 Loss/梯度误差 <1e-5；固定 Shape 20 步对照与编译成本单独计量。

算一算设首次编译花 60 秒、编译后每步省 10 毫秒：Break-even = 60s ÷ 10ms = 6000 步。训练 1 万步划算，训练 500 步血亏——编译收益必须用"步数"摊销。
边界与常见误区编译优化器/裁剪、max-autotune、手动 CUDA Graph 均不混入本期。[易错] 拿"首个 Step"测速——那包含编译时间；稳态收益要在编译完成后测，变长训练的主要风险就是重编译风暴。
产品对应torch.compile/Inductor [业界通识]；训练服务的 shape 策略（固定长度/桶化）是它的配套工程。
方案视角训练 shape 固定、长跑的生产任务是编译的好场景；短任务或 shape 多变时先算 Break-even。判据是"编译耗时 ÷ 稳态每步节省 = 多少步回本"，以及输入 shape 的分布。
讲给客户的一句话编译的账是"首次编译成本 vs 稳态收益"，变长输入会不断触发重编译——生产里要先固定 shape 策略。

ch29 · DDP（训练篇 14）

单卡机制已压到边界，吞吐还要翻倍——打开第一个并行维度时，训练语义还能严格不变吗？

从第 17 期起训练一直发生在单张 GPU 上。数据并行（Data Parallel, DP）的思路最朴素：每张卡持有一份完整模型，各处理全局批次的一个分片，各自算梯度，最后把梯度合起来。难的不是"多卡"，而是"加卡不悄悄改变训练语义"以及"通信别成为新瓶颈"。

名词卡
名词 白话解释
DDP DistributedDataParallel：PyTorch 的数据并行封装
副本 每张卡上那份完整的模型+梯度+优化器状态
分片 全局批次按 rank::world_size 切给每卡的一份
rank / world_size 当前卡的编号 / 总卡数
AllReduce 让所有卡上的同一份数据（这里是梯度）求和后人人拿到相同结果的通信原语
AllReduce SUM 上述"求和"版本，本章 Backward 后执行一次
Ring AllReduce 教学实现：沿环两阶段各 W-1 步完成，通信量 2(W-1)/W·D
Strong Scaling 固定总问题规模加卡，看加速比
NCCL NVIDIA 的集合通信库，AllReduce 的生产实现
互联 卡间通信线路：PCIe 慢、NVLink 快

为什么需要它：一个具体场景：两卡各算半批样本，梯度不同——参数更新会分叉。解决办法只有把梯度"合并成同一个"再更新；而 0.6B 模型的 FP32 梯度约 2.4 GB，每步都要在卡间走一个来回，互联带宽直接决定这笔通信是"顺带"还是"路障"。

这一章怎么工作：baseline 单卡算全局 Batch；variant 的两卡一步拆成五段：① 持全量——每张卡一份完整的模型+梯度+优化器状态副本（这也是为什么 DDP 治不了模型装不下，只治吞吐，残留 2.4 GB 状态要等 ZeRO）；② 分片——全局批次 4 条样本按 rank::world_size 切片，两卡各拿一半；③ 前向+反向——各卡对本地分片正常 Forward/Backward，先不碰对方；④ 一次 AllReduce SUM——Backward 结束后把两边梯度求和，人人拿到同一个结果。本地损失按 supervised_local / supervised_global（本地监督 Token 占全局比例）缩放后，AllReduce 结果与单卡大 Batch 的 token_mean 严格等价——和 ch24 的累积加权是同一个思想在卡间的翻版。通信量公式 2(W-1)/W·D（W 是卡数、D 是梯度字节数）；两卡经 PCIe 无 NVLink 时，每步约 2.4 GB 的 FP32 梯度 AllReduce 完全暴露在关键路径上，Strong Scaling 效率显著低于 2 是预期内的。⑤ 优化器——两卡拿同一份全局梯度，各自走裁剪+AdamW 后参数逐位一致。正确性对照在 AllReduce 之后、裁剪之前捕获梯度（after_allreduce 钩子）；比较时点错了会看到恒定偏差——那是裁剪系数，是比较错误不是梯度错误。

数字（chapter_29 README）：最低 2 张 GPU，参考覆盖 1/2/4 卡与双节点 4+4；每步约 2.4 GB FP32 梯度 AllReduce 走 PCIe PHB；NCCL 微基准覆盖 1–2360 MiB 测 algbw/busbw；对照要求 8 步轨迹与跨 Rank 逐位一致。

算一算W=2 时 AllReduce 通信量系数 2(W-1)/W = 1，每卡发出 D ≈ 2.4 GB；若 PCIe 带宽 16 GB/s，理想也要 ~150 ms/步——和一步计算同量级，这就是"通信暴露"的具体含义。
边界与常见误区本期不使用 Bucket 重叠（下一章）、no_sync（梯度累积配合）和状态分片（ZeRO）——通信严格排在 Backward 之后全额暴露，这正是后续章节要修的。[易错] "多卡自动加速一倍"——同步点暴露时远达不到，判据是 Strong Scaling 效率。
产品对应torch.nn.parallel.DistributedDataParallel、NCCL [业界通识]；所有训练框架多卡模式的地基。
方案视角数据并行适合模型单卡装得下、想扩吞吐的场景；问"通信和计算重叠吗、互联是什么（PCIe/NVLink/IB）"，判据是每步通信字节数除以互联带宽。
讲给客户的一句话数据并行的语义等价性很好证明，但后置的全量梯度同步在慢互联上会全额暴露——通信时机是下一个优化变量。

ch30 · DDP 梯度分桶与通信计算重叠

先回答一个问题：为什么第 29 期的 DDP"慢"在哪个环节？

DDP（Distributed Data Parallel，数据并行：每张卡持有完整模型、各吃一份数据，最后把大家的梯度加起来取平均）。它的梯度汇总靠 AllReduce（全体互相交换并求和，最后每张卡都拿到同一个总和的集合通信）。第 29 期的做法是：Backward 全部算完，再一次性对整份梯度做 AllReduce——通信排队在计算之后，整段通信时间都暴露在关键路径上（所谓关键路径，就是决定总时长的那条串行链条）。真实的 DDP 不这样工作：参数被分成若干桶（Bucket，把相邻参数打包成的通信单位），某个桶的梯度一齐就绪时就立刻发起异步 AllReduce，与后续 Backward 计算重叠。本期只改变一件事：AllReduce 的启动时机。

名词卡
名词 白话解释
梯度 "往哪边调参数能让 loss 变小"的方向值，Backward 逐层算出
Bucket 把相邻参数的梯度打包成一个桶，攒齐一桶发一桶
异步 AllReduce 发起通信后不干等，继续算 Backward，晚点再取结果
关键路径 决定整步耗时的串行链条；藏进链条里的时间等于白省
尾部等待 最后一个桶算完还得等通信收尾的那段时间

为什么需要它：想象你在食堂打饭——要么所有菜都点完再一起结账（第 29 期），要么点一个菜结一次、结账的同时继续点（本期）。当某层梯度算好时，它的通信根本不必等后面的层。

怎么工作（拆到计算步骤级）：整个机制只让"通信别排在计算后面"，拆成三步：

  1. 装桶：build_buckets 按参数逆序装桶——backward 从最后一层往回算，逆序装桶让"先就绪的梯度"恰好聚在同一个桶里；参数粒度打包，不跨桶拆分。
  2. 桶满即发：register_post_accumulate_grad_hook 在每个参数梯度算好的瞬间触发——拷入桶缓冲、计数器加一；桶内梯度一齐就绪，立刻以 async_op=True 发起 AllReduce，不等还没算完的层。
  3. 重叠与收尾：后续 backward 计算与已发出的 AllReduce 并行跑；wait_and_attach 在尾部等所有通信完成，把结果以视图挂回参数。baseline（第 29 期）是把第 2、3 步整体排在 backward 之后，通信零重叠。

桶的大小决定重叠质量——太小则每桶的固定启动延迟加起来反超省下的暴露时间；太大退化为第 29 期的全暴露形态。

算一算每步约 2.4GB 梯度要过 AllReduce。PCIe 3.0 x16 的有效带宽大约 12–16 GB/s [业界通识]，全暴露时单步通信 ≈150–200ms 排在关键路径上；重叠成功时这一百多毫秒的大头藏进 backward 计算——这就是分桶的赌注。

显存账：底数是每步 2.4GB FP32 梯度；分桶额外付桶缓冲与"已发未收"桶的临时显存，桶越大临时显存越高（README 把临时显存列为桶档位的权衡项之一）。

数字（README ch30）：benchmark 扫 1/16/128/1024 MiB 四档桶，3 次重复；假设前提：PCIe PHB、无 NVLink，通信与计算共享带宽，收益可能有限。

边界与易错：收益依赖通信带宽与计算能否真的重叠；桶大小是权衡不是越大越好。[易错] "分桶一定更快"——桶过小时每桶的启动延迟加起来比省下的暴露时间还多。

产品对应PyTorch DDP 内置的 gradient bucket（默认 bucket 化）[业界通识]。
方案视角现场先问"卡间走的是什么互联？"——NVLink 与 PCIe 的重叠收益差一个量级；再看单步梯度量，决定桶档位。
讲给客户的一句话数据并行的通信不必干等——按桶流水发出去，让通信和计算同时进行。
掌握目标能画出"Backward 中按桶异步 AllReduce"的时序图并与一次性 AllReduce 对比；能答出桶过大、过小分别退化成什么。

ch31 · 梯度累积期间延迟同步（no_sync）

先回答一个问题：当一个 Optimizer Step 由 K 个 Micro-step 组成时，前 K−1 次同步是浪费吗？

是。Micro-step（微步）指把一个大批次切成 K 份、逐份算梯度但不更新参数——这叫梯度累积，显存装不下大批次时的标准做法。每微步都做一次全量 AllReduce 是极大的浪费：前 K−1 次可以纯本地累积（no_sync 模式），最后一次统一同步，梯度数学不变、通信量降为 1/K。本期只改变一件事：微步间同步的时机（每微步同步 对照 仅最后一次同步）；Bucket 不用，AllReduce 仍是 Backward 结束后的平铺 SUM。

名词卡
名词 白话解释
梯度累积 切 K 份小批次逐个算梯度、攒够再更新一次参数
no_sync 累积期间不做跨卡同步，各卡只攒自己的梯度
独立累加器 存"每微步 AllReduce 结果之和"的缓冲区
监督 Token 真正参与 loss 计算的 Token（不含 padding）
token_mean loss 按全局监督 Token 数取平均的口径

为什么需要它：K=2 时每微步同步要做 2 次全量 AllReduce，而数学上只需要 1 次——一半的通信是白花的。

怎么工作（拆到计算步骤级）：把两种模式的执行序并排走一遍。

  • baseline every：①微步 k 本地 backward → ②全量 AllReduce SUM → ③结果写入独立累加器；K 个微步重复 K 轮，共 K 次全量 AllReduce。
  • variant last：①微步 k 本地 backward，梯度只加在本卡累积缓冲，no_sync 期间零跨卡通信；②K 个微步全部走完后，一次 AllReduce SUM 统一同步。
  • 两种模式每微步的 loss 都按该微步监督 Token 占比缩放，求和等于全局 token_mean 梯度——数学不变，通信量降为 1/K。[易错] 把每微步的 AllReduce 结果直接加进已被归约的累积缓冲再反复 AllReduce，会把先前微步的贡献放大 World Size 倍——必须用独立累加器。

显存账：每卡梯度仍是 2.4GB 全量驻留——no_sync 不省显存，省的全是通信（全量 AllReduce 从每步 K 次降到 1 次）。

算一算每步全量 AllReduce 的字节数约 2.4GB（FP32 0.6B 梯度），K 个微步下节省 = (K−1)/K × 2.4GB——K=2 省 1.2GB、K=4 省 1.8GB 的卡间传输。

数字（README ch31）：主对照 K=2（全局 batch 4），容量对照 K=4（全局 batch 8，每卡每微步 1 样本）；K=2 时 no_sync 省一次全量 AllReduce，即每步通信量 1/K。

边界与易错：省的是通信不是计算，backward 计算量不变；K 越大每微步 batch 越小、算力利用率越低。[易错] "延迟同步会改变梯度"——正确实现下两种模式梯度逐位（FP32 结合律容差内）一致。

产品对应PyTorch DDP 的 model.no_sync() 上下文、HF Trainer 的 gradient_accumulation_steps [业界通识]。
方案视角现场先问"显存允许的单步 batch 多大？"——不够就得累积，累积就该配 no_sync；顺带确认框架是否真的关掉了微步间同步。
讲给客户的一句话小卡训大 batch，靠梯度累积；累积期间关掉跨卡同步，通信量直接除以累积份数。
掌握目标能算出 K 个微步下 no_sync 的通信量节省；能答出"对已归约缓冲反复 AllReduce"错在哪里。

ch32 · ZeRO-1：切分优化器状态

先回答一个问题：DDP 每张卡上，最占显存但"最不该人手一份"的是什么？

优化器状态。AdamW 给每个参数存两个动量（一阶矩、二阶矩，可理解为"最近梯度的滑动平均"和"滑动平方平均"），FP32 下是参数字节数的 2 倍。DDP 每卡持有完整模型、完整梯度和完整优化器状态——0.6B 模型在 12GB 卡上已足以形成容量压力。本期只改变一件事：FP32 优化器状态是否在 Data Parallel Rank 间切分（ZeRO-1；Shard 指每卡只留 1/W 的分片）。参数和梯度仍每卡完整。

名词卡
名词 白话解释
优化器状态 AdamW 每参数两份动量，更新参数用的"记忆"
ZeRO 零冗余优化器：把训练状态切到各卡，消除人手一份的冗余
Shard 一份数据被切成 W 片，每卡只持一片
AllGather 各卡把各自分片拼回完整数据、人人拿全量的集合通信
Rank 分布式训练里每张卡的编号

为什么需要它：显存账（README 相对关系口径）：0.6B FP32 下参数 2.4GB、AdamW 状态 4.8GB（见 ch43 账本）——优化器状态是参数的 2 倍。复制式 DDP 里这 4.8GB 每卡一份、W 份全同；切分后每卡只留 1/W。0.6B 尚且如此，几十 B 的模型下这笔账就是"训得动 vs 训不动"。

怎么工作（拆到计算步骤级）：AdamW 是逐元素更新，派生出三步机制：

  1. 切分：shard_boundaries 把参数连续切块、余数给前几个 Rank；"本 Rank 状态分片 × 参数分片 × 梯度分片"与全量 AdamW 逐位一致——切了不等于改了数学。
  2. 只为分片配状态：ShardedStateAdamW 仅给本地分片分配 exp_avg/exp_avg_sq，step() 逐操作镜像 torch AdamW 公式，只更新本卡拥有的那段参数。
  3. 分块 AllGather 同步新参数：all_gather_parameters（块缓冲 128MB、非整除按 padded 长度打包）把更新后的参数同步给其他 Rank——DDP 原本没有的约 1×参数字节的额外通信。

显存账：0.6B FP32 下参数 2.4GB、梯度 2.4GB、AdamW 状态 4.8GB（见 ch43 账本）——复制式 DDP 每样全量；切分后状态降为 4.8/W GB，参数与梯度不动。

算一算W=2 时 AdamW 状态从每卡 4.8GB → 2.4GB，省 2.4GB；付出每步约 2.4GB（参数字节）的 AllGather——用便宜的通信换昂贵的显存。

边界与易错：多付通信，小模型上可能不划算；参数、梯度仍全量，更大的模型还得继续切（ch33/34）。[易错] "ZeRO-1 改变了数学"——分片更新与全量 AdamW 逐位一致，语义不变。

产品对应DeepSpeed ZeRO Stage 1、FSDP 的 optimizer state sharding [业界通识]。
方案视角现场先问三个数：卡数、单卡显存、卡间带宽。显存是第一瓶颈且带宽尚可时先上 ZeRO-1；用 capacity_probe 式探针找到 Batch/Length 准入边界再定服务形态。
讲给客户的一句话优化器状态是训练显存的大头，把它按卡数切分，同样的卡能装下更大的 batch 或更长的序列。
掌握目标能算出 W 张卡下 ZeRO-1 的状态显存与新增 AllGather 字节；能判断给定显存下该不该上 ZeRO-1。

ch33 · ZeRO-2：再切分梯度

先回答一个问题：backward 结束那一刻必须存在的完整梯度，之后都用得上吗？

用不上。ZeRO-1 之后每卡仍保留完整梯度，但本卡的优化器只会用到"属于本卡参数分片"的那一份。本期只改变一件事：梯度是否切分——完整 AllReduce 对照 Reduce-Scatter（归约求和的同时顺手分发：每卡只拿到总和里属于自己的那一片）。优化器状态沿用 ZeRO-1 切分，参数仍每卡完整——所以是 ZeRO-2 而不是 ZeRO-3。

名词卡
名词 白话解释
Reduce-Scatter 各卡数据求和后按编号分发：人人拿到总和的 1/W
梯度分片 本卡只保留"本卡参数分片"对应的梯度片
全局范数 所有参数梯度平方和开根号，梯度裁剪用
裁剪 梯度范数超阈值就按比例缩小，防训练爆炸
容量准入边界 给定显存下能跑的 Batch/长度上限

为什么需要它：backward 结束那一刻必须存在的完整梯度，之后只有本卡那一份会被用到——省下就是白赚。连同 ch32 的状态分片，每卡省下的显存直接换成更大的 batch——准入边界外移。

怎么工作（拆到计算步骤级）：梯度从此"按所有权分发"，四步：

  1. backward 产梯度：autograd 逐参数算出本卡完整梯度（这一步不变）。
  2. Reduce-Scatter 只留本 rank 分片：reduce_scatter_gradients 逐参数发起——整除时直接以梯度视图为输入，完成后立即释放完整梯度；非整除按零填充，填充位求和仍为零，不污染结果。
  3. 本地 optimizer step + 分块 AllGather 同步参数：与 ZeRO-1 完全相同的 ShardedStateAdamW 分片更新与参数刷新。
  4. 全局范数裁剪：梯度切分后 clip_grad_norm_ 直接失效——各卡只有局部范数，必须"各卡局部平方和 → 一次标量 AllReduce → 合成全局范数 → 按比例缩放本地分片"。

关键等式：Reduce-Scatter 与 AllReduce 的每链接数据量同为 2(W−1)/W·D，W=2 时通信时间接近——同样的通信字节数，免费换来"只留 1/W 梯度"（等价替换，不是新开销）。

显存账：完整梯度 FP32 下 0.6B 是 2.4GB；Reduce-Scatter 后每卡只留 2.4/W GB。

算一算W=2 每卡省 1.2GB 梯度显存、W=4 省 1.8GB（2.4×(1−1/W)）；通信侧不亏——Reduce-Scatter 与 AllReduce 的每链接数据量同为 2(W−1)/W·D，W 越大两者同步下降，省显存不减通信时间。

数字（README ch33）：固定项沿用 2 卡配置；capacity_probe 扫 ddp/zero1/zero2 × Micro-batch {1,2,4} × Length {128,256,512} 的准入网格；假设 ZeRO-2 应比 ZeRO-1 更晚 OOM。

边界与易错：真实 ZeRO 的扁平桶化 Reduce-Scatter 本期不做，逐参数发起的通信代价如实测量；参数仍完整常驻。[易错] "Reduce-Scatter 是新的通信开销"——W=2 时它与 AllReduce 数据量相同，不是额外开销而是等价替换。

产品对应DeepSpeed ZeRO Stage 2、FSDP 的 grad sharding [业界通识]。

ch34 · ZeRO-3 / FSDP：再切分参数

先回答一个问题：参数只在 forward/backward 里被读，凭什么在两步之间整份占着显存？

不该占。ZeRO-3/FSDP（Fully Sharded Data Parallel，全分片数据并行）让训练参数也只以 Shard 形式常驻每个 Rank，用的时候再临时拼全量。至此每卡常驻模型状态从 ZeRO-2 的 2N+14N/W 降到 16N/W 字节（README 的 FP32 账本口径，N 为参数量、W 为卡数）。本期只改变一件事：参数是否分片，对照 ZeRO-2。

名词卡
名词 白话解释
AllGather 参数 forward 前把各卡参数分片临时拼成全量
Reshard 用完全量立刻释放全量存储，退回分片状态
热路径 forward/backward 主计算流程，通信进去就要排队
no-grad 区 autograd 不记录的代码段，纯搬运用
tied 权重 Embedding 与 LM Head 共用同一个参数

为什么需要它：显存账（README 口径）：ZeRO-2 每卡 2N+14N/W，ZeRO-3 16N/W——W 越大差距越大。0.6B 小模型上差异不明显；参数量上去后这是"单机装不下 → 必须多机"还是"单机多卡即可"的分界。

怎么工作（拆到计算步骤级）：参数从此有了完整生命周期，四步一个循环：

  1. 分片常驻：训练参数平时只以 Shard 形式躺在每 Rank；forward 需要参数时，在 autograd 不可见的 no-grad 区里 AllGather 拼出全量权重。
  2. 算完即 Reshard：本单元的前向计算结束后真正释放全量存储、退回分片——不是"标记可回收"。
  3. backward 前再 AllGather：权重梯度要用全量权重，按需再拼一次；算出的权重梯度当场 Reduce-Scatter，只有本 Rank 分片落进 .grad。
  4. 分片 Optimizer Step：与 ZeRO-1/2 相同的分片 AdamW；下一个 forward 的 AllGather 本身就是参数刷新——ZeRO-1/2 那次 post-step AllGather 被取消。 代价：AllGather 从"每步一次"搬进了热路径；0.6B 上 Step Time 大概率变长，README 明确保留这个负优化结果。 显存账：W=4、N=0.6B（FP32）时：ZeRO-2 每卡 2N+14N/W = 1.2+2.1≈3.3GB 常驻模型状态，ZeRO-3 = 16N/4 = 2.4GB——参数、梯度、状态全按 1/W 等分。
算一算按公式代值（N 取 0.6GB 的口径）：W=8 时 ZeRO-2 每卡 2N+14N/8 ≈ 2.25GB，ZeRO-3 = 16N/8 = 1.2GB；W=4 时 3.3GB vs 2.4GB——差距随 W 线性放大，0.6B 上不算悬殊，几十 B 模型上就是"单机多卡 vs 必须多机"。

数字（README ch34）：参考配置 4 卡、覆盖双节点 4+4（W=8）；benchmark 扫 W ∈ {2,4,8}；显存报告与理论账本（2N+14N/W vs 16N/W）同列；FSDP 的 Reduce-Scatter 取平均，本地 loss 乘 W 校正后与全局 token_mean 一致。

边界与易错：通信进热路径，带宽差时纯负优化；激活重算与 CPU Offload 本期排除。[易错] "ZeRO-3 一定比 ZeRO-2 快"——它是容量方案不是速度方案，小模型上大概率更慢。

ch35 · MLP Tensor Parallel

先回答一个问题：ZeRO 切的是"训练状态"，单层内部的矩阵运算还能切吗？

能。Tensor Parallel（TP，张量并行：把一层内部的权重矩阵切开，各卡算自己那块，再拼起来）。本期只切 SwiGLU MLP：Gate/Up 权重沿输出维切（Column Parallel，输入复制、输出分片），Down 权重沿输入维切（Row Parallel，输入分片、输出 AllReduce 求和）。Attention、Embedding、LayerNorm 保持每卡完整，单独测清 MLP TP 这一个机制。

名词卡
名词 白话解释
Column Parallel 权重按列切：各卡算不同的输出通道
Row Parallel 权重按行切：各卡吃不同的输入切片，输出求和
f 算子 forward 恒等、backward 做 AllReduce 的通信占位符
g 算子 forward 做 AllReduce、backward 恒等的通信占位符
SwiGLU Qwen3 的 MLP 结构：silu(Gate)×Up 再过 Down

为什么需要它：单卡显存装不下"单层的权重+激活"时，就得把层切开。0.6B 单卡本可完整常驻，所以 TP 在本实验里更可能是负优化——这是课程预期内的合法结果，负优化如实保留。

怎么工作（拆到计算步骤级）：一个 forward 一个 backward，四步：

  1. 输入复制、切权重算局部：每 Rank 拿相同的输入 x，算自己分片的 G_r = x@W_gate_r^T、U_r = x@W_up_r^T、H_r = silu(G_r)·U_r、P_r = H_r@W_down_r^T——Gate/Up 沿输出维切（Column Parallel），Down 沿输入维切（Row Parallel）。
  2. forward 一次 AllReduce（g 算子）：各自的部分和 P_r 求和成完整输出 y——每层前向的通信。
  3. backward：分片权重梯度全留本地：dW_down_r = dY^T@H_r、dW_gate_r、dW_up_r 只依赖本 Rank 分片前向和复制的 x；各 Rank 分片梯度按顺序拼接就是完整梯度——不需要也不应该 AllReduce。
  4. backward：残差流输入梯度一次 AllReduce（f 算子）：真实梯度是 Σ_r dX_r；down_proj 前向 AllReduce 的 backward 是恒等、补不上这一步——漏掉它，"部分梯度"沿残差流流进 Attention 路径，训练语义被静默改坏。

第三类陷阱：复制参数（Attention、LayerNorm）的梯度各卡天然相同（forward AllReduce 后激活逐位一致），再做 AllReduce SUM 会恰好放大 tp_size 倍——是错误不是浪费。三类梯度三种处理，是 Megatron 张量并行的核心纪律 [业界通识]。

显存账：MLP 的 Gate/Up/Down 权重与其 AdamW 状态按 1/tp_size 与其他卡分摊，Attention/Embedding/LayerNorm 仍全量复制；README 的所有权账本按"复制参数/分片参数/状态"三类同列。

算一算tp=2 时 MLP 参数与其 AdamW 状态每卡各减半（省 MLP 参数 × 6 字节 FP32 + 动量的一半）；Attention/Embedding 逐字节不变——所以 0.6B 上挤出不多，模型越大 MLP 占比越高收益越大。tp=4 再减半，但每层 2 次 AllReduce 也在暴露的链路上排队。

数字（README ch35）：每层新增 2 次 TP AllReduce（forward down_proj 输出、backward MLP 输入梯度），全部暴露在关键路径上；对照臂 tp1/tp2/tp4，正确性红线 loss < 1e-5。

边界与易错：TP 通信暴露不重叠，收益依赖高速互联；每层两次 AllReduce 随层数线性累积。[易错] "所有梯度都要 AllReduce"——分片权重不需要，复制参数更不能做，三类梯度三种处理。

产品对应Megatron-LM 的 MLP 并行、vLLM/SGLang 的 TP 推理同源机制 [业界通识]。
方案视角现场先问"卡间互联带宽够不够 TP"——TP 的 AllReduce 每层两次且不能重叠，NVLink 机器和 PCIe 机器结论完全不同。
讲给客户的一句话TP 把一层内部的计算切开分给多卡，但每层要付两次"全员对账"的通信——只有高速互联才付得起。
掌握目标能画出 MLP TP 的 f/g 算子位置；能区分三类梯度的通信要求并答出"复制参数再 AllReduce 会放大几倍"。

ch36 · Attention Tensor Parallel

先回答一个问题：MLP 切完了，Attention 的"头"怎么切？

按 Head 切。Qwen3-0.6B 用 GQA（Grouped-Query Attention：多个 Q 头共享一组 KV 头，省 KV 显存的注意力结构）：32 个 Q 头、8 个 KV 头（4:1）、head_dim 128。TP=2 时每 Rank 拿 16 个 Q 头 + 4 个 KV 头，TP=4 时 8+2——切分必须满足整除约束，每 Rank 拿整数个完整 Head；head_dim 永不切。

名词卡
名词 白话解释
Q/KV Head 注意力的"视角"：Q 头提问，KV 头提供检索内容
GQA 多个 Q 头共享一组 KV 头，Q:KV = 4:1
RoPE 给 Q/K 加位置信息的固定旋转，Head 内操作
q/k norm Qwen3 对每个 Head 内部做 RMSNorm
repeat_kv 把 KV 头复制 4 份对齐 Q 头的操作

为什么需要它：0.6B 的 Attention 参数占比小，预期收益有限甚至为负——但机制必须掌握：这是大模型 TP 的标准组成。

怎么工作（拆到计算步骤级）：在 MLP TP 基础上，Attention 补做四步：

  1. 按 Head 切投影：q/k/v 投影按 Head 行切（本 Rank 只算自己的 16+4 份投影）、o_proj 切对面的列；RoPE 是 Head 内的固定旋转、repeat_kv 只涉及本 Rank 的 Q/KV 对——都在局部 Head 集合内重放，与全局逐位等价。
  2. Attention 部分和不归约：本 Rank 的注意力输出就是部分和，直接交给 MLP 段——归约只发生在块边界，块内不对账。
  3. 每层通信账：forward 2 次（o_proj 输出、down_proj 输出）+ backward 4 次（两个块输入梯度 + q/k norm 同步）——从 mlp_tp 的 1+1 变成 2+4。
  4. 本期特有的陷阱——q/k norm：这两个 norm 权重每卡复制，但各卡只累积自己那几个 Head 的梯度项——原始梯度是部分和，各卡不同；不处理则各卡对同一参数施加不同更新，副本从第一次 optimizer step 起静默分叉。实现用 post-accumulate-grad 钩子对每个 norm 权重做一次 backward AllReduce SUM。

显存账：Attention 的 q/k/v/o 权重及其 AdamW 状态按 Head 数等分成 1/tp_size（TP=2 时 Q/KV 都减半，局部 GQA 组数恒为 4），LayerNorm/Embedding 仍复制。

算一算TP=2 → 每 Rank 32/2=16 个 Q 头、8/2=4 个 KV 头；TP=4 → 8+2。无论切几份，每 Rank 的"局部 GQA 组数"都是 4 个 Q 头共享 1 组 KV——组结构在切分下守恒。

数字（README ch36）：32 Q/8 KV Head，TP=2 → 16/4，TP=4 → 8/2，局部 GQA 组数恒为 4；attn_tp 臂每层 6 次 AllReduce 对 mlp_tp 的 2 次。

边界与易错：Head 数与 tp_size 的整除约束（32/8 都能被 2、4 整除）；0.6B 上收益小。[易错] "RoPE 要在全局上做"——它是 Head 内固定旋转，局部重放逐位等价。

产品对应Megatron-LM 与 vLLM/SGLang 的 Attention TP、GQA 布局 [业界通识]。
方案视角现场先问"卡间互联带宽够不够 TP"，再看模型 Head 数能否被 TP 度整除——不整除的模型配不出来的 TP 度直接排除。
讲给客户的一句话Attention 按"头"切是多卡并行的天然切法，但每层通信次数翻倍，对互联带宽的要求比只切 MLP 更高。

ch37 · 词表并行 Embedding 与分布式 Cross Entropy

先回答一个问题：TP 模型里最大的单项激活是什么？

不是注意力，是 Logits。Qwen3-0.6B 词表 151936；batch 2 × seq 512 的完整 Logits 是 151936 × 1024 × 4B ≈ 622 MiB——TP 模型里最大的单项激活。本期把 Embedding/LM Head 沿词表维切分（TP=2 每 Rank 75968 行），并用不物化完整 Logits 的分布式 Cross Entropy 闭合训练。

名词卡
名词 白话解释
Logits 对全词表每个 Token 打的分数，CE 的输入
Cross Entropy（CE） 把分数变成"下一个词"的 loss 的标准算法
log-sum-exp CE 里的归一化分母，可分块计算
Vocab Parallel 词表按行切开，每 Rank 持有一段
tie Embedding 与 LM Head 共享同一个权重矩阵

为什么需要它：622MiB 的完整 Logits 在长序列/大 batch 下线性膨胀，常常是 OOM 的元凶；分片后每 Rank 只物化自己的 1/tp_size 段。

怎么工作（拆到计算步骤级）：CE 的两个数学性质让"不物化全 Logits"成为可能：log-sum-exp 可按词表任意分块归约；softmax−onehot 的 backward 只需要本 Rank 分片和三个全局标量。逐步走：

  1. 词表切行：Embedding/LM Head 沿词表维每个 Rank 持 75968 行（tie 共享同一分片参数）；Embedding 查表时越界 token mask 成 0、输出一次 AllReduce 求和，人人拿到完整隐状态。
  2. 分片 logits：LM Head 只算本 Rank 分片的 logits，完整 Logits 从 622MiB 降到 311MiB。
  3. 分布式 CE 的 3 次 forward Collective：全局 max 用 AllReduce MAX、全局 exp 和用 AllReduce SUM、目标 token 的 logit 按所属 Rank 用一次 AllReduce SUM 取回——三次 Collective 的尺寸都是 token 数而不是词表数，几乎不占带宽。
  4. backward 0 通信：(softmax − onehot) 只用本 Rank 分片和三个全局标量即可算出——CE 本身零反向通信。真正要补的是 LM Head 输入梯度 dlogits_r @ W_r 是部分和，需要一次 backward AllReduce（f 算子）——漏掉它，LayerNorm 梯度跨 Rank 不一致、tied Embedding 梯度对照失败。tie 的 lookup+logits 两条路径梯度自动累进同一个分片参数。

显存账：批 2 × seq 512 下的完整 Logits ≈ 622MiB 是 TP 模型最大的单项激活，长序列/大 batch 下线性膨胀、常是 OOM 元凶；再加上 Embedding/LM Head 权重与其状态按 1/tp_size 分摊。

算一算152.0K 词表 × (批 2 × 512 tokens = 1024 个位置) × 4B ≈ 622 MiB；TP=2 只物化一半 ≈ 311MiB，比值恒为 1/tp_size。

数字（README ch37）：词表 151936、TP=2 每 Rank 75968 行、batch 2×seq 512 完整 Logits ≈ 622 MiB；vocab_tp 臂 forward 每层 2 次块输出 + embedding 1 次 + CE 3 次。

边界与易错：0.6B、tp=2 下收益可能仍为负——负优化如实保留；词表必须被 tp_size 整除。[易错] "分布式 CE 的 backward 很贵"——恰相反，它 backward 0 通信；固定代价是 LM Head 输入梯度那一次 AllReduce。

产品对应Megatron-LM 的 VocabParallelEmbedding 与分布式 CE、vLLM 的并行词表 [业界通识]。
方案视角现场先问"卡间互联带宽够不够 TP"，再看序列长度 × batch × 词表的 Logits 账——长序列场景它是第一显存大项。
讲给客户的一句话词表 15 万行的 Logits 是显存杀手——把它按卡切开、loss 各算各的再合，622MiB 直接变 311MiB。

ch38 · Sequence Parallel

先回答一个问题：权重都切完了，还有什么在每卡重复？

残差流和 LayerNorm 的激活。它们是完整的 [batch, seq, hidden]，与权重是否分片无关。本期在 Attention+MLP 权重分片不变的前提下，把这些非 TP 区域的激活沿 Sequence 维切分（Sequence Parallel，SP：激活按序列切段、每卡只存一段）。Attention 内部仍跑全序列；Context Parallel / Ring Attention 不在本期。

名词卡
名词 白话解释
激活 forward 中间结果，backward 要用所以驻留显存
SP 区域 TP 块之间做 LayerNorm/残差的部分
g（SP 版） 进 TP 块前 AllGather 拼全序列
ḡ 出 TP 块后 Reduce-Scatter 切回序列段
saved-for-backward 为反向保存的激活字节数

为什么需要它：长序列训练时激活是显存第一大头；权重切得再细，激活不切照样 OOM。

怎么工作（拆到计算步骤级）：一个 SP 区的进出是四次换手，一层重复一遍：

  1. 分片上算 norm：x_r [b, s/N, h] 上直接做 RMSNorm——它逐 Token 独立（均值只在 hidden 维）、残差逐元素，分片算等于全局算完再切片。
  2. AllGather 进 TP 块（g 算子）：把 s/N 段拼成全序列交给 Attention/MLP——Attention 是唯一的序列耦合算子，仍在 TP 区域内部跑全序列。
  3. Reduce-Scatter 出 TP 块（ḡ 算子）：Attention/MLP 输出的部分和切回每卡一段，残差加法仍在分片上——x_r += out_r。
  4. 非 TP 权重梯度 hook 同步：序列切分后每个 Rank 只看到自己的 Token，LayerNorm、最终 norm、Embedding/LM Head 的原始梯度从"天然一致"变成"部分和"——必须用钩子逐权重做 backward AllReduce SUM；漏掉任何一个，副本从第一次 optimizer step 起静默分叉。

两个反向细节：g 的 backward 是本地切片不是 Reduce-Scatter（f 已求和出一致的完整梯度，切片即可；对一致副本再 Reduce-Scatter 会放大 tp_size 倍）；ḡ 的 forward 是 Reduce-Scatter、backward 是 AllGather——两种"分散"语义不同，不能互换。Megatron 把 f 与 g 融合成一次 Reduce-Scatter 省一半反向字节，本期保留第 36 期形态、不做该融合。

显存账：saved-for-backward 的激活字节 SP < 纯 TP（README 用 ActivationLedger 实测两条线：峰值 allocated 与 saved-for-backward 字节，同 batch 两臂差值即 SP 收益）；权重布局与 ch36 完全一致不变。

算一算SP 区域的激活（LayerNorm 输出、残差流等）从 [b,s,h] 缩到 [b,s/N,h]——相对纯 TP，这部分激活字节约省 1−1/N（主实验 N=2 时约省一半的 SP 区激活）；TP 块内部激活不动。0.6B、L=512 下余额小，L=2048 时才值得付边界通信。

数字（README ch38）：主实验 W=2、L=512；代价是每并行块多一次 AllGather + 一次 Reduce-Scatter；0.6B 激活占比小，端到端吞吐可能为负，收益预期首先出现在长序列容量（capacity_probe 扫 L 到 2048）。

边界与易错：短序列下边界通信吃掉收益；Megatron 把 f 与 g 融合成一次 Reduce-Scatter 省一半反向字节，本期不做。[易错] "SP 是新并行维度"——它只切 TP 区域之间的激活，序列维切分发生在 SP 区域。

ch39 · GPipe Fill-Drain 流水

先回答一个问题：模型按层切成两半放两卡，为什么反而更慢？

因为一个 micro-batch 走流水时，任一时刻只有一张卡在算——另一张在等。Pipeline Parallel（PP，流水线并行：模型按层跨卡切成 Stage，数据像流水线一样流过）。本期把 28 层连续均分：PP=2 每 Stage 14 层、PP=4 每 Stage 7 层（0.6B 恰好整除）；唯一变量是多 micro-batch 的调度——逐个走完全流水（serial）对照先连续 Forward 再连续 Backward 的 GPipe Fill-Drain。

名词卡
名词 白话解释
Stage 流水线上的一站：连续若干层+边界件
Micro-batch 把 batch 切小后逐个喂进流水线的单位
Fill/Drain 流水的填充与排空阶段，必然有空转
Bubble 流水空转的时间占比
P2P 相邻卡点对点直传激活与梯度

为什么需要它：PP 把模型放下了，但不调度就白切——serial 模式下 S 张卡的利用率只有 1/S。

怎么工作（拆到计算步骤级）：比起 serial，GPipe 只有调度变了，四个动作扫完一步：

  1. Fill（连做 M 个 forward）：micro 1 的分段激活沿 Stage 0→1→…→S−1 的 P2P 流下去；Stage 0 不等 micro 1 走完全流水，紧接着发 micro 2 的分段——流水被逐段填满。
  2. Drain（连做 backward）：末 Stage 从 loss 反传；其余 Stage 收到自己"输出激活的输入梯度"后 autograd.backward(out, g) 启动本段反传，把输入激活的 .grad 传回上一 Stage——梯度逆流排空。
  3. tied 梯度交换：Qwen3 的 Embedding/LM Head 被 PP 拆在首末两个 Stage，各自累积不同的部分梯度——exchange_tied_gradients 反向结束后做一对 P2P（末→首、首→末），两侧都拿 g_embed + g_lm_head 再更新（每步 2 × vocab×hidden 字节）。
  4. 更新：所有 Stage 所有 micro 反传完成 + tied 交换后，各 Stage 用精确全局范数（1 次标量 AllReduce）裁剪、各自 AdamW step——与单卡逐参数一致。

baseline serial 没有第 1 步的"连续填充"：一个 micro 走完所有 Stage 才下一个，任一时刻只有一张卡在算，利用率 1/S。

显存账：激活图——serial 每 Stage 同一时刻只驻留 1 个 micro 的激活图，gpipe 要驻留 M 份（README 把这条"峰值显存差"列为机制性结论）。

算一算填充-排空模型给出 Bubble 上界 = (S−1)/(M+S−1)。PP=2、M=8：1/9 ≈ 9%；M=2：1/3——micro 数直接决定流水效率；这也是显存账的另一面：压 Bubble 靠加 M，代价是驻留 M 份激活。

数字（README ch39）：28 层 PP=2 → [14,14]、PP=4 → [7,7,7,7]；micro 扫 {2,4,8}；serial 与 gpipe 峰值显存差（1 份 vs M 份激活图）是机制性结论。

边界与易错：0.6B 太小、P2P 走 PCIe，端到端加速可能被通信吃掉甚至为负。[易错] "PP=2 就快一倍"——没有流水调度是 1/S 的利用率，有调度还有 Bubble 与激活显存代价。

产品对应Megatron-LM 的 GPipe schedule、torchgpipe [业界通识]。
方案视角现场先问"模型层数和卡数怎么配 Stage"——层数要能被 Stage 数基本整除；再问 micro 数能不能开大，micro 太少流水白搭。
讲给客户的一句话把模型按层切给多卡接力，再用多个微批把流水填满——卡越多切得越细，但"填不满"的空转要用微批数压下去。
掌握目标能算出给定 S、M 的 Bubble 上界；能画出 Fill-Drain 时序并标出空转段。

ch40 · 1F1B 流水调度

先回答一个问题：GPipe 的代价是"所有 micro 的激活图都攒在手里"，能不能边走边放？

能。1F1B（one-forward-one-backward：稳态时每做一次 Forward 就做一次 Backward）把激活生命周期从"整个 Step"缩短到"一个 micro"。Fill-Drain 下每 Stage 从 Fill 开始驻留 M 份激活图；1F1B 下每 Stage 的 in-flight 激活峰值降到 min(S−s, M) 份（s 为本 Stage 编号、S 为 Stage 总数、M 为 micro 数）。本期唯一变量：Fill-Drain 对照非交错 1F1B，Stage 划分、micro 序列、P2P 协议完全相同。

名词卡
名词 白话解释
Warm-up 开局连做若干次 Forward，凑出稳态需要的在飞深度
Steady State 一次 Forward + 一次 Backward 交替的主循环
Cool-down 结尾排空剩余 Backward
in-flight 激活 已 Forward 还没 Backward、必须驻留的激活图
1F1B 稳态 F/B 交替的流水调度

为什么需要它：M 大时 GPipe 的 M 份激活图是显存灾难；1F1B 用"更早开始 Backward"换显存，Bubble 上界不变，仍服从 (S−1)/(M+S−1)。

怎么工作（拆到计算步骤级）：Stage s 的 Step 主体切成 Warm-up/Steady/Cool-down 三段，收尾与 ch39 相同；全部由 (stage_index, S, M) 公式决定，无需额外同步：

  1. Warm-up（连做 min(S−1−s, M) 个 forward）：越靠前的 Stage 第一个 Backward 到达越晚，能提前做的 Forward 越多；M 封顶——micro 不够时 Warm-up 吃下全部，退化成 Fill-Drain 形状。
  2. Steady State（1F1B 交替）：每轮按"收激活→Forward→收梯度→Backward→发梯度→发激活"执行 M − warmup 轮——先收后发是死锁关键：gloo 这类严格阻塞传输下，若先 send 激活再 recv 梯度，相邻 Stage 可能互相等成环；先收后发打断环（NCCL 异步入队两种顺序都行，所以 CPU/GPU 同一条代码路径）。
  3. Cool-down（排空 warmup 个 backward）：稳态结束后清尾巴。
  4. 收尾与更新与 ch39 完全相同：tied 一对 P2P 交换 → 精确全局范数 → AdamW step——调度只重排时间，不改更新边界，梯度按 micro 序累加与 gpipe 逐位一致。

显存账：每个 Stage 的 in-flight 激活从 gpipe 的 M 份降到 min(S−s, M) 份（Warm-up 结束时驻留 warmup 份，稳态每轮先多拿一份再放掉一份）——这是 1F1B 的主要价值假设，benchmark 用每 Rank 峰值 allocated 对照。

算一算S=4、M=4：末 Stage（s=3）Warm-up = min(0, 4) = 0，拿到激活直接开始 F/B 交替；首 Stage（s=0）Warm-up = min(3, 4) = 3，峰值在飞 min(4−0, 4)=4 份。

数字（README ch40）：in-flight 峰值 min(S−s, M) 对照 gpipe 的 M；benchmark 扫 micro {2,4,8}，W=2 主实验、W=4 对照；主要价值假设是峰值激活显存下降而非吞吐大增。

边界与易错：Bubble 不比 GPipe 小，收益全在显存；更多次收发等待在 PCIe 小模型上可能吃掉收益。[易错] "1F1B 更快"——它先解决"放得下"，其次才是速度。

产品对应Megatron-LM 的 non-interleaved 1F1B schedule、DeepSpeed Pipeline Engine [业界通识]。
方案视角现场先问"模型层数和卡数怎么配 Stage"，再看显存瓶颈在参数还是激活——激活主导时 1F1B 优先于加大 micro。
讲给客户的一句话1F1B 让每张卡"算一个就还一个"激活，流水照样满，但显存占用从微批总数降到流水深度量级。
掌握目标能算出给定 S、s、M 的 Warm-up 数与 in-flight 峰值；能画出 1F1B 时序并对照 Fill-Drain 标出显存差。
延伸阅读GPipe (arXiv 1811.06965)——1F1B 之于它就是"按激活生命周期重排"的下一步

ch41 · Interleaved 1F1B（虚拟 Stage）

先回答一个问题：流水级数 S 被物理卡数锁死，还能再"切细"吗？

能——一个物理卡放多个非连续的虚拟 Stage（模型块）。虚拟 Stage s 位于物理 Rank s % P，total = P × vpp（P 为物理卡数、vpp 为每卡块数）。W=4、vpp=2 时 28 层切成 8 个虚拟 Stage [4,4,4,4,3,3,3,3]，每 Rank 合计仍 7 层、权重切分互补不重叠。流水级数从 P 增到 2P，Bubble 更短；代价是同一载荷要飞过 2P−1 条 Stage 边而非 P−1 条，P2P 次数约翻倍。

名词卡
名词 白话解释
虚拟 Stage 一张卡上的一个模型块，占流水线中的一级
vpp 每物理卡放的虚拟 Stage 数
Placement 表 虚拟 Stage → 物理 Rank 的映射，唯一真相来源
wrap 边 块边界从 P−1 绕回 Rank 0 的跨卡传递
isend 异步发送：投递后不等对方，先干别的

为什么需要它：Bubble 上界 (S−1)/(M+S−1) 里 S 越大 Bubble 越小；物理卡不够时，虚拟 Stage 是唯一能"加级数"的办法。

怎么工作（拆到计算步骤级）：把上一章的调度公式搬进"虚拟化 + 分组扫描"，四步：

  1. 建 Placement 表：虚拟 Stage s 位于物理 Rank s % P，是本 Rank 的第 s // P 块；stage_owner 表是唯一真相来源，所有收发先查表（28 层/P=4/vpp=2 → [4,4,4,4,3,3,3,3]，每 Rank 合计仍 7 层）。
  2. micro 按 P 分组扫描：组内按块序扫 Forward、按块逆序扫 Backward；num_micro % P ≠ 0 直接报错不做静默重排。Warm-up 数 = min(2(P−1−r) + (vpp−1)P, vpp·M)。
  3. 异步发送是死锁前提：块边界依赖闭合成环（Rank A 下一块 Forward 依赖邻居 B 当前块 Backward，B 的这次 Backward 又依赖 A 上一块产物）——开发期 CPU smoke 用阻塞 send 实测死锁。实现统一 dist.isend 立即投递、步末统一 wait：所有阻塞等待都是 recv，链条必终于无 recv 的端点（Embedding 前向或 loss 反向），可证明无环。
  4. 收尾不变：所有反传完成后物理首末 Rank 一对 tied 梯度 P2P，精确全局范数（参数在所有虚拟 Stage 互斥，1 次标量 AllReduce）裁剪、各自 AdamW step。

显存账：每 Rank 常驻权重不变（仍是 7 层），变的是 in-flight 激活——Warm-up 数从上一章的 min(S−1−s, M) 涨到 min(2(P−1−r)+(vpp−1)P, vpp·M)——多存的正是"更快填流"垫的那几份。

算一算P=4、M=8 时 P2P 激活消息数：interleaved (2×4−1)×8=60 条 vs 非交错 (4−1)×8=24 条——消息更小更密，次数与等待时间要分开读。

数字（README ch41）：total = P × vpp；W=4/vpp=2 下 8 块 [4,4,4,4,3,3,3,3]、每 Rank 7 层；micro 扫 {4,8}；warm-up 公式 min(2(P−1−r) + (vpp−1)P, vpp·M)。

边界与易错：0.6B + PCIe 上端到端可能为负；vpp>2 与自动负载均衡排除。[易错] "虚拟 Stage 免费"——它用约翻倍的 P2P 次数和更大的 in-flight 显存换 Bubble。

产品对应Megatron-LM 的 interleaved 1F1B schedule（--num-layers-per-virtual-pipeline-stage）[业界通识]。
方案视角现场先问"模型层数和卡数怎么配 Stage"——层数 ÷ (卡数 × vpp) 要基本整除；Bubble 仍是痛点时再评估 vpp=2 的通信增量。
讲给客户的一句话给每张卡发两段不相邻的模型块，流水级数翻倍、空转更短——代价是卡间点对点传输次数约翻倍。

ch42 · 混合并行与双节点 4+4

先回答一个问题：DP、TP、PP 各自学完了，生产环境怎么组合？

三维并行（TP×PP×DP 同时启用）。本期不发明新原语，把三者拼起来并在双节点 4+4 上验证。拓扑由唯一的 rank 分解公式给出：rank = dp_rank × (pp_size × tp_size) + pp_rank × tp_size + tp_rank。TP=2、PP=2、DP=2（8 rank）时：TP 组 {0,1}{2,3}{4,5}{6,7}、PP 组 {0,2}{1,3}{4,6}{5,7} 都在节点内，DP 组 {0,4}{1,5}{2,6}{3,7} 跨节点——每个节点一份完整 TP2×PP2 模型副本，训练主路径只有 DP 的梯度 AllReduce 跨节点。

名词卡
名词 白话解释
DP/TP/PP 数据/张量/流水三种并行的组合维度
Process Group 一次集合通信的"参与人名单"
逻辑 Rank 一张卡在 (dp,pp,tp) 三维坐标系里的坐标
Strong Scaling 同一全局工作量下比较不同并行布局
LOCAL_RANK 一张卡在本节点内的插槽编号

为什么需要它：单维并行各有硬边界：TP 受限于节点内带宽、PP 受限于层数与 Bubble、DP 受限于显存；生产级训练（如 Llama 系列公开配置 [业界通识]）都是三维组合。

怎么工作（拆到计算步骤级）：三维并行的全部工作就是把"谁和谁通信"建表，再沿用已知机制：

  1. 建表：rank 公式 rank = dp_rank × (pp_size × tp_size) + pp_rank × tp_size + tp_rank 唯一确定每张卡在 (dp,pp,tp) 坐标系的位置；三族组表由此导出并逐 Rank 断言"恰好划分 world"。dist.new_group 是全局集合操作——每个 Rank 必须按相同顺序创建所有组、只保留自己所在的那个；只建"自己的组"会让其他 Rank 永久等待。PP 不建组，邻接 P2P 直接用全局 rank 寻址。
  2. 数据只按 DP 切：DP rank 按 stride 取分片再切成 num_micro 个 micro-batch；TP 组内每 Rank 同一 micro-batch（TP 切权重不切数据）；PP 按 micro 顺序流过 Stage。
  3. 梯度三类不变 + DP 一次：TP shard 权重梯度 rank-local；残差流输入梯度被 f 算子已在 TP 组内求和；复制参数在 TP 组内值相同（组内再 AllReduce 会乘上 tp_size，是错误）。DP 维度上所有参数只需一次梯度 AllReduce——跨节点的就是它。
  4. 精确全局范数防重复计数：先 TP 组归约 shard 部分，再全 world 归约后除以 tp_size——每个 (dp,pp) 单元恰好被计 tp_size 次；跳过 TP 归约会把 replicated 部分乘上 tp_size。PP=1 时 tied 权重就地绑定成单参数（首末同 Stage 的特例）。

显存账：每个节点一份完整的 TP2×PP2 副本——单卡常驻 = 模型/TP + Stage 层块（PP2 下每卡 14 层），DP=2 意味着节点 0 和节点 1 各重复一份全套。 算一算：rank=5 分解：pp_size×tp_size=4，5 ÷ 4 = 1 余 1 → dp_rank=1；余 1 ÷ 2 = 0 余 1 → pp_rank=0、tp_rank=1——rank5 在节点 1、GPU 1（与 README 映射表 rank 5 / dp 1 / pp 0 / tp 1 一致）。再看冗余：每条 Stage 边界消息按 tp_rank 配对飞 tp_size 次，字节冗余 = tp_size 倍（计入 p2p_bytes 不隐藏）。

数字（README ch42）：实验 D 在双节点 4+4 上跑 TP2/PP2/DP2；Stage 连续均分 28 层 / PP=2 → [14,14]。

边界与易错：本期的调度是第 39 期 GPipe，无 1F1B/Interleaved；0.6B 上组合可能是负优化。[易错] "任意两维布局的性能差能归因到某一维"——README 明确：同时改多个维度的横向差异不写成单变量因果结论，只有单变量差分（A1→A2、B1→B2、C1→C2）才有因果意义。

ch43 · 分布式 Checkpoint 与恢复

先回答一个问题：训练跑到第 N 步断电，前面烧的卡时怎么办？

靠 Checkpoint（训练状态快照：参数、优化器状态、进度、随机数种子等一起存盘，崩溃后从快照续跑）。第 42 期之后训练状态只在各 Rank 内存里——崩溃或停机即从头再来。本期唯一变量：完整状态集中保存为单文件（rank 0 聚合写出，其他 Rank 在 barrier 等待），还是各 Rank 并行保存 Shard（分片 + manifest 清单）；torch.distributed.checkpoint（DCP）作为官方对照。

为什么需要它：快照不是只存参数——0.6B FP32 每副本约 7.2GB（参数 2.4GB + AdamW 状态 4.8GB），还要 LR 调度器、全局 Step、Sampler 游标、每 Rank 一份的 RNG 状态、拓扑与软件版本。漏任何一样，续训就"接不上"。

怎么工作（拆到计算步骤级）：快照 life-cycle 是"存 → 崩 → 载 → 续"，四步：

  1. 分片写出 + manifest：sharded 模式每个 Rank 并行写自足分片（*.tmp 写完后 os.replace 原子替换——被 Kill 的进程不可能留下会被信任的半写文件），rank 0 额外写 manifest（文件名、Rank、校验和、字节）；centralized 是 rank 0 聚合单文件、其他 Rank 在 barrier 等待。保存前先聚合各 Rank 模型校验和、必须逐位相等——AllReduce 契约一旦破坏，Checkpoint 会把分叉静默固化。
  2. 恢复时按 Rank 重分片：DDP 各 Rank 在 AllReduce 后持有逐位相同的副本，所以"分片"是可互换的完整副本——重分片退化为副本选择 + 校验：4 卡保存 → 2 卡加载，新 Rank r 读 shard-{r % 4}（rank 0 先核对 manifest 里各分片校验和一致）。跨 World Size 后 loss 只有全局值可比。
  3. 状态回填：两处著名陷阱——① LRScheduler.load_state_dict 不回写 optimizer 的 param_groups，新建调度器已把 LR 重置为 Warm-up 初值，必须用 _last_lr 回填（第 16 期的测试恰好被平坦 Warm-up 掩盖了这个错误）；② RNG 是每 Rank 状态：同 World Size 各取自己的槽位，重分片时新 Rank r 取旧 Rank r % W_old。
  4. 恢复即验证：连续性脚本对照五样——接续段逐步全局 loss、LR 序列、下一 batch 预览、RNG 指纹、最终参数校验和；同构恢复要求逐位相等，不是容差内一致。

显存账：0.6B FP32 每副本 ≈ 7.2GB（参数 2.4GB + AdamW 状态 4.8GB）都要进快照，再加 LR/进度/Sampler/每 Rank RNG/拓扑与软件版本；sharded 不省字节（总体积约等于 centralized），收益只在不并行就得不到的 I/O 时间。

算一算4 卡并行保存 7.2GB，理想写盘时间 ≈ 单 Rank 串行写的 1/4；保存时间/训练时间占比 = 保存墙钟 ÷ 单步均值（README 同进程测）——这个比值乘上保存间隔，就是训练为容错交的停摆税。

数字（README ch43）：0.6B FP32 Checkpoint ≈ 7.2GB/副本；sharded 不省字节，收益只在 I/O 并行；4 卡保存 → 2 卡加载重分片可跑。

边界与易错：异步/影子 Checkpoint、远端对象存储、ZeRO/FSDP 的真重分片（字节级实切）都排除。[易错] "存个参数就能续训"——LR、Sampler、RNG、拓扑缺一个，续跑轨迹就分叉；平坦 Warm-up 恰好会掩盖 LR 回填错误。

公式三：Token 成本（自建 vs 调 API）

自建一枚 token 的成本 ≈（卡租费 + 电 + 运维）÷（卡的 token 吞吐 × 利用率）。售前现场要做的是量级判断，不是精确报价：利用率没打满时，自建的单价可以比 API 贵几倍；利用率打满的长稳负载，自建才可能占优。原作者《自建服务器卖token的详细计算过程》《10亿Token到底需要多少钱》等帖即按此思路展开（延伸阅读）。

这章回答你迟早会被问的问题："部署一个 XXB 模型，要几张什么卡？"所有算例只用三个乘法公式 + 公开的卡型显存，不需要跑任何实验。

先立规矩：三个公式

  1. 权重显存 = 参数量 × 每参数字节数（基础概念篇的精度阶梯：FP32=4B、BF16=2B、FP8=1B、INT4=0.5B）。
  2. 每 Token 的 KV 显存 = 2 × 层数 × KV 头数 × 头维 × 每参数字节数（ch02 公式的"每条请求每一层"形态）。
  3. 全参训练常驻状态 ≈ 16 字节 × 参数量（FP32 参数+梯度 + AdamW 两个状态，ch32–34 的账本口径）。

算例一（主例）：部署一个 70B 开源模型，GPU 要多少、什么型号？

第一步：权重账。 70B 参数 × 2 字节（BF16）= 140GB。任何单卡（消费级 24–32GB、专业卡 80–141GB）都放不下——多卡并行是数学必然，不是炫技。

第二步：KV 账。 以 Llama 系 70B 结构为参照：80 层、8 个 KV 头、头维 128 [业界通识]。每 Token KV = 2×80×8×128×2B ≈ 320KiB。上下文 8K 时每条请求 ≈ 2.6GB——要接 16 路并发就是 42GB，比一半权重还多。结论提前给：70B 服务的并发上限主要卡在 KV，不在权重（这就是为什么 ch05 分页、ch08 前缀复用、ch12 换出都是部署 70B 的常用件）。

第三步：组合方案（GQA 整除校验：64 个 Q 头、8 个 KV 头 → TP=2/4/8 都能整除，ch36 的约束）：

方案 卡型 账 适用
BF16 · TP=2 2× H20-96G 权重 70G/卡 + KV 余量大 生产主流，并发上限高
BF16 · TP=4 4× A800/H800-80G 权重 35G/卡 老卡集群复用
FP8 · 单卡 1× H20-96G 权重 70G + KV/激活 ≈ 96G 顶格 单卡即服务，并发受限
W4A16 量化 1× A800-80G 或 2× 4090-24G 权重 ≈35–40G 预算敏感、并发低；量化有精度代价 [业界通识]

第四步：画结论。 报容量时永远写三行：权重 = 参数×字节；KV = 每 Token×上下文×并发；余量 = 激活+框架开销。缺任何一行，报价都经不起追问。

算例二：7B 单卡能不能上？

7B × 2B = 14GB 权重。4090-24G：14G 权重 + KV（7B 结构每 Token ≈131KiB，8K 上下文每条 ≈1.1GB）× 2 并发 ≈ 2.2G + 框架 ≈ 1G → 约 17GB，24G 卡舒服跑。同卡 FP8/INT8 更是绰绰有余——7B 是"单卡自信"区，70B 是"必须组队"区，这个分界约在 30B 上下（BF16 权重 ≈60GB 起）。

算例三：70B 全参数 SFT 训练，要什么？

训练状态 ≈ 16B × 70B = 1,120GB——还没算激活。16 张 80G 卡（1.28TB）刚好只装账本，加激活与通信缓冲，现实方案是 32 卡级 + ZeRO-3/FSDP（ch32–34），或双节点 4+4 的混合并行（ch42）。预算只有单卡？走 QLoRA：4-bit 底座 ≈35G + 少量可训参数 → 单张 80G 卡可训 [业界通识]——代价是"全参"变"适配器"，能力上限不同，方案里要写清。

算例四：Agent 应用的容量为什么爆

聊天用户每条请求的上下文是"一问一答"；Agent 是"一跑半小时"：工具结果全进上下文、多轮驻留不释放。设 500 路并发 × 平均 8K 上下文驻留：KV ≈ 500 × 2.6GB = 1.3TB——比权重还贵一个量级。这就是原作者 8/10 帖"agent 产生数百倍内存消耗"的机制版。方案组合：Prefix 复用（ch08）+ 分页（ch05）+ 换出/重算（ch12）+ 分层缓存（ch13–14），并按"并发 × 上下文 × 驻留时长"报容量，不按"日活"。

每条答案都是"机制一句话 + 出处章"。背下来不够，要能现场展开一层。

Q1 · 客户：模型 7B，一张 80GB 卡跑训练够吗？ 机制版：常驻状态 ≈ 16 字节/参数（FP32 参数+梯度+AdamW 两状态）≈ 112GB，没算激活——单卡不可能。要么 ZeRO 切分到多卡（ch32–34），要么换 bf16 纯推理思路。追问点：客户说的"训练"是全参数 SFT 还是 LoRA/推理？三者差一个数量级。

Q2 · 客户：为什么上下文越长，每次回答越慢越贵？ 机制版：KV Cache 随上下文线性涨（公式二），Decode 每步都要读全量 KV；Prefill 一次算完整个 prompt（ch02 已知边界：Decode 并非与上下文长度无关的常数复杂度）。长上下文贵在 KV 存储+带宽，不在"思考更久"。

Q3 · 客户：都说 PagedAttention 省显存，到底省在哪？ 机制版：固定批/连续批时代 KV 按"全局最长请求"预留 dense 空间，短请求的空槽全是浪费；Paged 把逻辑序列映射到固定大小物理块，按需分配释放（ch05）。省的是"预留但不填"的部分。注意边界：教学实现无 fused kernel，生产引擎另有 kernel 优化 [业界通识]。

Q4 · 客户：多轮对话/固定 system prompt，重复算不浪费？ 机制版：前缀相同 → 前缀 KV 可共享（ch08）。只共享"填满且不可变"的块，所以不用 CoW；至少重算最后一个 prompt token（KV 不存首 token 的 logits）。

Q5 · 客户：GPU 都满了，新请求进来怎么办？ 机制版：准入控制（预算/排队，ch06）→ 不够时抢占：swap 保留断点 vs 重算放弃缓存（ch12，取舍是 PCIe 时间 vs 重算算力）→ 更大规模上外部分层缓存与 PD 分离（ch13–15）。

Q6 · 领导：为什么大厂要做 PD 分离？我们用得上吗？ 机制版：Prefill 是"一次吃长序列"，Decode 是"每步走一小步"，资源形状完全不同；同一 Worker 里互相干扰（ch15）。规模大、两类负载比例失衡才值得分离；小规模上了就是纯复杂度。

Q7 · 客户：agent 应用怎么容量规划？ 机制版：先问请求形态。agent 循环式（多轮工具调用、长驻上下文）的 KV/存储消耗是聊天式的百倍量级（原作者 8/10 帖结论性观察：数百倍内存消耗）——按"并发数×上下文长度×驻留时长"算，不按"日活"算。

Q8 · 客户：国产卡/ASIC 能不能替换 NVIDIA？ 机制版：看生态三件套——CUDA 生态的 kernel 覆盖（如 FlashAttention 类算子）、通信库（NCCL 对应物）、推理引擎适配。训练侧要求更高（并行通信栈）。延伸：原作者《廉价算力的希望——ASIC芯片》《国产算力，终于要上桌吃饭了》《求寒武纪显卡推理性能》等帖（延伸阅读）。

Q9 · 领导：训练中断了怎么办，之前白跑了？ 机制版：取决于 checkpoint 覆盖度。完整训练状态=参数+优化器状态+调度器状态（warm-up 进度等，ch43）；分片保存+manifest 恢复语义最完整。没保存调度器状态的"能续"大多是假续。

Q10 · 客户：为什么你们的方案不用更大的单卡就行？ 机制版：因为三座大山（参数/梯度/优化器状态）+ KV 都吃显存，大卡只是把爆炸点推迟；ZeRO/TP/PP 是结构性解法，不是权宜（表 B）。反过来也要会讲：能单卡/少卡解决的，不上分布式——通信是真实的税。

Q11 · 面试/答辩：KV Cache 为什么有时候开了更慢？ 机制版：小模型+短上下文时，省下的计算量小于 Cache 管理开销（拼接/调度/kernel 发起）（ch02 实测：16-token 负优化，1024-token 才 1.85×）。能答出"优化有适用边界"比背加速比高一个档次。

Q12 · 面试/答辩：梯度累积和加大 batch 是一回事吗？ 机制版：等价的前提是 loss 缩放口径正确（微批 i 按 token_sum_i/total_supervised 加权，ch24）。梯度数学等价、优化器视角一样；但 BatchNorm 类统计、性能特征不同。Qwen3 用 RMSNorm，无此坑，但回答要显式提边界。

Q13 · 面试/答辩：ZeRO-1/2/3 一句话区分？ 机制版：切优化器状态 → 再切梯度 → 连参数也切（ch32–34）。代价依次是参数 AllGather、Reduce-Scatter、双向 AllGather；通信越多，换来的是常驻显存 16N/W 量级递减。

Q14 · 面试/答辩：TP 和 PP 通信量谁大？ 机制版：TP 每层都要通信（前反向高频、要求高速互联）；PP 只在 stage 边界传激活（量小但引入 bubble）。所以 TP 卡要同机高带宽，PP 可以跨机（ch35–41 的架构含义）。
