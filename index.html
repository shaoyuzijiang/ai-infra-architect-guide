ch01 · 手写 Qwen3 推理

一句话定位：不用任何推理框架，手写 Qwen3-0.6B 的 Tokenizer 与单请求自回归生成。

解决什么问题：一切推理加速的话术都建立在一个前提上——知道"大模型推理到底在算什么"。上万人同时用着传播的加速比时，谁都说不清一条请求从 Prompt 进来到文本出来经历了什么。本章把这件事拆到最底层：只用 Python 和 PyTorch 跑通生成循环，为全系列建立 baseline。

原理图解：

原理要点：

  • baseline 是"裸生成"：读取配置与 Safetensors 权重 → 手写 Byte-level BPE 与 non-thinking Chat Template → 逐层手写 Qwen3 前向 → greedy decoding 逐 Token 生成；本期唯一变量是"能否自己跑通"，不引入任何优化。
  • 对照物是 Transformers（只出现在对照程序里，不进推理路径）：相同输入、greedy 条件下，三组 Prompt 的生成 Token 逐个一致，Logits 最大误差均为 0。
  • 成本侧裸露问题：Prefill 与 Decode 是两种延迟结构——19 输入 + 32 输出在 3080 Ti 上 Prefill 34.43 ms，平均 Decode 33.40 ms/token，端到端模型计算 1069.80 ms，峰值显存 1173.80 MiB。
  • 每个 Decode 步都重新计算完整上下文（无 KV Cache）：历史越长浪费越大，这正是 ch02 的第一个优化目标。

重点：推理循环 = Prefill 一次算完整段 Prompt，再逐 Token 自回归 Decode；而 Decode 每步重算全部历史的浪费，是所有推理优化的起点。

边界与常见误区：仅支持固定 revision 的 0.6B dense 模型、batch size 1、greedy、关闭 thinking 的纯文本 system/user 模板，不支持工具调用与多模态。[易错] "手写实现不如 Transformers 准"——同为对照路径下两者逐 Token 一致，Transformers 只是正确性参照；且单次测量不能外推。

产品对应：任何推理引擎的最小可运行内核 [业界通识]；Transformers/HF 在本章只作正确性对照，不进入执行路径。

方案视角：评估任何推理优化方案之前，先要一份可复现 baseline。向供应商问两个问题："你们的加速比以什么为分母？""在什么模型、硬件、dtype 上测得？"没有 baseline 的加速比无从审计。

讲给客户的一句话：谈加速之前，先建立一份可复现的 baseline——否则"优化"无从谈起。

掌握目标：能画出单请求自回归生成的循环（Prefill + 逐步 Decode）；能答出为什么 Decode 每步成本随历史长度增长。

ch02 · KV Cache

一句话定位：把每层历史 K/V 存下来复用，Decode 只算新 Token——第一个推理优化。

解决什么问题：上万人同时用聊天模型时，每次生成一个字都要把整段历史重跑一遍模型层——上下文越长浪费越大。KV Cache 是对这个浪费的直接回应：历史 Token 的 Key/Value 算过一次就够，存下来给后面所有步复用。

原理图解：

原理要点：

  • baseline 每 Decode 步对完整上下文重跑所有模型层；variant 在 Prefill 时保留每层历史 K/V，此后每步只算新 Token 的 Q/K/V 并追加进 Cache——机制差异只在"历史是否重算"。
  • Cache 是普通 Tensor，每层一对 [batch, num_kv_heads, seq_len, head_dim]，用 torch.cat 增长；Key 在 QK Norm 与 RoPE 之后写入，位置编号从 Cache 长度续算。
  • 数据量公式 2 × layers × num_kv_heads × head_dim × seq_len × batch × dtype_bytes 线性增长，1024 Token Prompt 实测 115.39 MiB，与公式一致。
  • 实测揭示关键边界：16 Token 短 Prompt 上 KV Cache 反而负优化（端到端 1191 vs 1012 ms）——Qwen3-0.6B 单步算量极小，Python 调度、Kernel Launch 与 torch.cat 再分配把省下的计算吃掉了；到 1024 Token 才有约 1.85× 加速（Decode 均值 60.43→32.64 ms）。

重点：KV Cache 只优化 Decode、不优化 Prefill；收益随上下文变长才显现——短上下文上管理开销可能反超节省的计算。

边界与常见误区：KV Cache 不减少 Prefill 计算；Query 仍要读全部历史 K/V，Decode 不是与上下文长度无关的常数复杂度；torch.cat 动态增长的教学实现远谈不上高效。[易错] "开了 KV Cache 一定更快"——16 Token 组实测更慢，结论必须按负载给。

产品对应：所有推理引擎的核心组件；vLLM 等引擎的 Cache 预分配与分页管理（ch05 起）远优于动态 torch.cat。

方案视角：判断按 Token 计价或访谈时上下文收益的问题：客户业务 Prompt 通常多长？上下文越长，KV Cache 与其显存管理越关键；全是几十 Token 的短对话，重点反而落在调度与其他开销上。

讲给客户的一句话：KV Cache 的收益随上下文变长才显现，短 Prompt 小模型上管理开销可能吃掉全部节省。

掌握目标：能算出给定模型层数/KV 头数/head_dim/长度下 KV Cache 的字节数；能判断"开了 KV Cache 是否更快"取决于什么条件。

ch03 · Static Batching

一句话定位：把多个请求组成成员固定的 Batch 共享一次前向，提高 GPU 并行度。

解决什么问题：单请求跑模型 GPU 利用率很低——矩阵太小。把多个请求拼进同一个 Batch、共享一次模型前向，是最朴素的"凑大批"。但请求长短不齐时，padding 和"完成不能退出"会让省下来的算力又漏回去。

原理图解：

原理要点：

  • baseline 是多个带 KV Cache 的请求逐个串行执行；variant 组成成员固定的 Batch：异长 Prompt 左 Padding + Attention Mask，一次 Batched Prefill，然后按槽位同步 Batched Decode。
  • Batch 开始后不进新请求，完成请求的槽位空转到最长请求结束——输出预算 [8,16,32,64] 的批次运行到 64 轮，有效槽位利用率仅 46.88%，有效吞吐 57.63 token/s。
  • 异长 Prompt Padding 有效率 46.88% 时有效 Prompt 吞吐减半（6880.90 vs 14641.75 token/s），而 Prefill 延迟与峰值显存几乎不变——浪费来自无效 Token 也占满计算，不是"短 Prompt 拖慢 Batch"。
  • 收益侧：Batch Size 16 相对串行 makespan 约 13.98×；但 Batch Size 192 吞吐 2981.83 token/s 高于 196 的 2931.97——接近显存边界后延迟上升，最大可跑 Batch ≠ 吞吐最优 Batch（197 起在 Prefill LM Head 处 OOM）。

重点：固定 Batch 的吞吐收益来自并行度，而 padding 浪费与空转槽位会把它抵消——拼批的关键是请求长度整齐，不是越大越好。

边界与常见误区：float32 下无请求串扰；bfloat16 下 Batch Shape 改变矩阵 Kernel 的归约顺序，候选 Logits 接近时可能分叉——这是数值现象，不是"Batch 降低准确率"。离线结果不含排队与网络，不代表在线 SLO。[易错] 把 46.88% 的浪费理解成"短 Prompt 拖慢别人"——真实原因是矩形 Tensor 按最长长度执行。

产品对应：离线批量任务（评测打分、数据标注）仍用固定 Batch 思路；在线服务已被 Continuous Batching 取代。

方案视角：面向离线批量客户时问"请求长度分布是否整齐？"整齐可用静态拼批吃满并行度；在线交互业务直接看下一章。

讲给客户的一句话：拼批能提吞吐，但请求长短不齐时 padding 空转可能浪费一半算力。

掌握目标：能算出给定长度分布下 Batch 的 Padding 有效率；能区分"批越大越好"与"吞吐最优 Batch"两个命题。

ch04 · Continuous Batching

一句话定位：让已完成请求的 Batch 槽位在下一次迭代被等待请求复用。

解决什么问题：固定 Batch 里先完成的请求不退出，后面的请求只能等整批结束——在线场景下请求到达和输出长度的随机性让槽位常年空着。Continuous Batching 允许这些名额在迭代边界被"见缝插针"地补满。

原理图解：

原理要点：

  • baseline 成员固定、完成槽位空转；variant 在每次模型迭代前执行"回收完成槽位 → FCFS 填补 → 有新请求做 Batched Prefill，否则对剩余槽位 Decode"——唯一变量是"完成名额能否复用"。
  • 异长输出场景：makespan 1.169×、吞吐 +16.8%、执行槽位有效率 62.50%→74.07%；等长输出负对照两条路径几乎无差（约 0.4%）——没有可提前复用的槽位就没有收益，机制成立的前提是负载不整齐。
  • 固定到达轨迹（每 150 ms 一请求）：makespan 1.486×、TTFT p95 1511→205 ms，但 ITL p95 36.50→71.48 ms；干扰实验里 512 Token 新 Prompt 在中途到达使 ITL 最大值 35.07→72.71 ms——完整 Prefill 会阻塞已有的 Decode。
  • KV Cache 本期仍是 dense 固定容量的 [max_running_requests, heads, physical_length, head_dim] 槽位入库；新请求更长时全批左扩容搬移，这是留给 ch05 的浪费。

重点：Continuous Batching 在迭代级复用完成槽位，但新请求的完整 Prefill 会卡住已有请求 Decode——这个矛盾要等 Chunked Prefill 才能解决。

边界与常见误区：本期 Prefill 优先、FCFS 策略是为了可复现而非最优调度的声明；CPU 调度与状态管理仍有约 2.3% 开销；dense Cache 扩容须搬移。[易错] 把 ITL p95 恶化读成机制失效——是 Prefill 阻塞 Extend 其他请求的确认代价，不是复用机制的错误。

产品对应：vLLM/SGLang 等在线引擎的标准调度方式，源自 Orca 论文的 iteration-level scheduling。

方案视角：评估在线引擎时的必选能力；观察指标是" TTFT p95 和 ITL p95 是否同时可接受"——只看一项会被 Prefill 干扰欺骗。

讲给客户的一句话：Continuous Batching 让新请求见缝插针，但 Prefill 与 Decode 会互相干扰，延迟分位要一起看。

掌握目标：能画出请求在 waiting→running→finished 状态机中的槽位复用流程；能判断什么负载下 Continuous Batching 无收益。

ch05 · Paged KV Cache

一句话定位：把 KV 显存切成固定物理 Block，用 Block Table 把逻辑序列映射到物理块。

解决什么问题：dense KV Cache 按全局最长请求预留物理宽度：一个 4096 Token 的请求会让所有槽位在 4096 级别上跑 masked Attention，长度不均时显存浪费严重、并发上不去——而"上万人同时用"恰恰意味着长度分布杂乱。

原理图解：

原理要点：

  • baseline 沿用 dense 槽位，长请求加入时所有层所有槽位一起左扩容搬移、完成后宽度不回收；variant（variant 路径）借鉴操作系统虚拟内存分页：显存切成物理 Block，请求只为实际长度申请 Block，尾块浪费限制在最后一个 Block，完成后物理块直接归还复用，不动其他请求的 K/V。
  • 机制示意：一个物理 Block 携带全部层 K/V（[num_layers, 2, kv_heads, block_size, head_dim]），每请求只存 Block Table 与逻辑长度；逻辑连续不要求物理连续。
  • 成硅收益随长度不均显著增大：3072 Token 长请求下 KV 读取减少 94.1%、Cache Pool 减少 82.6%；但同并发吞吐反而降 36–45%——PyTorch reference 的 Block gather、分组 Attention 与额外 Kernel Launch 吃掉了计算节省。
  • 真正的收益在容量：12GB 卡上 dense 最大成功并发 8（12 起 OOM），paged 跑到并发 16，吞吐 157.80 token/s 高于 dense 最优约 0.9%、峰值显存低约 43.0%。

重点：分页把显存占用从"按最长请求预留"变成"按需分配"——收益主要在并发容量，同并发下的单步速度要靠专用 Kernel 而非分页本身。

边界与常见误区：减少 K/V 访问 ≠ 端到端更快，Block gather 的 Kernel 效率同样决定成败；Block Pool 按已知上界预分配、无动态准入。[易错] "上了分页吞吐就涨"——本期同并发吞吐是负的，价值在容量换吞吐。

产品对应：vLLM 的 PagedAttention；vLLM/SGLang 的专用 CUDA/Triton Kernel 直接读 Block Table，无本期 PyTorch reference 的开销。

方案视角：先问客户两个问题："你们的 Prompt 长度分布有多离散？""GPU 显存余量有多紧？"长度越离散、显存越紧张，分页收益越明显；再算容量账：同一张卡能多接多少并发。

讲给客户的一句话：分页把显存从"按最长请求预留"变成"按需分配"，同一张卡能多接一倍请求。

掌握目标：能画出 Block 的逻辑 Token 位置→物理 Block 的映射；能判断"减少 KV 读取"与"端到端变快"何时不是一回事。

ch06 · 迭代级推理请求调度器

一句话定位：在迭代边界用 Token Budget 约束每轮 Prefill 强度，保护已有 Decode。

解决什么问题：ch05 解决了显存分配，但调度本身没有"算力预算"的概念：Prefill 突发涌入时，调度器可以连续多轮做 Prefill，把已在生成中的用户长时间晾着——界面上的"系统停了"多半是这个原因。

原理图解：

原理要点：

  • baseline 是纯 FCFS：有空闲槽位就一次 Prefill 所有可加入的请求；variant 是软 Token Budget：按 padded cost batch_size × max(prompt_length) 扣预算、预算不足即停，并且已有 Decode 请求时两个 Prefill iteration 之间至少插一次 Decode iteration。
  • "软"的含义：单条 Prompt 超预算时不拆分（本期无 Chunked Prefill），允许队头超预算执行，避免 FCFS 队列永久阻塞。
  • 突发 12 条长短混合 Prompt 实测，budget 2048 相对 baseline：吞吐 +13.1%、既有请求最大 ITL 降 58.5%、突发 TTFT p95 降 15.8%、Padding 减少 53.0%。
  • 但 ITL p95 从 98.52 升到 207.37 ms：baseline 把 Prefill 集中成少数长停顿，budgeted 拆成多次中等停顿——最大值改善，p95 改善仍不成立；budget 256 过紧，反而因 6 次超预算请求吞吐 -6.8%。

重点：调度器的核心不是"多收请求"，而是限制每轮 Prefill 的预算并强制插入 Decode 轮，保护已开始的会话不被卡住。

边界与常见误区：预算按 padded 而非有效 Token 计，Padding 本身也耗预算；无显存准入、抢占、优先级与 P/D 分离。[易错] "预算调小总是更公平"——过紧的预算引发超预算执行和更多轮次开销，吞吐反向下降。

产品对应：vLLM/SGLang 的迭代级调度与 Decode 保护；max_num_batched_tokens 类参数即 Token Budget。

方案视角：评估调度策略先问两件事："单轮 Prefill 的最大时长是多少？""已有会话的最长卡顿（ITL max）是多少？"部署时 Token Budget 默认非最优，需按负载扫档。

讲给客户的一句话：调度器的核心指标是"已开始的对话不被新请求卡住"，要看最大停顿而非平均。

掌握目标：能画出 FCFS + Token Budget 的每轮选择逻辑；能判断 ITL max 与 ITL p95 何时反向变化的原因。

ch07 · Chunked Prefill

一句话定位：把长 Prompt 按预算切成多轮增量 Prefill，在 Chunk 间穿插 Decode。

解决什么问题：软预算下长 Prompt 必须整条执行——一条 2048 Token 的 Prefill 一次就叫同批 Decode 停数百毫秒，预算形同虚设。只有单条 Prompt 可拆，Token Budget 才能从"软建议"变成"硬约束"。

原理图解：

原理要点：

  • baseline（full）沿用 ch06 软预算，长 Prompt 一次完整 Prefill、可以超预算；variant（chunked）给请求新增 prefilling 状态与 prefill_cursor，Prompt 按 Token Budget 跨多轮推进，每轮只把本段 K/V 追加进 Block Table，中间 Chunk 不出 Token，最后一块完成才生成首 Token。
  • Chunk 内 Attention 用全局因果偏移：逻辑位置 q 只能看见 k ≤ q，共享同前缀长度的多请求 Chunk 由调度器分在同一轮计划。
  • 长 Prompt 干扰实验（budget 256，2048 Token）：最大单轮 Prefill 316.28→65.39 ms（-79.3%）、既有请求最大 ITL 降 67.8%、峰值显存降 16.8%；代价是长请求 TTFT +141.6%、吞吐 -6.2%——本质是延迟在请求间再分配。
  • 负对照很干净：短 Prompt（128 Token）场景没有可拆工作，chunked 反而慢 6.4%；无并行 Decode 场景中 ITL 隔离收益按定义为零。

重点：Chunked Prefill 用长请求首 Token 稍晚，换取其他请求不被一次长 Prefill 卡住——预算有硬约束的前提、单请求 Prefill 可拆分。

边界与常见误区：这是引擎内部对同一 Token 序列的增量计算，不是 RAG chunking 或流式接收；Chunk 切得越小停顿越短但迭代与 Kernel Launch 开销越多，ITL max 改善不保证 ITL p95 与吞吐同时改善。[易错] 把 Chunked Prefill 当作无条件加速器——两个负对照都证明了收益需要"有要保护的 Decode + 有要拆的长 Prompt"。

产品对应：vLLM/SGLang 均默认启用 Chunked Prefill，chunks/max_prefill_tokens 类参数控制粒度。

方案视角：负载里有长文档/Prompt 输入 + 流式输出响应交互时必开；纯批量生成（无并发交互）时收益有限，反而多吃轮次开销。

讲给客户的一句话：Chunked Prefill 用"首 Token 稍慢一点"，换"其他用户不掉帧"——本质是延迟在用户之间的再分配。

掌握目标：能画出 prefilling→running 状态下 Prefill Cursor 的推进与穿插 Decode 的时序；能判断某负载该不该开 chunked。

ch08 · Prefix Cache

一句话定位：块级缓存共享前缀的 KV Block，多请求命中同前缀时免重算。

解决什么问题：系统提示、few-shot、合同/代码模板——很多业务所有请求带着同一段长前缀。每条请求都把前缀重新 Prefill 一遍，是纯浪费。块级 Prefix Cache 让后续请求直接复用已算好的完整前缀 KV Block。

原理图解：

原理要点：

  • baseline 每条请求重算完整 Prompt；variant 匹配最长连续完整前缀，只 Prefill 未命中的后缀——机制差异只在"前缀 KV 是否重算"。
  • 缓存键是链式的：SHA256(model_namespace || parent_hash || block_token_ids)；相同 Token 块在不同历史上下文里 KV 不同，不能对单块单独哈希误判断命中。
  • 只共享已填满并发布为不可变的 Block，未填满尾块与 Decode Block 私有——因此无需 Copy-on-Write；KV 不含首 Token Logits，最多复用 prompt_length - 1，至少重算最后一个 Prompt Token。
  • 主实验（8 请求共享 2048 前缀）：热请求 service TTFT p50 降 86.30%、Prefill Token 减少 84.85%（16896→2560）；但 Makespan 只降 11.33%——Decode 不受益，且缓存池多占 280 MiB。

重点：Prefix Cache 省的是 TTFT 和 Prefill 算力，不省 Decode；生命周期靠"请求引用计数 + 缓存所有权 + leaf-LRU"管理。

边界与常见误区：不做部分块共享/COW、并发冷请求去重（in-flight dedup）、跨模型或跨进程共享（后者是 ch14）。[易错] "命中率决定一切"——readme 表明命中多但 Makespan 只小降；收益上限由 Decode 占比决定，缓存池还占用显存。

产品对应：vLLM 的 Prefix Caching、SGLang 的 RadixAttention（Radix Tree 存储）；跨进程跨实例共享见 LMCache（ch14）。

方案视角：先问"业务前缀是否整齐、多长"：高命中率业务（统一系统提示/RAG 长 context）值得开，随机对话业务收益小且占显存；有前缀的业务用指标：Prefill Token 实际数 vs 请求数。

讲给客户的一句话：前缀缓存的价值取决于前缀是否整齐——命中省的是首 Token 延迟和 Prefill 算力，Decode 一秒都省不了。

掌握目标：能画出前缀 Block 的链式哈希结构与复用流程；能判断一笔业务的前缀命中率是否值得开启该功能。

ch09 · FlashAttention

一句话定位：Triton 分块计算 + Online Softmax，Attention 中间矩阵不落全局显存。

解决什么问题：Eager Attention 显式物化 QK^T → softmax → PV 的完整 Score/Probability 矩阵，中间显存随序列长度平方增长——4096 Token 增量峰值 2576 MiB，8192 直接 OOM。长上下文生不能升，先卡在 Attention 的写法上。

原理图解：

原理要点：

  • baseline（eager）：显式物化全量 Score 矩阵再 softmax；variant（flash，手写 Triton inference-only 前向）：分块读入 K/V，每个 Query 行维护最大值 m、归一化总和 l、累加器 acc，用 Online Softmax 逐块修正（alpha = exp(m − m_new)）——完整中间矩阵不写显存。
  • 数学结果相同、计算量仍是二次方：降的是显存读写规模，不是 FLOPs。
  • 微基准（因果 Attention、head_dim 128）：1024 Token 3.38×、4096 达 3.70× 且增量峰值仅 16 MiB，8192 Token 上 eager OOM 而 flash 可用。
  • 接入完整引擎温效果为零：端到端只有 1.08–1.10×——Chunked Prefill 把 Query 限制在 256，Projection/MLP/Paged KV 读取/调度稀释了 Kernel 收益。证明面积为"Kernel 加速比 ≠ 模型加速比"。[关键细节] Chunked Prefill 要用全局因果偏移 k ≤ P + q，不能按局部位置算。

重点：FlashAttention 省的是显存搬运而非计算量；它让长序列能算，收益幅度则由 Attention 占全模型时间的比例决定。

边界与常见误区：本轮不支持 backward/任意 Mask/paging-Aware 的 Paged Attention（K/V 仍先 gather 成稠密再进 Kernel）[INV]; 教学手写实现不代表 PyTorch SDPA 或官方 flash-attn。[易错] "接入 flashattention 能带来一帧几倍"——微基准 3.7× 到引擎层只剩 1.08×，瓶颈在别处，别把 Kernel 基准宣传成产品加速能力。

产品对应：FlashAttention 官方库、vLLM/SGLang 内置融合 Attention。

方案视角：长上下文业务的前置条件（没有它 8K+ 都困难）；选型时看"Attention 占整体时间多少"而不是 Kernel 公认数字；集成后用端到端 TTFT/吞吐验证。

讲给客户的一句话：FlashAttention 省的是显存搬运，序列越长收益越大，但整体加速要看它占总时间的多少。

掌握目标：能画出 Online Softmax 的与其借助 m/l/acc 修约式流程；能判断 Kernel 级加速何以在端到端被稀释。

ch10 · CUDA Graph

一句话定位：把一轮 Decode 提前捕获成 CUDA Graph，重放时一次 Host 提交替代逐个 Launch。

解决什么问题：Decode 每步的计算量很小，而 Eager 路径单步约 1903 次 cudaLaunchKernel——GPU 在等 CPU 发号施令。小模型 Decode 的瓶颈不是算不出来，是"指挥慢于干活"。

原理图解：

原理要点：

  • baseline（static_eager）每轮逐个提交 Kernel（实测 1903 次 cudaLaunchKernel + 4 次 cudaMemcpyAsync）；variant 把同一程序提前捕获成 Graph，之后更新输入缓冲、一次 cudaGraphLaunch 重放——Host 提交从上千次变成 1 次。
  • 代价是静态化：每个 (batch_capacity, context_bucket) 建独立 Runner，预分配全部 Buffer 和覆盖整个 Bucket 的 KV Block，地址与形状不变，无效位置用 Mask 屏蔽；Replay 前可更新 Block Table 内容与输入 Token。
  • 实测：capacity 1、128 Token 下 Decode TPOT 37.90→5.22 ms（7.26×）；上下文与 Batch 变大后 GPU 工作变重，capacity 4、2048 Token 下只剩 2.25×——Graph 不减少计算，能消除的 Host 开销占比递降。
  • Capture 一次 95–140 ms，按每步节省估算 3–5 个 Decode 步即可摊销；Prefill 仍走出 Eager，所以 2048 Token 请求 TPOT 提升 4.03× 而端到端只 2.53×。

重点：CUDA Graph 消除的是 Host 提交开销，不是计算量；Batch/上下文越大、GPU 越忙，剩余收益越小。

边界与常见误区：需要 Bucket/Padding 换取可捕获性（Bucket 尾部有无效读取）；请求准入、Block 分配仍在 Graph 外；逐 Token .item() 同步会抹掉稳态收益。[易错] "Graph 静态化所以显存暴涨"——本期稳态峰值反而略低（复用 Capture 期内存），但 KV Pool 要按 Bucket 整段预留，这才是池扩展的代价所在。

产品对应：vLLM/SGLang 均对 Decode 使用 CUDA Graph，按 batch/context 档位缓存 Graph 实例。

方案视角：小模型 + 低并发（Decode 粒细）服务收益最大；大模型高并发下 Host 开销占比低，Graph 是标配但增益有限；观察点：Decode TPOT 提升 vs 端到端提升的差距。

讲给客户的一句话：CUDA Graph 解决的是"CPU 指挥慢于 GPU 计算"的问题，Batch 和上下文越大、剩余收益越小。

掌握目标：能画出 Capture 与 Replay 两段流程；能答出为什么加速比随负载变重而下降。

ch11 · Greedy Speculative Decoding

一句话定位：小 Draft Model 连提候选 Token，大 Target Model 一次批验证，减少串行调用。

解决什么问题：Decode 最大的浪费是"每出一个字都要请大模型跑一次"。Speculative Decoding 让便宜的小模型连续猜几个候选，大模型一次批验证：接受最长匹配前缀、拒绝处补 Token——数学上 Greedy 输出与只跑大模型完全一致。

原理图解：

原理要点：

  • baseline（Target-only）逐 Token 串行生成；variant：Qwen3-0.6B 作为 Draft 连提 γ 个候选，Qwen3-4B 作为 Target 一次块验证——接受最长匹配前缀、拒绝处补 Correction Token、全对补 Bonus Token，收益完全取决于接受率与两个组件的成本。
  • 两套 KV Cache 按同一接受边界提交或截断回滚——输出提交与 KV 回滚必须在同一个边界，否则两套 Cache 会漂移。
  • FP16 下与 Target-only 逐 Token 等价的确定性成立；但实测在 3080 Ti 上几乎全是负优化：中文解释负载 γ=8 接受率仅 0.173，TPOT 加速比 0.284×；只有接受率 1.0 的代码样例在 γ=8 得到 1.023×。
  • 根因在组件成本：Draft 单步 42.51 ms 只比 Target 的 48.16 ms 快约 12%——Eager 教学栈让两者都被小算子和 Host Launch 拖住，参数量 6.7 倍差距没转化为速度差；而一轮推测仍要付 γ+1 次 Draft 前向。

重点：投机解码是"用便宜计算赌接受率"；Draft 不够快或接受率不够高时是纯亏，且每轮都要多付 γ+1 次 Draft 前向。

边界与常见误区：只做 Greedy（非随机 Speculative Sampling）、Batch 1、无 MTP/EAGLE/Medusa。[易错] "Draft 候选生成器越 الاقتص也多收益越高"——γ 大则错得更远；接受率 0.357–0.833 的组别在 γ=1/2/4/8 的加速比始终低于 1——组件成本比越长才是第一关。

产品对应：vLLM/SGLang 内置 speculative decoding；MTP/EAGLE 是更轻的候选生成器，信号是"候选生成尤其便宜"场景的替代物种。

方案视角：评估模型：固有数字"是否"？"输出是否重复性强（代码/模板）"（接受率高）且"Draft 是否明显比 Target 快一个量级"（原生 MTP 或融合 Kernel）；要按业务 Prompt 分布实测，不能听开发者"理论上快"。

讲给客户的一句话：投机解码是"用便宜计算赌接受率"，Draft 不够快或接受率低时是纯亏——上线前要按业务负载实测。

掌握目标：能画出候选提出→批验证→接受/补正的流程；能按 Draft 单步加速比与接受率，判断实测是否值得上线。

ch12 · KV Cache Offloading

一句话定位：GPU Block 不足时，把受害请求的 KV 换到 CPU 或弃算，用延迟换准入。

解决什么问题：GPU 显存装不下所有并发请求的 KV，新请求进不来。乐观准入 + 抢占给出第三条路：池满了就让晚来的请求挤掉一个受害请求——受害者在哪暂停？其 KV 是搬到 CPU（swap）还是扔掉重算（recompute），这是本章的上半部。

原理图解：

原理要点：

  • 两个抢占路径对比：swap 把整请求 KV 经 PCIe 换出到 Pinned CPU 池，恢复时换回断点续算；recompute 直接丢弃 KV，恢复时对 prompt + 已生成部分重新 Prefill（另有 conservative 保守准入与 664 块大池两类对照）。
  • 为什么是整请求：Decode 每步 Attention 要读全部历史 KV，"运行中部分换出"不存在；受害单位是整请求，被暂停请求的 KV 才是"暂时无用"的部分。
  • 本环境下 swap 机制成本更低：换出+换入双向传输合计约 49–63 ms（实测约 11.9 GB/s，正值，仅限 PCIe Gen3 x16）；recompute 的重新 Prefill 暴露 673–764 ms，差距远超需带宽补偿幅度。
  • 容量收益成立：同池下 swap 吞吐 37.0 vs 保守准入 35.7 token/s（池 230）、44.9 vs 40.7（池 320），逻辑并发从 2–3 升到 4–5；但都低于 664 块大池的 45.5——池充足时抢占收益为零。

重点：抢占把"显存不足=失败/拒绝"变成"慢一点但能跑"；代价由被抢占请求的秒级暂停承担，而恢复方式的选择由带宽和重算成本的相对值决定。

边界与常见误区：换出副本只用于恢复原请求，不做复用；单请求上下文上限仍由 GPU 池决定；所有传输在默认 Stream 上同步、拷贝期间 GPU 不推进其他工作。[易错] "swap 一定优于 recompute"——端到端均值受负载支配（池 230 中 recompute 略胜），机制计时才能区分；ITL max 约等于受害请求暂停时长（秒级），不能把秒级暂停归因于几十毫秒的 PCIe 拷贝。

产品对应：vLLM 的 swap-based 抢占与 CPU Offload；Pinned Memory 池用于预分配而非临时申请。

方案视角：适用于"不能拒绝请求但可容忍偶发慢回复"的客户；池大小决策：宁可保守预留还是乐观准入+抢占？看 pipeline SLA 对秒级延迟尖刺的容忍度。

讲给客户的一句话：换出把"显存不够就失败"变成"慢一点但能跑"，代价由被抢占请求的延迟承担。

掌握目标：能画出抢占→暂停→换出→恢复的两条路径；能判断 swap 与 recompute 何者更优的判据（带宽成本 vs 重算成本）。

ch13 · KV Cache 异步传输

一句话定位：把 KV 换出/换入放到独立 Copy Stream，用 Event 管理块所有权以隐藏传输。

解决什么问题：ch12 的换出在默认计算 Stream 上同步拷贝——拷贝那几十毫秒里，GPU 只能站着等。独立 Copy Stream 让数据和计算各走各的通道，用 CUDA Event 保证"谁在搬、谁能用"的正确性。

原理图解：

原理要点：

  • baseline（sync）在计算 Stream 逐块传输，完成后调度器才继续；variant（async）在独立 Copy Stream 提交 D2H/H2D，用 CUDA Event 延迟转移 Block 所有权——D2H 完成前 GPU 源块不能释放，H2D 完成前目标块不能读；调度器只在无工作可做或下一步必须申请 Block 时才等 Event。
  • 请求新增 swapping_out / swapping_in 中间状态；Event.query() 只轮询、不等待；正确性由"所有权未转移就不动块"保证，而不是由"先拷贝完"的同步直觉保证。
  • 受控微基准证明本机具备重叠能力：传输与 BF16 GEMM 并发 1.21–1.50×；但主实验不是单向正优化：池 230 组 async 略慢（39.31 vs 39.61 token/s），池 320 组较快（47.62 vs 45.55）。
  • 机制结论看专门指标：async 把暴露等待 48.3→20.0 ms（池 230）、62.2→19.2 ms（池 320）；M 所以 D2H 在紧急水位触发、完成前源块不能释放，重叠窗口可能大部分暴露。

重点：异步传输的正确性靠 Event 管块所有权，不是靠提交顺序；能赚多少取决于"拷贝时有没有别的计算可做"——不是开了就快。

边界与常见误区："异步提交"不等于"传输已完成"；D2H 水位触发过晚时窗口大部分暴露；不实现 SSD/RDMA/预测性换出。[易错] 认为端到端应能稳定超越 sync——主实验的差异多于几十毫秒传输窗口，且单次运行波动明显，机制结论必须看分阶段 Event 指标。

产品对应：vLLM/SGLang 的 offloading 流水线、NIXL 等 KV 传输层的异步 Stream 设计。

方案视角：当抢占频繁且同时有多个请求可推进时，异步传输才显价值；评估指标是"暴露等待时间"，不是设备传输总时间。

讲给客户的一句话：异步传输用 Event 管住块所有权，收益取决于端到端是否被迫等待——不是开了就快。

ch14 · 外部 KV Cache 与 LMCache

一句话定位：用进程无关的 Token Chunk 标识 KV，使其可跨进程、跨请求、跨实例被复用。

解决什么问题：ch08 的 Prefix Cache 只在同一进程内共享物理块；引擎重启、多实例部署时，其他请求或进程命中的前缀都得重算。如果 KV 以 Token 序列为身份存在服务端，任何进程都能"Lookup 命中→加载→只算尾巴"。

原理图解：

原理要点：

  • baseline（recompute）新请求完整重算；variant（external）用链式 CacheKey SHA256(model namespace || parent digest || token ids) 标识 256 Token 的外部 Chunk，向独立 Cache Service 发 Lookup/Load/Store，命中的 CPU KV 重建到新申请的本地 GPU Block（因外部对象不含本地 Block ID，Block Table 必须重建），只 Prefill 未命中后缀。
  • 与 ch08 的关键差异：外部 Chunk 只存 prompt_length - 1 范围的完整 Block，KV 不含首 Token Logits，至少要重算最后一个 Prompt Token 才能出首 Token。
  • 正确性完美：跨进程命中 512 Token、warm Prefill 只算 1 Token、输出与重算逐位一致、Producer 退出后 Consumer 仍能命中。
  • 但性能全负优化：2048 Token 前缀 warm TTFT 2131.68 ms vs 重算 480.62 ms（0.23×）——Lookup 只要约 1 ms，成本在 TCP 传输（Payload 约 235 MB）与逐 Chunk 重建；"已经命中"不等于"值得加载"。

重点：KV 变成可跨进程命中的"外部对象"是架构上的关键一步；但加载成本必须在数据路径上被压到比重算更便宜，缓存才不会变负资产。

边界与常见误区：本期是同步 TCP + 用户态复制，非共享内存/CUDA IPC/GPUDirect/RDMA；Cache Service 无持久化、无认证。[易错] "命中了就赚"——当传输成本 > 重算成本时，命中反而在损失；负优化的存在不是机制错误，是传输路径不达标。

产品对应：LMCache（ExternalCacheClient↔Connector、Token Chunker↔Token Index、原始 KV Payload↔Memory Object、CacheStore↔CPU Backend + LRU）；vLLM 的 KV Connector 接口。

方案视角：多实例部署或服务重启频繁的业务才需要；评估按"命中率 × 复用范围 × 传输速度"三项问：Lookup 便宜吗？加载走什么路径？按业务带宽算出"加载 vs 重算"的成本临界点。

讲给客户的一句话：外部 KV Cache 的价值在"命中率 × 复用范围"，但必须保证加载比重算快——慢速传输会让缓存变负资产。

掌握目标：能画出 Lookup→Load→重建 Block Table→算尾 Token 的流程；能算出一笔前缀的"加载 vs 重算"成本临界线。

ch15 · Prefill/Decode 分离

一句话定位：Prefill 与 Decode 拆进不同 Worker，经 KV Handoff（含 ACK）实现所有权转移。

解决什么问题：Prefill 是计算密集、Decode 是访存密集，混在同一个 Worker 里互相干扰；扩容时也难以按各自瓶颈独立扩。P/D 分离的极简版：Prefill Worker 算完 Prompt KV 与首 Token，把 KV 移交给 Decode Worker 继续生成——那时才能谈"Prefill 与 Decode 独立扩容"。

原理图解：

原理要点：

  • baseline（monolithic）同一进程完成 Prefill、首 Token 与 Decode；variant（disaggregated）跨进程 Handoff：Prefill Worker 导出逻辑 KV Payload，经同步 GPU→CPU→TCP→CPU→GPU 路径发布，Decode Worker 重建本地 Paged KV 后返回 ACK。
  • ACK-gated 语义：确认所有权转移后 Decode 侧续算、首 Token 才可发给客户端；Payload 损坏或 Namespace 不匹配时回退（fallback），Decode 侧完整重算保证正确性——split TTFT = Prefill + Export + Publish + Receive + Import + ACK。
  • 与 ch14 的差异：Handoff 是同一 Request ID + Attempt ID 的一次性所有权交接，不做前缀 Lookup、不保留副本。
  • 正确性达标（三 Worker PID 不同、首 Token Logits 摘要一致、输出与 mono 逐 Token 一致），但单卡串行路径明确负优化：2048 Token 的 KV Payload 224 MiB，split TTFT 是 mono 的 5.49×（2378 vs 433 ms），其中 Publish 约 896 ms、Export 约 433 ms；换 1.7B 压力模型倍数只缩到 5.23×——"负优化是模型太小"不成立，是单请求上 split 永远比 mono 多一次 KV 交接。

重点：P/D 分离的机制价值在"角色分离后的独立扩展与干扰隔离"，而非单请求更快——单请求路径上它只是多一次昂贵的 KV 交接。

边界与常见误区：同卡串行不具备 GPU 资源隔离； HANDOFF Service 无认证/TLS。[易错] "上 P/D 分离就加速"——本期单卡实测全负优化；多 GPU 的并行吞吐收益不在范围，部署时真实收益来自多实例调度与干扰隔离，不能拿本章数字直接推产品效果。

产品对应：vLLM disaggregated prefill、DistServe、Mooncake 等多卡/多机 P/D 分离方案；KV-aware 调度是后续主题。

方案视角：大规模并发下的资源配比问题：Prefill（计算密集）与 Decode（访存密集）能否按各自瓶颈分别扩容、互不干扰？没有多卡资源隔离和 KV-aware 调度的单卡业务，P/D 分离只是"多了一次数据搬家"。

讲给客户的一句话：P/D 分离卖的是大规模下的资源配比和干扰隔离，不是单请求更快——单卡串行演示里它只会更慢。

掌握目标：能画出 ACK-gated 的 Handoff 时序（Publish/Receive/Import/ACK/释放）；能判断某业务何时该考虑 P/D 分离、何时不该。

ch18 · 固定Mini-batch（训练篇 03）

一句话定位：把逐样本累加梯度改成右 Padding 二维 Batch 一次算，同时保住训练目标。

解决什么问题：一条更新内逐个样本 Forward/Backward 太慢；但变长样本长度不一，合成二维 Batch 必须Padding，一不留神还会在合并时暗中改变训练目标。

原理图解：

原理要点：

  • baseline 是一组 [1, T_i] 调用逐样本累加梯度；variant 右 Padding 到组内最大长度后一次 [B, max(T_i)] 调用，两者用相同样本、Labels 和一次 AdamW Step。

原理要点：

ch20 · Sequence Packing（训练篇 05）

一句话定位：把多个样本装进同一物理序列，用三条 Mask 约束锁住训练语义。

解决什么问题：分桶只能缩小长度差；只要一个样本独占一行，短样本仍以 Padding 填满自己那行。要让短样本互相拼满一行，必须保证它们在 Attention 里互相看不见。

原理图解：

原理要点：

  • baseline 沿用 Padding Batch（每样本一行）；variant 用贪心装包把不切分的样本装进固定容量的 Pack，三条正确性约束缺一不可。
  • ① Position ID 从 0 重置：RoPE 是相对位置编码，不平移则后续样本全部位置错位。
  • ② Block-diagonal 加性因果 Mask：跨样本与 Padding 位置以 finfo(dtype).min 屏蔽，Softmax 权重精确为 0，隔离可逐位验证；简单的 EOS 拼接只作负对照。
  • ③ 边界 Loss Mask：Causal Shift 会让前一样本末 Token 预测下一样本首 Token，每个样本首个 Label 显式置 ignore_index。
  • 代价：每步固定成本（Optimizer、Kernel 启动）随 Pack 数线性放大，单 Pack 每步可能仍慢于多行 Padding Batch。

重点：Packing 把 Padding 换成有效 Token，但正确性靠位置重置、块对角 Mask、边界 Loss Mask 三条锁住。

边界与常见误区：装包收益由长度分布决定，收益可能被每步固定开销吃掉；实现要求模型 forward 接受 position_ids 与 4D 加性 Mask。[易错] 只拼 Token 不做 Mask 是"看似省了槽位、实则训练语义已错"的最典型事故。

产品对应： packing + block-diagonal attention [业界通识]；如数据引擎的 sequence packing 选项与多种 Mask 实现。

方案视角：语料长度方差大时 Packing 收益最大；问供应商"packing 的 mask 方案是什么、有没有逐位隔离验证"，而不是只看吞吐提升。

讲给客户的一句话：Packing 把 Padding 槽位变成有效 Token，正确性靠三条 Mask 约束锁住，缺一条训练语义就悄悄错了。

掌握目标：能画出两个样本共居一个 Pack 的 Block-diagonal Mask 结构；能答出三条约束分别防止哪种错误。

原理要点：

  • baseline 在线读 JSONL、逐条渲染编码；variant 训练前一次性编码成二进制 Shard，训练时按索引随机读取并校验。

ch22 · DataLoader预取与异步H2D（训练篇 07）

一句话定位：Worker 线程 + Pinned 双缓冲 + 独立 CUDA Stream，把"等数据"藏进"算梯度"。

解决什么问题：Shard 读取、校验、组批和 Host-to-Device 拷贝仍发生在每步关键路径上，GPU 算完就闲着等下一批数据。

原理图解：

原理要点：

  • baseline 同步串行：主线程读 Shard、组批、阻塞式 H2D 到默认流，然后计算；variant 用一个 Worker 线程把未来 Batch 物化进 Pinned Memory，有界队列深度 2。
  • Pinned Memory 是锁页内存，可被 DMA 直接异步拷贝；非锁页内存的 non_blocking 拷贝实际会退化为同步。
  • 双缓冲错拍：第 k 步计算期间，在独立 CUDA Stream 上对第 k+1 步发起 non_blocking H2D 并记录事件；计算流 wait_event 等待对应拷贝事件，Pinned 源缓冲在事件完成前不复用。
  • 可隐藏的上限就是同步路径的数据侧耗时——数据成本远小于训练 Step 时，端到端收益自然有限。
  • Worker 异常通过哨兵在主线程显式抛出，不静默吞掉。

重点：预取不是让数据变快，而是把数据侧耗时藏进计算时间窗，上限就是同步路径的数据耗时。

边界与常见误区：Worker 固定 1 个，队列深度 2 限制宿主内存占用。[易错] 以为加了 non_blocking=True 就异步了——没有 Pinned 源内存和事件管理，拷贝仍阻塞在默认流上。

产品对应：DataLoader 的 prefetch_factor + pin_memory=True + non_blocking 传输 [业界通识]。

方案视角：数据侧耗时占比可以用分段计时量出来；占比小于一成时，预取不是优先级，先看计算段，判据是 CUDA Event 分段时间线。

讲给客户的一句话：数据预取是把"等数据"藏进"算梯度"的时间窗里，能藏多少取决于数据侧原本占多少。

掌握目标：能画出双缓冲的时序图（计算 k 与拷贝 k+1 重叠）；能判断一个数据流水线瓶颈在数据侧还是计算侧。

ch23 · BF16混合精度（训练篇 08）

一句话定位：Forward/Loss 进 autocast(bfloat16)，主参数、梯度与 AdamW 状态保持 FP32。

解决什么问题：FP32 的前向/反向由 GEMM 主导，没吃到 Tensor Core 低精度算力的红利；但直接全低精度又会动优化器的数值稳定性。

原理图解：

原理要点：

  • baseline 全 FP32；variant 的 Forward 与 Loss 在 torch.autocast(bfloat16) 下执行，主参数、梯度、AdamW 状态仍 FP32——这就是"混合"的含义。
  • BF16 比 FP16 动态范围大，不需要 loss scale 的 GradScaler。
  • 效果预期：前向/反向显著缩短（GEMM 走 BF16 Tensor Core），激活显存减半但 FP32 主状态不动，峰值显存只部分下降。
  • 代价：Loss 与梯度出现 BF16 舍入级分叉并随步数累积，用轨迹误差和 dtype 普查（forward hook 逐模块记录输出 dtype、参数/梯度/优化器状态直方图）量化。
  • TF32 显式关闭并记录，避免混入第三个精度变量。

重点：混合精度省的是计算和激活，不省优化器状态；数值分叉是精度代价，要用轨迹误差盯住。

边界与常见误区：TF32 被固定关闭，防止它悄悄替你"开"了低精度 GEMM。[易错] 把 FP16 的经验（必须 GradScaler、可能 NaN）直接套到 BF16 上——BF16 的动态范围与 FP32 相同，不需要 loss scale。

产品对应：torch.autocast 混合精度；GradScaler 是 FP16 方案 [业界通识]；训练配置里的 bf16=True 选项。

方案视角：显卡有 BF16 Tensor Core 时混合精度基本是标配；问供应商"精度策略是什么、优化器状态什么 dtype、有没有轨迹误差监控"，判据是 dtype 普查而不是口头承诺。

讲给客户的一句话：混合精度省的是计算和激活，不省优化器状态；数值分叉需要用轨迹误差监控来定价。

掌握目标：能画出一行参数在混合精度下的各段 dtype（前向激活 BF16 / 主参数与优化器 FP32）；能算出激活显存大约减半而状态显存不变的账。

ch24 · 梯度累积（训练篇 09）

一句话定位：一个 Optimizer Step 由 K 个微批的梯度累加构成，用时间换显存容量。

解决什么问题：想要大 Batch 的训练语义（更稳的梯度估计），单步显存却装不下那么大的批。能不能拆成 K 次小 Forward/Backward，效果还和一次大批一样？

原理图解：

原理要点：

  • baseline 一次大 Batch 完成 Forward/Backward/Step；variant 把同一批样本切成 K 个微批，各自 Forward/Backward 累加梯度，最后一次裁剪 + Step。
  • 正确性全在加权规则：微批 i 的损失按 token_sum_i / total_supervised 缩放，累积出的梯度才与一次大 Batch 的 token_mean 严格同口径。
  • 微批均值直接平均在监督 Token 数不均时会偏离联合目标——本章用反例显式验证这一点。
  • 代价是 K 次小 GEMM 的时间加总；收益是微批级显存上限带来的容量（大批 OOM 的配置可以跑）和更少 Padding。
  • FP32 下累积梯度与大 Batch 只差求和顺序噪声。

重点：等价性的钥匙是每个微批按监督 Token 占比 token_sum_i / total_supervised 加权。

边界与常见误区：与 ch31 的 no_sync 是分布式版的天然搭档（本期是单卡）。[易错] "每个微批 Loss 取均值再平均"——监督 Token 数不均时它不等于联合 token_mean，这不是理论洁癖，是可复现的偏差。

产品对应：训练配置的 gradient_accumulation_steps [业界通识]；几乎所有训练框架的标准选项。

方案视角：客户说"显存不够上大批"时，先看能不能用累积凑出等效 Batch；判据是目标有效 Batch 大小 = 微批尺寸 × K，以及可接受的步时间增加。

讲给客户的一句话：梯度累积用时间换显存容量，等价性的钥匙是每个微批按监督 Token 占比加权。

掌握目标：能算出给定两个微批监督 Token 数下各自应有的损失缩放系数；能判断一种累积实现是否与大 Batch 同口径。

ch25 · Activation Checkpointing（训练篇 10）

一句话定位：不存全部中间激活，只存每段层输入和 RNG 状态，Backward 时重算前向。

解决什么问题：ch24 解决了大 Batch 准入，但 autograd 为 Backward 保留的中间激活仍是显存大头——28 层 Transformer 每层的注意力分数、FFN 中间值都被扣着等反向用。

原理图解：

原理要点：

  • baseline 保存全部激活到 Backward；variant 只保存每层（段）的输入，Backward 时先恢复该段 RNG 状态（dropout 等随机算子依赖它），再 enable_grad 重算一次前向、然后正常反传。

重点：激活显存可以换成约一次额外前向的时间，段数粒度就是这之间的定价表。

边界与常见误区：只存层输入的重算方案，不涉及按算子的选择性 checkpoint。[易错] "checkpoint 就是无损免费"——时间代价恒在；以及忘存 RNG 导致含 dropout 的重算逐位漂移。

产品对应：gradient checkpointing，HF Trainer 的 gradient_checkpointing=True、FSDP 内建 [业界通识]。

方案视角：显存不够、又不想减 Batch 时第一顺位开关；判据是客户能接受的步时间增幅（约 +1 次前向）与段数设置的匹配。

讲给客户的一句话：激活显存可以换成约一次额外前向的时间，段数粒度就是这之间的定价表。

掌握目标：能画出"存边界→重算→反传"的时序；能算出 28 层模型在段数为 4 时保存与重算的相对量。

ch27 · Fused AdamW（训练篇 12）

一句话定位：AdamW 数学不变，只把参数更新的 Kernel 从逐 Tensor 循环换成 foreach/fused，省发射次数。

解决什么问题：0.6B 模型有约 310 个参数 Tensor，优化器一步要为每个 Tensor 发射一串小 Kernel，逐元素算子的 Kernel 启动开销积少成多，Optimizer 段的时间不好看。

原理图解：

原理要点：

  • 三种 Kernel 组织对照：loop（逐 Tensor 循环）、foreach（多 Tensor 打包发射）、fused（单 Kernel 完成整个更新）——数学公式完全相同。
  • 用 profiler 统计一次 step 的 CUDA Kernel 数和设备时间，配合手写参照实现（含解耦权重衰减与偏置校正）验证三臂数值一致。
  • 方法论核心：算子不变，只改 Kernel 组织，开销差异就能被干净归因到"发射次数"。
  • clip_grad_norm_ 三臂走同一路径并单独计时，作为 step 分段计时的锚点。

重点：算子数学不变，只改 Kernel 组织，Optimizer 段的开销就能被干净归因和压缩。

边界与常见误区：不涉及优化器状态 dtype 与分片——那是 ZeRO-1（ch32）的事，两者维度正交。[易错] 把 fused optimizer 和"更快的收敛"混为一谈——它不改任何数学，只改执行方式。

产品对应：torch.optim.AdamW(fused=True)、apex fused optimizer [业界通识]；框架里 optim="adamw_torch_fused" 一类开关。

方案视角：参数 Tensor 多、模型小、步时间短的场景里 Optimizer 份额才显眼；判据是 profiler 分段里 optimizer 段占比，而不是无差别上 fused。

讲给客户的一句话：小 Tensor 一多，优化器也能吃掉可观的步时间——省 Kernel 发射次数是零数学风险的提速。

掌握目标：能区分 loop/foreach/fused 三种 Kernel 组织并画出它们的发射模式；能判断一个优化器加速 claim 是否涉及数学变化。

ch28 · torch.compile（训练篇 13）

一句话定位：把 Forward/Backward 交给 Inductor 编译融合，用首次编译成本换稳态 Kernel 收益。

解决什么问题：Eager 执行下逐元素算子链有大量 Kernel 启动和内存读写开销，编译能融合它们；但编译不是免费的，账要分三笔记。

原理图解：

原理要点：

  • baseline 是 Eager 执行；variant 的 Forward/Backward 交给 torch.compile（Inductor 默认配置），Loss、梯度裁剪、优化器留在 Eager。
  • 三笔必须分开记的账：稳态收益（Inductor 只能融合逐元素链，收益受 GEMM 份额限制）、首次编译成本（Break-even 摊销）、变长序列的重编译——每来一个新 shape 就触发一次编译。

重点：编译的账是"首次编译成本 vs 稳态收益"，变长输入会不断触发重编译。

边界与常见误区：编译优化器/裁剪、max-autotune、CUDA Graph 均不混入本期。[易错] 拿"首个 Step"测速——那包含编译时间；稳态收益要在编译完成后测，变长训练的主要风险就是重编译风暴。

方案视角：训练 shape 固定、长跑的生产任务是编译的好场景；短任务或 shape 多变时先算 Break-even。判据是"编译耗时 ÷ 稳态每步节省 = 多少步回本"，以及输入 shape 的分布。

讲给客户的一句话：编译的账是"首次编译成本 vs 稳态收益"，变长输入会不断触发重编译——生产里要先固定 shape 策略。

ch29 · DDP（训练篇 14）

一句话定位：两卡各持全量模型，各算各的分片，Backward 后一次 AllReduce SUM 合成全局梯度。

解决什么问题：单卡机制已被前几章压到边界，吞吐还要翻倍就得打开第一个并行维度——数据并行。但加卡不能悄悄改变训练语义，通信也会成为新瓶颈。

原理图解：

原理要点：

  • baseline 单卡算全局 Batch；variant 两张卡各持一份完整模型、完整梯度和完整优化器状态，各处理全局批次的一个分片（成员按 rank::world_size 切片）。
  • 等价性核心：本地损失按 supervised_local / supervised_global 缩放后，Backward 结束做一次 AllReduce SUM（各卡梯度求和并广播一致），与单卡大 Batch 的 token_mean 数学等价。
  • AllReduce 通信量为 2(W-1)/W·D；W=2 时每张卡每步发出约等量的 FP32 梯度数据。
  • 两卡走 PCIe 无 NVLink 时，每步约 2.4 GB 的 FP32 梯度 AllReduce 完全暴露在关键路径上，Strong Scaling 效率显著低于 2 是预期内的。
  • 正确性对照在 AllReduce 之后、裁剪之前捕获梯度（after_allreduce 钩子）；比较时点错了会看到恒定偏差，那是比较错误不是梯度错误。

重点：本地损失按监督 Token 占比缩放 + Backward 后一次 AllReduce SUM，就是数据并行的全部语义等价性。

边界与常见误区：本期不使用 Bucket 重叠（ch30）、no_sync（ch31）和状态分片（ch32/33）——通信严格排在 Backward 之后全额暴露，这正是后三章要修的。[易错] "多卡自动加速一倍"——同步点暴露时远达不到，判据是 Strong Scaling 效率。

产品对应：torch.nn.parallel.DistributedDataParallel、NCCL [业界通识]；所有训练框架多卡模式的地基。

方案视角：数据并行适合模型单卡装得下、想扩吞吐的场景；问"通信和计算重叠吗、互联是什么（PCIe/NVLink/IB）"，判据是每步通信字节数除以互联带宽。

讲给客户的一句话：数据并行的语义等价性很好证明，但后置的全量梯度同步在慢互联上会全额暴露——通信时机是下一个优化变量。

掌握目标：能画出两卡 DDP 一步的时序（前向→反向→AllReduce→更新）；能算出 W=2 时 AllReduce 的通信量 2(W-1)/W·D。

ch30 · DDP 梯度分桶与通信计算重叠

一句话定位：把梯度装进桶里，让 AllReduce 藏进 Backward。

解决什么问题：上一章的 DDP 要等所有参数的梯度都算完，才发起一次全量 AllReduce——整个通信时间赤裸裸排在关键路径上，GPU 在这段时间里纯粹等网络。真实的训练步里，靠后的参数其实早就反向算完了，为什么不让它们先去通信？

原理图解：

原理要点：

  • baseline 是"Backward 结束后一次性 AllReduce"（通信全暴露）；variant 把参数按反向就绪顺序（参数逆序）装进若干桶，某桶梯度一齐就绪就立刻以异步方式发起 AllReduce，与后续 Backward 计算重叠，步末统一等待并挂回梯度。
  • 通信数据总量不变（约 2.4 GB/步，FP32、2 卡、全局 batch 4），变的只是启动时机与分批粒度。
  • 桶大小是个双向权衡：桶过小，每次 collective 的固定延迟占比上升反而变慢；桶过大退化为基线的全暴露形态。
  • 收益上限受物理约束：无 NVLink 时走 PCIe，通信与计算共享带宽，重叠是"抢带宽"不是"变出带宽"。

重点：Bucket 化不减少通信字节数，只改变通信与计算的时间重叠关系。

边界与常见误区：

  • 本期最重要的边界：通信与计算共享带宽，重叠收益可能有限，小模型 + PCIe 上甚至接近零。
  • [易错] "分桶就是省流量"——错。分桶省的是暴露的等待时间；总字节一克都没少，桶太大还等于没分。

产品对应：PyTorch DDP 的 bucket 机制（bucket_cap_mb，默认 25MB）；DeepSpeed、Megatron-LM 的梯度引擎同构 [业界通识]。

方案视角：当客户的步时间被通信主导（梯度大、互联弱）时，bucket 重叠是零改动的第一档优化；判据是问"通信时间占步时间的比例"，以及节点内有没有 NVLink。若计算本身是大头，这一档收益不值得放进承诺。

讲给客户的一句话：把"算完再传"改成"算一部分传一部分"，通信尽量藏进计算里——在共享带宽的机器上，这是不花钱的一档优化，但收益取决于互联。

掌握目标：能画出按桶异步 AllReduce 与 Backward 重叠的时间线；能判断给定桶大小是偏"尾部等待"还是偏"退化全暴露"。

ch31 · 梯度累积期间延迟同步（no_sync）

一句话定位：K 个微步只同步最后一次，通信量降为 1/K。

解决什么问题：当一个优化步由 K 个 micro-batch 累积而成时，朴素的 DDP 会在每个微步 backward 后都做一次全量 AllReduce——前 K−1 次同步的结果马上又被本地覆盖，纯属浪费。能不能前面攒着、最后一次性同步？

原理图解：

原理要点：

  • baseline 是"每微步都同步"；variant 是前 K−1 步 no_sync（纯本地累积），最后一步统一做一次 AllReduce SUM。梯度数学不变，每步通信量降为 1/K；K=2 时省一次全量 AllReduce。
  • 正确性前提：每微步损失按监督 Token 占比缩放后，两种模式都收敛到同一个全局 token_mean 梯度。
  • [关键机制] "每微步同步"的正确实现必须用独立累加器——对已归约的累积缓冲再次 AllReduce，会把先前微步的贡献放大 World Size 倍。
  • 累积维度（本章）与单步内的重叠（ch30）是正交的两个变量，本期刻意不用 bucket 机制。

重点：no_sync 省的是同步次数：K 个微步只付 1 次 AllReduce，通信量 1/K。

边界与常见误区：

  • 本期最重要的边界：主对照 K=2（全局 batch 4）；K 增大到 4 时每卡每微步样本数在变，容量口径要跟着改。
  • [易错] 复用同一个梯度缓冲边同步边累积——会把之前微步的梯度放大 W 倍，训练悄悄发散。

产品对应：PyTorch DDP 的 no_sync() 上下文、HF accelerate 的 gradient_accumulation_steps 都是这个语义 [业界通识]。

方案视角：显存吃紧被迫用小 micro-batch 时，梯度累积是标准解；配 no_sync 后累积几乎不额外付通信。判据：看 K 与全局 batch 的关系——K 越大，这一档节省越显著；K=1 时无收益。

讲给客户的一句话：小批量攒梯度时，中间那些次同步本来就是白做的；攒到最后同步一次，梯度一样，通信开销按累积轮数成比例下降。

掌握目标：能算出给定 K 下每步 AllReduce 次数与通信量；能区分"独立累加器"与"缓冲复用"两种实现的梯度差异。

ch32 · ZeRO-1：切分优化器状态

一句话定位：AdamW 动量按 Rank 切片，状态显存除以 W。

解决什么问题：DDP 里每张卡都存着完整模型、完整梯度、完整 AdamW 状态（一二阶动量）。0.6B 模型在 12GB 显卡上，光优化器状态就足以构成容量压力——而动量这个东西，每张卡存一份其实存了 W 份一模一样的。

原理图解：

原理要点：

  • baseline 是每卡全量 AdamW 状态；variant 把动量分片存放在各 Rank（1/W），参数与梯度仍每卡全量。AdamW 是逐元素更新，"本 Rank 状态分片 × 本 Rank 梯度分片"与全量 AdamW 逐位一致。
  • 更新只发生在参数分片的所有者上；更新完成后用一次分块 AllGather（128MB 块缓冲）把新参数同步给其他 Rank。
  • 显存账（README 口径）：优化器状态从全量 12 字节/参数降为 12N/W，W=2 时状态显存减半；参数、梯度账目不变。
  • 通信账：每步新增约 1×参数字节的 AllGather——这是 DDP 没有的开销。
  • 准入含义：加大 micro-batch 或序列长度时，ZeRO-1 应比复制式 DDP 更晚 OOM。

重点：ZeRO-1 用"每步多一次参数 AllGather"换"优化器状态降到 1/W"。

边界与常见误区：

  • 本期最重要的边界：训练语义与复制式 AdamW 的等价性靠"公式逐操作镜像"保证，分片边界是非均匀的（余数分给前几个 Rank）。
  • [易错] 以为切了状态就省了通信——方向反了：ZeRO-1 是花通信（+1×参数字节 AllGather）买显存。

产品对应：DeepSpeed ZeRO Stage 1；PyTorch 侧等价思路见 FSDP 的状态分片 [业界通识]。

方案视角：模型在单卡显存里"装得下但转不开"（状态挤占激活空间）时，ZeRO-1 是第一刀；判据是看容量探针里 OOM 首先出现在状态还是激活。若模型本身就放不下，需要 ch34 的参数分片。

讲给客户的一句话：每张卡其实存了 W 份相同的动量，把它们切开只留自己那份，更新后把新参数广播回去——显存立省，代价是每步多一次参数同步。

掌握目标：能算出 N 参数模型在 W 卡上 ZeRO-1 相对 DDP 的状态显存变化；能说出新增通信的字节量级（1×参数字节/步）。

ch33 · ZeRO-2：再切分梯度

一句话定位：Reduce-Scatter 只留本 Rank 那份梯度。

解决什么问题：ZeRO-1 之后每卡还留着完整梯度——backward 结束那一刻它必须存在，可之后只有本 Rank 的那份会被本 Rank 的优化器用到。梯度也切了会怎样？

原理图解：

原理要点：

  • baseline 是完整 AllReduce（每卡拿到全量梯度）；variant 用 Reduce-Scatter：全局求和后只保留本 Rank 的分片，其余立刻释放。
  • 通信账（README 口径）：Reduce-Scatter 与 AllReduce 的每链接数据量同为 2(W−1)/W·D，W=2 时通信时间应接近——省显存几乎不多付时间。
  • 显存账（README FP32 账本）：每卡常驻模型状态从 ZeRO-1 形态降为 ZeRO-2 的 2N+14N/W——完整梯度消失，只剩 1/W 分片。
  • 代价之一：clip_grad_norm_ 不再直接可用，全局范数要由"各 Rank 分片局部范数平方和 → 一次标量 AllReduce"合成，再缩放本地分片。

重点：Reduce-Scatter = AllReduce 的省显存版：求和完只留自己那段，其余当场扔。

边界与常见误区：

  • 本期最重要的边界：真实 ZeRO 用扁平桶做 Reduce-Scatter，本期逐参数发起，固定开销如实计入、不美化。
  • [易错] 切了梯度之后照用 clip_grad_norm_——拿到的是错的范数；分片世界里连"裁剪"都需要一次跨 Rank 合成。

产品对应：DeepSpeed ZeRO Stage 2；FSDP 的梯度 Reduce-Scatter 同机制 [业界通识]。

方案视角：ZeRO-1 与 ZeRO-2 之间的选择几乎不需要权衡——W≥2 时梯度分片通信时间与完整 AllReduce 接近而显存直降。判据：确认框架版本的梯度裁剪路径是分片感知的。

讲给客户的一句话：全量梯度在每卡上只活到求和那一刻，之后 1−1/W 的部分注定没用；Reduce-Scatter 把它们当场丢掉，通信时间基本不变、梯度显存除以卡数。

掌握目标：能画出 AllReduce 与 Reduce-Scatter 的每链接数据量对比；能答出分片梯度下全局范数的三步合成方法。

ch34 · ZeRO-3 / FSDP：再切分参数

一句话定位：参数也分片常驻，用时 AllGather、算完即释放。

解决什么问题：状态和梯度都切了，参数还整份占着显存——它只在 forward/backward 里被读，却在两个优化步之间整份闲置。能不能让它也不常驻？

原理图解：

原理要点：

  • baseline（ZeRO-2）参数全量常驻；variant 里参数只以 Shard 形式常驻，获得完整生命周期：分片常驻 → Forward 前 AllGather → 计算 → Reshard（释放全量存储）→ Backward 前再 AllGather → Reduce-Scatter 梯度 → 分片 Optimizer Step。
  • 显存账（README FP32 账本）：每卡常驻从 ZeRO-2 的 2N+14N/W 降到 ZeRO-3 的 16N/W——参数、梯度、状态全部 1/W。
  • 通信账：ZeRO-1/2 的 post-step AllGather 被取消，下一个 Forward 的 AllGather 本身就是参数刷新；但通信搬进了 Forward/Backward 热路径。
  • 0.6B 上 AllGather 进热路径很可能让 Step Time 变长——负优化如实保留，收益首先出现在容量。
  • FSDP 的 Reduce-Scatter 取平均，本地损失需乘 W 校正才能对齐全局 token_mean 梯度。

重点：ZeRO-3 把常驻显存压到 16N/W，代价是 AllGather 进入前反向热路径。

边界与常见误区：

  • 本期最重要的边界：0.6B 这种单卡本可容纳的模型，ZeRO-3 往往是负优化；它的主场是大模型装不下的场景。
  • [易错] Reshard 不是"逻辑上标记释放"——全量存储必须在单元返回时真正消失，否则账是假的。

产品对应：PyTorch FSDP（FULL_SHARD）、DeepSpeed ZeRO Stage 3、Megatron-LM 的分布式优化器 [业界通识]。

方案视角：模型权重本身超过单卡显存时，ZeRO-3/FSDP 是必选项；判据直接看容量：单卡放不下参数就上 ZeRO-3，放得下就优先 ZeRO-1/2 保吞吐。还要问激活重算与 offload 是否需要一起开。

讲给客户的一句话：参数平时也只留 1/W，算哪层临时凑齐哪层、用完立刻散伙——显存账降到 16N/W，代价是通信从步末挪进了计算热路径。

掌握目标：能画出参数"分片→AllGather→Reshard→再 AllGather"的完整生命周期；能算出 W 卡上 ZeRO-2 与 ZeRO-3 的每卡常驻账（2N+14N/W 对 16N/W）。

ch35 · MLP Tensor Parallel

一句话定位：SwiGLU MLP 沿中间维切，卡间两次求和。

解决什么问题：ZeRO 系列从数据并行维度切了模型状态，但单层内部的矩阵计算与权重仍每卡完整。单层能不能也切开，让"放不下"的大层摊到多卡上？

原理图解：

原理要点：

  • baseline 是 MLP 权重完整复制（tp=1）；variant 用 Column Parallel（Gate/Up 沿输出维切）+ Row Parallel（Down 沿输入维切），Attention、Embedding、LayerNorm 仍每卡复制，单独测清 MLP TP 这一个机制。
  • 每层新增 2 次 TP AllReduce：forward 的 down_proj 输出求和、backward 的 MLP 输入梯度求和（Megatron 的 f 算子），全部暴露在关键路径上。
  • 梯度所有权三分：分片权重梯度纯本地（不通信）；MLP 输入残差流梯度必须做 backward AllReduce，漏了会有"部分梯度"静默污染下游；复制参数梯度各 Rank 天然相同，再做 AllReduce SUM 会放大 tp_size 倍——是错误不是浪费。
  • 数学上与完整 SwiGLU 等价（FP32 下仅归约顺序分叉）；0.6B 单卡放得下，TP 更可能是负优化。

重点：TP 切的是单层权重：省参数省激活，代价是每层固定两次 AllReduce。

边界与常见误区：

  • 本期最重要的边界：0.6B 上 TP 是预期内的合法负优化——机制成立与否与"当下值不值"是两回事。
  • [易错] 把复制参数的梯度也 AllReduce——直接放大 tp_size 倍；TP 组内数据相同，只有 DP 组之间才需要梯度同步。

产品对应：Megatron-LM 的 ColumnParallelLinear/RowParallelLinear；vLLM、SGLang 的 TP 推理同源 [业界通识]。

方案视角：TP 只该用在"单层放不下"的模型上，且 TP 组必须放在 NVLink/同节点内——每层的 AllReduce 对延迟极其敏感。判据：单卡（或单 NVLink 域）能否容纳最大层；跨节点做 TP 通常是方案红旗。

讲给客户的一句话：把一层的大矩阵掰成几份各算各的，每层付两次卡间求和作门票——它解决"单层放不下"，不解决"跑得更快"。

掌握目标：能画出 Column+Row Parallel 的切分位置与两次 AllReduce 时机；能区分"必须通信/禁止通信"的梯度类别。

ch36 · Attention Tensor Parallel

一句话定位：Attention Head 按 TP Rank 切，GQA 整除约束。

解决什么问题：MLP 切完之后，每层的 Attention 投影与 Head 还是完整的。Attention 天然按 Head 并行——能不能让每张卡只拿一部分 Head？

原理图解：

原理要点：

  • baseline 是 MLP TP + Attention Head 完整复制；variant 在其上把 Q/KV Head 按 TP Rank 连续切分。Qwen3-0.6B 是 GQA：32 个 Q Head、8 个 KV Head（4:1），TP=2 每 Rank 16Q/4KV、TP=4 每 Rank 8Q/2KV，每 Rank 局部 GQA 组数不变（4）。
  • 硬约束：每 Rank 必须拿到整数个完整 Head；head_dim 永不切分；per-head RMSNorm 作用在 head_dim 内，随 Head 留在本 Rank。RoPE 是 Head 内固定旋转，局部重放与全局等价。
  • 通信账：attn_tp 臂每层 2 次前向（o_proj 输出、down_proj 输出）+ 4 次反向（两个块的输入梯度 + q/k norm 梯度同步）；对照 mlp_tp 臂每层各 1 次。
  • 本期特有陷阱：q/k norm 权重复制但梯度是部分和，必须 hook 同步，否则副本从第一次更新起静默分叉。

重点：切 Attention 就是切 Head：整除是硬前提，head_dim 永不切。

边界与常见误区：

  • 本期最重要的边界：0.6B 的 Attention 占比小，预期收益有限甚至为负。
  • [易错] TP 度与 Head 数不整除还硬切——GQA 的 32Q/8KV 对 TP=2/4 都整除，但对任意 tp_size 不保证；不整除必须报错而非就近凑合。

产品对应：Megatron-LM 的 ParallelAttention；vLLM/SGLang 按 Head 切分 TP 组 [业界通识]。

方案视角：选择 TP 度时把"Q/KV Head 数能否整除"列为硬检查项；GQA 模型的 KV Head 数往往是更紧的上界（8 KV Head 天然封顶 TP=8 的头数约束 [业界通识]）。

讲给客户的一句话：Attention 天然按头并行，每卡领走整数个完整 Head 即可；但 KV Head 总数决定了能切多细，选 TP 度前先做整除检查。

掌握目标：能算出 GQA 32Q/8KV 在 TP=2/4 下每 Rank 的 Head 布局；能答出 q/k norm 梯度为什么需要额外同步。

ch37 · 词表并行 Embedding 与分布式 Cross Entropy

一句话定位：词表按 Rank 切行，Logits 不再整块物化。

解决什么问题：权重都切完了，但最后一层的 Logits 仍是全词表的大矩阵：batch 2 × seq 512 时，151936 词表的完整 Logits 约 622 MiB——TP 模型里最大的单项激活。训长序列、大 batch 时它先爆。

原理图解：

原理要点：

  • baseline 是完整词表 Logits + 完整 CE；variant 把 Embedding/LM Head 沿词表切（TP=2 每 Rank 75968 行），CE 用分布式算法：全局 max 用 AllReduce MAX、全局 exp 和用 AllReduce SUM、目标 token logit 按所属 Rank 取回。
  • 分布式 CE 的通信账：forward 新增 3 次标量级 Collective（尺寸是 token 数而非词表数），backward 0 次通信——log-sum-exp 可分块归约，softmax−onehot 只需本 Rank 分片和三个全局标量。
  • 显存账：物化的 Logits 从完整词表降为 1/tp_size（622 MiB 量级的账按 TP 度均摊，README 口径）。
  • backward 侧固定代价：LM Head 的输入梯度 dlogits_r @ W_r 是部分和，需一次 backward AllReduce（f 算子）；漏掉会让 LayerNorm 梯度跨 Rank 不一致。
  • Qwen3 的 Embedding 与 LM Head 共享权重，词表分片后两者共享同一个分片 Parameter，两条路径梯度自动累加。

重点：词表并行的本质是让 622 MiB 量级的 Logits 不物化：CE 拆成三次标量级归约。

边界与常见误区：

  • 本期最重要的边界：tp=2 下词表切分在 0.6B 上收益可能仍为负——它是长序列/大词表场景的容量技术。
  • [易错] 以为分布式 CE 的 backward 也要通信——恰好相反：backward 0 次通信，代价在 forward 的三次 Collective 和 LM Head 输入梯度那次 AllReduce。

产品对应：Megatron-LM 的 VocabParallelEmbedding/VocabParallelLMHead 与 parallel cross entropy [业界通识]。

方案视角：客户抱怨"加大 batch/长度就在 CE 层 OOM"时，先算 Logits 账：vocab×tokens×4 字节。它超过激活大头时词表并行+分布式 CE 才是对症的刀；否则先调 micro-batch。

讲给客户的一句话：输出层的 Logits 矩阵随词表和序列长度平方级膨胀；把词表切到各卡、交叉熵只传三个标量，这层显存就不再是最先爆的那块。

掌握目标：能算出给定 batch/seq/vocab 的完整 Logits 字节数；能画出分布式 CE 的三次 forward Collective 与"backward 0 通信"结构。

ch38 · Sequence Parallel

一句话定位：TP 区域之外的激活沿 Sequence 维切开。

解决什么问题：MLP、Attention、词表都切了，但残差流和 LayerNorm 的激活仍是完整的 [batch, seq, hidden]，每卡重复一份——它们和权重是否分片无关。长序列时这块越来越贵。

原理图解：

原理要点：

  • baseline（纯 TP）TP 区域间激活全量复制；variant 把残差/LN 激活沿 Sequence 维切成 [b, s/N, h]：进 TP 区域前 AllGather（g 算子），离开时 Reduce-Scatter（ḡ 算子）。
  • 数学前提：RMSNorm 逐 Token 独立、残差逐元素，所以在序列分片上计算等于全序列算完再切片；Attention 是唯一的序列耦合算子，仍在 TP 区域内部拿全序列计算。
  • 显存账：saved-for-backward 激活字节按 TP 度下降（每 Rank 只存自己 Token 窗口）；代价是每个并行块多一次 AllGather + 一次 Reduce-Scatter 的边界通信。
  • 易错点：序列切分后 LayerNorm 等复制参数的梯度从"天然一致"变成部分和，必须 hook 同步，否则副本静默分叉——与第 35/36 期的"禁止 AllReduce"正好相反。
  • 收益预期首先出现在长序列容量；0.6B、L=512 上端到端吞吐可能是负优化，如实保留。

重点：SP 切的是权重切不到的激活：序列维进 TP 区、出 TP 区，一聚一散。

边界与常见误区：

  • 本期最重要的边界：Context Parallel / Ring Attention 不在本期——Attention 内部仍跑全序列，切分只在 TP 区域之外。
  • [易错] 把 g 算子的 backward 也做成 Reduce-Scatter——f 算子已把梯度求和成一致副本，切片即可；再 Reduce-Scatter 会放大 tp_size 倍。

产品对应：Megatron-LM Sequence Parallel；Hugging Face 凡带 sequence_parallel 开关的 TP 实现同构 [业界通识]。

方案视角：长上下文训练（序列 8K+）激活显存成为大头时，SP 是与 TP 搭配的标准件 [业界通识]；短序列上它只添通信。判据：激活账占每卡显存的比例。

讲给客户的一句话：权重切完之后，激活里还有一大块每卡重复着——沿序列把它们也切开，长上下文训练的显存大头才真正松下来，代价是每层多一进一出两次通信。

掌握目标：能画出 g（AllGather）与 ḡ（Reduce-Scatter）在层内的位置；能解释为什么 SP 下 LayerNorm 梯度反而需要同步而纯 TP 下不需要。

ch39 · GPipe Fill-Drain 流水

一句话定位：模型按层跨卡切，多个微批先填满再排空。

解决什么问题：把 28 层均分到 4 张卡（PP=2 每 Stage 14 层）后，如果一个 micro-batch 从头走到尾才放下一个，任一时刻只有一张卡在算、其余全在等——并行度是假的。

原理图解：

原理要点：

  • baseline 是"一个 micro-batch 走完全流水再下一个"（serial）；variant 是 GPipe Fill-Drain：先连续做完所有 Forward（Fill），再连续做所有 Backward（Drain）。Stage 划分、权重、micro 序列、loss 口径完全一致。
  • Bubble 收益（README 口径）：填充-排空模型给出 Bubble 上界 (S−1)/(M+S−1)，micro 数 M 越大 Bubble 越小。
  • 显存账：serial 每 Stage 同一时刻只驻留 1 份激活图；gpipe 驻留 M 份——峰值激活显存随 M 线性上升，这是调度的机制性代价。
  • Backward 靠 P2P 梯度种子驱动：每个 Stage 收到输出激活的输入梯度后启动本段反传，再把输入梯度传回上一 Stage；PP 把 tied 的 Embedding/LM Head 拆到首末 Stage，每步要做一对 P2P 梯度交换。
  • 小模型走 PCIe P2P 时，调度收益可能被传输吃掉甚至为负。

重点：流水的本质是让 M 个微批在 Stage 间错峰：Bubble 压到 (S−1)/(M+S−1)，激活驻留涨 M 倍。

边界与常见误区：

  • 本期最重要的边界：PP=2 每 Stage 14 层是连续均分，不做自动负载均衡；层不均的 Stage 会拖累整条流水。
  • [易错] 以为切了层就自动并行——serial 调度下 GPU 利用率不变；真正产生重叠的是调度，不是切分。

产品对应：PyTorch 的 torch.distributed.pipelining、DeepSpeed Pipeline Engine、Megatron-LM 的 GPipe 式调度 [业界通识]。

方案视角：模型按层都放不下单卡、或单卡算一层利用率不足时才用 PP；PP 的 Bubble 上界决定它偏好配大 M。判据：Stage 划分是否均衡、M 能开多大（受激活显存反压）。

讲给客户的一句话：按层切四段后让四个微批流水错峰，卡与卡互相喂活；微批越多流水越满，但每个 Stage 要同时攥着所有微批的激活，显存按批数涨。

掌握目标：能画出 S=4、M=8 的 Fill-Drain 时空图并标出 Bubble；能算出 serial 与 gpipe 的激活驻留份数差。

ch40 · 1F1B 流水调度

一句话定位：热身几张后一前一后交替，激活驻留砍到 min(S−s, M)。

解决什么问题：Fill-Drain 的代价是每个 Stage 从 Fill 开始就攥着全部 M 份激活图直到 Drain 结束。批越大显存越爆——能不能让 Backward 提前排、激活用完就扔？

原理图解：

原理要点：

  • baseline 是 Fill-Drain（先所有 F 再所有 B）；variant 是非交错 1F1B：Stage s 先做 min(S−1−s, M) 个 Warm-up Forward，Steady State 交替一 Forward 一 Backward，最后 Cool-down 排空。
  • 激活生命周期（README 口径）：同时驻留的激活图从 M 份降到 min(S−s, M) 份——Warm-up 结束驻留 warmup 份，Steady 每轮先拿一份再放一份。1F1B 的主要价值假设是峰值激活显存下降，而非吞吐大涨。
  • Bubble 上界仍服从 (S−1)/(M+S−1)：micro 增大时两臂差距收窄。
  • 执行序完全由 (stage_index, S, M) 决定，无需额外同步；Steady 一轮固定"先收后发"以打断阻塞传输下的死锁环。
  • 梯度按 micro 序累加，与 Fill-Drain 逐位一致；tied 交换与更新边界不变。

重点：1F1B 用提前的 Backward 换激活早释放：驻留份数从 M 降到 min(S−s, M)。

边界与常见误区：

  • 本期最重要的边界：小模型 + PCIe P2P 上，调度收益可能被更多次收发等待吃掉。
  • [易错] 以为 1F1B 主要提速——它主要省显存；Bubble 上界和 Fill-Drain 相同，micro 足够大时两者时间线趋同。

产品对应：Megatron-LM 的 non-interleaved 1F1B schedule；DeepSpeed 的流水引擎默认即此形态 [业界通识]。

方案视角：PP 配置评审时问两件事：调度是 Fill-Drain 还是 1F1B、micro 数与激活驻留的乘积是多少。长序列大 batch 场景，1F1B 是让 PP 可用的前提而非可选项。

讲给客户的一句话：让每个 Stage 攒几张"热身批"后就开始边算前向边还后向账，激活用完立刻释放——显存峰值从"全部批"降到"一截流水"，批数再大也压得住。

掌握目标：能写出 Stage s 的 Warm-up 数公式并画出 S=4、M=8 的 1F1B 时空图；能判断给定显存预算下最大可用的 M 受哪一项约束。

ch41 · Interleaved 1F1B（虚拟 Stage）

一句话定位：每卡存多个非连续虚拟 Stage，流水级数翻倍压 Bubble。

解决什么问题：1F1B 仍把流水级数 S 锁死在物理卡数 P 上。Bubble 上界 (S−1)/(M+S−1) 想再降就得加大 S——卡不够，能不能让每张卡假装成多级？

原理图解：

原理要点：

  • baseline 是每卡一个连续 Stage（1F1B）；variant 是每卡 2 个非连续虚拟 Stage（total = P × vpp）：虚拟 Stage s 位于物理 Rank s % P（strided placement），28 层 / P=4 / vpp=2 时 8 个虚拟 Stage 依次 [4,4,4,4,3,3,3,3] 层，每 Rank 合计仍 7 层。
  • 调度是 Interleaved 1F1B：micro 按 P 分组，组内按块扫 Forward、按块逆序扫 Backward；micro 必须能被 P 整除，否则显式报错。
  • Bubble 与通信的交换（README 口径）：Bubble 因流水级更密而下降，但同一 [b, s, h] 载荷要飞 2P−1 条 Stage 边而非 P−1 条，P2P 次数约翻倍；Warm-up 数增大，in-flight 激活上升。
  • 依赖在块边界闭合成环，阻塞式 send 在严格阻塞传输上会死锁——统一用异步 isend 投递、所有阻塞等待都是 recv，链条必终于无 recv 的端点，可证明无环。
  • 梯度语义与更新边界不变；tied 交换发生在物理首末 Rank 之间。

重点：虚拟 Stage 是用通信次数买 Bubble：流水级数 P×vpp，P2P 次数约翻倍。

边界与常见误区：

  • 本期最重要的边界：0.6B 小模型 + PCIe P2P 上端到端吞吐可能为负优化；interleaved 的主场是大模型 + 高带宽互联。
  • [易错] 延迟发送激活"等反向完再发"——会静默打乱接收端的 FIFO 匹配，把梯度当激活；消息必须按每对每方向固定顺序立即投递。

产品对应：Megatron-LM 的 interleaved schedule（--num-layers-per-virtual-pipeline-stage） [业界通识]。

方案视角：vpp>1 是大模型 + 节点内高带宽下的精调手段，属于"压 Bubble 的最后一档"；小模型或弱互联集群上要求开 vpp 的方案应当追问动机。判据：Bubble 占比与 P2P 次数曲线的交点。

讲给客户的一句话：让每张卡兼两段不连续的层，流水从 4 级变 8 级、空窗更短；代价是块与块之间飞行的消息翻倍——高带宽互联上划算，PCIe 上未必。

掌握目标：能画出 P=4、vpp=2 的 strided placement 表；能算出 interleaved 相对 1F1B 的 P2P 次数比与 Bubble 变化方向。

ch42 · 混合并行与双节点 4+4

一句话定位：DP×TP×PP 三维组合，TP/PP 留节点内、DP 跨节点。

解决什么问题：DP、TP、PP 各自验证过了，真实集群要三者同时开：8 张卡分两个节点，哪维放节点内、哪维跨节点、rank 怎么编号——这是每个训练集群方案的顶层拓扑题。

原理图解：

原理要点：

  • baseline 是单维并行（TP2/PP1/DP1 等已验证配置）；variant 是三维组合。本期没有单一两臂对照，而是三组单变量差分（只加 PP、只加 DP、只加 DP）加一个综合配置 D（TP2/PP2/DP2，8 rank，双节点 4+4）。
  • rank 分解公式是唯一的 placement 真相来源：rank = dp_rank × (pp_size × tp_size) + pp_rank × tp_size + tp_rank。实验 D 的映射表：TP 组 {0,1}{2,3}{4,5}{6,7} 节点内，PP 组 {0,2}{1,3}… 节点内，DP 组 {0,4}{1,5}… 跨节点——每节点一份完整 TP2×PP2 副本，训练主路径只有 DP 同步跨节点。
  • 梯度所有权三类不变，DP 只做一次：TP 分片梯度 rank-local、残差流梯度 f 算子已按 TP 组求和、replicated 参数只在 DP 维做一次 AllReduce。
  • 精确全局范数要防重复计数：先在 TP 组归约分片部分，再全 world 归约后除以 tp_size。
  • 本布局的真实代价：PP 边界消息按 tp_rank 配对飞行 tp_size 次（字节冗余 = tp_size 倍），如实计入。

重点：三维并行不发明新原语：拓扑表定组，通信各回各组，TP/PP 不跨节点。

边界与常见误区：

  • 本期最重要的边界：排除 1F1B/Interleaved 调度、ZeRO 组合、SP/Vocab Parallel——任何两维同时改变的横向对比不构成单变量因果结论。
  • [易错] 只建"自己所在的组"——new_group 是全局集合操作，每个 rank 必须按相同顺序创建所有组，否则其他 rank 永久等待。

产品对应：Megatron-LM / DeepSpeed 的 3D parallelism 配置（tensor_model_parallel_size 等）；NCCL 的组划分 [业界通识]。

方案视角：给客户排拓扑时的标准顺序：TP 放 NVLink 域内、PP 放节点内、DP 承担跨节点——DP 通信是每步一次的梯度归约，最耐弱互联。判据：问节点内卡数与互联带宽，TP 度一旦要跨节点就是方案红旗。

讲给客户的一句话：8 卡两节点，节点内四张卡组成 TP2×PP2 的完整模型副本，两个副本之间只做一次梯度同步跨节点——把怕慢的通信关在节点内，把扩展性交给数据并行。

掌握目标：能写出 rank 分解公式并对实验 D 算出任意 rank 的 (dp, pp, tp) 三元组；能判断给定集群拓扑下三维各自该放哪一层。

ch43 · 分布式 Checkpoint 与恢复

一句话定位：各 Rank 并行保存分片 + manifest，替代 rank 0 单文件聚合。

解决什么问题：三维并行跑起来后，训练状态只存在于各 Rank 内存：崩溃或停机即从头再来。保存时若让 rank 0 收齐所有 Rank 的状态再写一个文件，rank 0 的网络和磁盘就是单点瓶颈——卡越多越不可用。

原理图解：

原理要点：

  • baseline 是 centralized（rank 0 聚合写单文件，其他 Rank 在 barrier 等待）；variant 是 sharded（每 Rank 并行写自足分片 + rank 0 写 manifest 清单：文件名、Rank、校验和、字节）。DDP 分片是可互换的完整副本，两种模式恢复结果必须逐位一致，差别只在 I/O。
  • 显存/字节账（README 口径）：0.6B FP32 的 Checkpoint 约为参数 2.4GB + AdamW 状态 4.8GB ≈ 7.2GB/副本；sharded 不省总字节，收益在不并行就得不到的 I/O 时间。
  • 保存清单（两模式一致）：参数、优化器一二阶矩、LR 调度器、进度/Sampler 游标、每 Rank 各一份 RNG、拓扑元数据、软件版本；全部 *.tmp + 原子替换。
  • 恢复陷阱：LRScheduler.load_state_dict 不回写 optimizer 的 param_groups，恢复后必须用 _last_lr 回填，否则续训第一步就用错学习率。
  • 重分片（4 卡保存 → 2 卡加载）：DDP 下退化为"副本选择 + 校验"，新 Rank r 读 shard-{r % 4}；字节级真重分片属于 ZeRO/FSDP 的状态形态。

重点：sharded checkpoint 的语义 = 并行 I/O + manifest：总字节不省，省的是训练停摆时间。

边界与常见误区：

  • 本期最重要的边界：异步/影子 Checkpoint、增量保存、远端对象存储都不在本期；torch.distributed.checkpoint 是官方对照路径，不是被替代的理解。
  • [易错] 认为恢复就是 load_state_dict——LR 回填、每 Rank RNG 槽位、校验和核对缺任何一项，续训都会静默偏离。

产品对应：torch.distributed.checkpoint（DCP）；Hugging Face Trainer / DeepSpeed 的分片 checkpoint 格式 [业界通识]。

方案视角：长训练预算评审必问三件事：Checkpoint 频率、保存占训练时间比、恢复演练有没有做过。分片保存是大规模集群的默认选项；判据是"保存墙钟占步时间比例"随卡数的走势，以及共享文件系统是否可用。

讲给客户的一句话：让每张卡并行写自己那份状态、用一个清单登记校验和，保存时间不再被 rank 0 单点卡死；配合故障注入演练，中断后能从最近检查点逐位接上。

掌握目标：能列出 sharded 模式 manifest 的必备字段；能答出恢复后 LR 回填与每 Rank RNG 各解决什么静默错误。

公式一：训练显存（什么时候 12GB 放不下）

FP32 混合精度训练的常驻状态 ≈ 每参数 16 字节：

组件 每参数字节 说明
参数（FP32） 4
梯度（FP32） 4
AdamW 动量 m（FP32） 4
AdamW 二阶矩 v（FP32） 4

0.6B 模型 ≈ 0.6e9 × 16B ≈ 9.6GB——所以原课程反复强调"0.6B 在 12GB 上已经足以形成容量压力"（ch32）。激活再加一截（batch × seq × hidden × 层数）。推论：7B 模型纯常驻状态 ≈ 112GB，单卡必不可能；这就是 ZeRO/切分存在的理由，不是炫技。

公式二：KV Cache 显存（什么时候上下文贵）

每章 README 给出（ch02）：

2 × layers × num_kv_heads × head_dim × sequence_length × batch × dtype_bytes

以 Qwen3-0.6B（28 层、8 KV head、head_dim 128、bf16 2B）为例，每 1024 Token 上下文约 115 MiB（ch02 实测口径：batch 1）。要点：

  • 随并发×上下文线性涨——batch 和 context 任一翻倍，KV 翻倍。长上下文服务的成本大头在 KV，不在权重。
  • GQA 的价值（ch36）：Q 32 头 / KV 8 头（4:1），KV 存储直接少 4 倍。
  • 这条公式是"KV Cache 命中与未命中的成本极限分析"那类帖子的底层（延伸阅读见原作者主页）。

公式三：Token 成本（自建 vs 调 API）

自建一枚 token 的成本 ≈（卡租费 + 电 + 运维）÷（卡的 token 吞吐 × 利用率）。售前现场要做的是量级判断，不是精确报价：利用率没打满时，自建的单价可以比 API 贵几倍；利用率打满的长稳负载，自建才可能占优。原作者《自建服务器卖token的详细计算过程》《10亿Token到底需要多少钱》等帖即按此思路展开（延伸阅读）。

Agent 场景的新变量：原作者 8/10 帖的结论性观察是 agent 场景产生数百倍于聊天场景的存储/内存消耗（多轮、工具结果、长上下文驻留）。给客户做容量规划时，先问清楚"请求是一次性还是 agent 循环式"，两者差几个数量级。

遇到瓶颈的开刀顺序（推理侧）

  1. 先削无效计算：KV Cache（ch02）→ 连续批处理（ch04）→ 长度分桶思想同样适用于推理的组批。
  2. 再管显存结构：Paged（ch05）+ Prefix 共享（ch08）——结构问题不解决，加卡只是延迟爆炸。
  3. 然后才外移：swap/重算（ch12）→ 异步分层（ch13）→ 外部 Cache（ch14）→ PD 分离（ch15）。
  4. 算子最后：FlashAttention（ch09）、CUDA Graph（ch10）——它们决定"每步多快"，前面的决定"每步算多少"。

常见售前误判：客户一抱怨慢就想"换大卡/加卡"，实际多数场景先死在调度与显存结构上。

Q1 · 客户：模型 7B，一张 80GB 卡跑训练够吗？ 机制版：常驻状态 ≈ 16 字节/参数（FP32 参数+梯度+AdamW 两状态）≈ 112GB，没算激活——单卡不可能。要么 ZeRO 切分到多卡（ch32–34），要么换 bf16 纯推理思路。追问点：客户说的"训练"是全参数 SFT 还是 LoRA/推理？三者差一个数量级。

Q2 · 客户：为什么上下文越长，每次回答越慢越贵？ 机制版：KV Cache 随上下文线性涨（公式二），Decode 每步都要读全量 KV；Prefill 一次算完整个 prompt（ch02 已知边界：Decode 并非与上下文长度无关的常数复杂度）。长上下文贵在 KV 存储+带宽，不在"思考更久"。

Q3 · 客户：都说 PagedAttention 省显存，到底省在哪？ 机制版：固定批/连续批时代 KV 按"全局最长请求"预留 dense 空间，短请求的空槽全是浪费；Paged 把逻辑序列映射到固定大小物理块，按需分配释放（ch05）。省的是"预留但不填"的部分。注意边界：教学实现无 fused kernel，生产引擎另有 kernel 优化 [业界通识]。

Q4 · 客户：多轮对话/固定 system prompt，重复算不浪费？ 机制版：前缀相同 → 前缀 KV 可共享（ch08）。只共享"填满且不可变"的块，所以不用 CoW；至少重算最后一个 prompt token（KV 不存首 token 的 logits）。

Q5 · 客户：GPU 都满了，新请求进来怎么办？ 机制版：准入控制（预算/排队，ch06）→ 不够时抢占：swap 保留断点 vs 重算放弃缓存（ch12，取舍是 PCIe 时间 vs 重算算力）→ 更大规模上外部分层缓存与 PD 分离（ch13–15）。

Q6 · 领导：为什么大厂要做 PD 分离？我们用得上吗？ 机制版：Prefill 是"一次吃长序列"，Decode 是"每步走一小步"，资源形状完全不同；同一 Worker 里互相干扰（ch15）。规模大、两类负载比例失衡才值得分离；小规模上了就是纯复杂度。

Q7 · 客户：agent 应用怎么容量规划？ 机制版：先问请求形态。agent 循环式（多轮工具调用、长驻上下文）的 KV/存储消耗是聊天式的百倍量级（原作者 8/10 帖结论性观察：数百倍内存消耗）——按"并发数×上下文长度×驻留时长"算，不按"日活"算。

Q8 · 客户：国产卡/ASIC 能不能替换 NVIDIA？ 机制版：看生态三件套——CUDA 生态的 kernel 覆盖（如 FlashAttention 类算子）、通信库（NCCL 对应物）、推理引擎适配。训练侧要求更高（并行通信栈）。延伸：原作者《廉价算力的希望——ASIC芯片》《国产算力，终于要上桌吃饭了》《求寒武纪显卡推理性能》等帖（延伸阅读）。

Q9 · 领导：训练中断了怎么办，之前白跑了？ 机制版：取决于 checkpoint 覆盖度。完整训练状态=参数+优化器状态+调度器状态（warm-up 进度等，ch43）；分片保存+manifest 恢复语义最完整。没保存调度器状态的"能续"大多是假续。

Q10 · 客户：为什么你们的方案不用更大的单卡就行？ 机制版：因为三座大山（参数/梯度/优化器状态）+ KV 都吃显存，大卡只是把爆炸点推迟；ZeRO/TP/PP 是结构性解法，不是权宜（表 B）。反过来也要会讲：能单卡/少卡解决的，不上分布式——通信是真实的税。

Q11 · 面试/答辩：KV Cache 为什么有时候开了更慢？ 机制版：小模型+短上下文时，省下的计算量小于 Cache 管理开销（拼接/调度/kernel 发起）（ch02 实测：16-token 负优化，1024-token 才 1.85×）。能答出"优化有适用边界"比背加速比高一个档次。

Q12 · 面试/答辩：梯度累积和加大 batch 是一回事吗？ 机制版：等价的前提是 loss 缩放口径正确（微批 i 按 token_sum_i/total_supervised 加权，ch24）。梯度数学等价、优化器视角一样；但 BatchNorm 类统计、性能特征不同。Qwen3 用 RMSNorm，无此坑，但回答要显式提边界。

Q13 · 面试/答辩：ZeRO-1/2/3 一句话区分？ 机制版：切优化器状态 → 再切梯度 → 连参数也切（ch32–34）。代价依次是参数 AllGather、Reduce-Scatter、双向 AllGather；通信越多，换来的是常驻显存 16N/W 量级递减。

Q14 · 面试/答辩：TP 和 PP 通信量谁大？ 机制版：TP 每层都要通信（前反向高频、要求高速互联）；PP 只在 stage 边界传激活（量小但引入 bubble）。所以 TP 卡要同机高带宽，PP 可以跨机（ch35–41 的架构含义）。
